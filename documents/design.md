# Design Notes

## Pipeline

`String pattern` → **`PatternParser`** (recursive descent) → **`PatternConstruct` AST** → **compile step** → **`MatcherConstruct` graph** → **`Matcher`** walks the graph against input, one code point at a time, with no backtracking.

### Parsing (`PatternParser` / `PatternConstruct`)

- Grammar is documented as regex-flavored BNF in comments at the top of `PatternParser.java`. It supports much of `java.util.regex.Pattern`'s syntax: groups (capturing, named, non-capturing), alternation, quantifiers (`?`, `*`, `+`, `{n,m}`, and their reluctant/possessive forms — accepted but treated as no-ops since this engine has no backtracking to be reluctant about), character classes (including nested `&&` intersection and `^` negation), escapes, boundaries (`\b`, `\B`, `\A`, `\G`, `\Z`, `\z`), and Unicode property/script/block/category classes (`\p{...}`).
- Lookahead and lookbehind are explicitly rejected at parse time (`throwUnexpectedChar("lookahead/lookbehind not supported...")`) because they can't be guaranteed to execute in linear time.
- Output is a `PatternConstruct` AST: `QuantifiedUnion` (alternation + optional quantifier + optional capture), `Sequence`, `LiteralString`, `ComplexCharacter` (a character class as a `RangeSet<Integer>`), `ComplexQuantifiedCharacter`, `BoundaryConstruct`, `BackReference`, `EndConstruct`.

### Compilation (AST → matcher graph)

- Each `PatternConstruct` compiles itself plus its "what comes next" continuation into one or more `MatcherConstruct` nodes. This is the LL(1)-flavored core of the design: instead of a generic NFA, each construct's `buildEntryMap` computes, from the *next* possible input code point, which `MatcherConstruct` to dispatch to — represented as a `RangeMap<Integer, MatcherConstruct>` ("entryMap") plus a catch-all `entryElse`.
- The critical invariant the compiler must enforce: for any `QuantifiedUnion` (i.e. any `|` alternation, and any quantified construct's "keep looping vs. exit the loop" choice), the entry ranges of its branches must be pairwise disjoint. If two branches could both match the same next code point, that's a compile-time `PatternSyntaxException` (ambiguous branch), not a runtime backtrack.
- **Status as of 2026-09-06**: implemented and tested for literals, character classes, sequences, alternation, quantifiers/loops, and capturing groups (including capturing-and-quantified at once, e.g. `(a)*` — see below). `PatternConstruct.compileAndMergeCandidates` (used by both plain alternation and loop dispatch) compiles each candidate, converts its entry ranges to a `TreeCodePointMap`, and rejects the first overlapping range with a `PatternSyntaxException` naming the candidate index and the conflicting characters. `Sequence` correctly chains each element to the one after it (tail-to-front). Remaining known gap: `BoundaryConstruct`/`BackReference` compile structurally but their `match()` still throws.
- **Quantifier/loop compilation**: a quantified construct (`QuantifiedUnion` or `ComplexQuantifiedCharacter` with `min != 1 || max != 1`) compiles to a `LoopDispatchMatcherConstruct` (the externally-visible entry point, self-registering into `owner.matcher` to break the cycle described below) whose one dispatch map routes "continue" characters through a `LoopMatcherConstruct` (enforces `max`, then dispatches to whichever body part matched) and "exit" characters through an `EndLoopMatcherConstruct` (enforces `min`, then dispatches to `next`). The *same* map serves both the first attempt and every re-check after a successful iteration — no special-casing for `min == 0` vs `min >= 1` is needed in the dispatch map itself, because the runtime min/max counters (not two different static maps) are what make one map correct for every bound: even on the very first attempt, if the input's next character happens to look like "exit", the dispatch correctly routes there and `EndLoopMatcherConstruct` correctly rejects it if `min` hasn't been satisfied yet.
- **Capturing groups**: a capturing, unquantified `QuantifiedUnion` (`captureConstructIndex != -1`) wraps its compiled alternation-dispatch node in a `BeginCaptureMatcherConstruct` (which becomes `owner.matcher`, recording the start position), and compiles its branches against a `CaptureEndMarker` — a zero-width synthetic `PatternConstruct` standing in for the real `next` — whose own matcher is an `EndCaptureMatcherConstruct` (records the substring, then forwards unconditionally to the real `next`). Capture storage (`Matcher#captureGroups`) is a flat array indexed by `captureConstructIndex`, not a stack: this engine has no recursion, so the same capture construct can never be open twice at once, and re-entering it naturally overwrites the previous `Group` — exactly regex's "last iteration wins" semantics — for free (this is exactly what the capturing-and-quantified case below relies on).
- **Capturing AND quantified at once** (e.g. `(a)*`): implemented 2026-09-06. `LoopDispatchMatcherConstruct` takes a `captureConstructIndex` (`-1` when not capturing). When capturing: each loop body part compiles against a `CaptureEndMarker` standing in for the loop's own `owner` (instead of `owner` directly), so finishing one iteration records the captured substring before looping back rather than looping back directly; and `LoopMatcherConstruct` dispatches unconditionally to a shared, internal (non-self-registering) `BeginCaptureMatcherConstruct`, which records the start position and then does the by-character dispatch among body parts itself (the dispatch that would otherwise have lived directly on `LoopMatcherConstruct`). Ambiguity detection is unaffected — it runs identically whether or not the loop is capturing, since capturing only changes what happens once a branch is chosen, not which branch gets chosen.
- `MatcherConstruct` subclasses (in `MatcherConstruct.java`) are the compiled, executable nodes: `SingleCharMatcherConstruct`, `LiteralMatcherConstruct`, `LoopMatcherConstruct`/`EndLoopMatcherConstruct` (quantifier loop counters), `BeginCaptureMatcherConstruct`/`EndCaptureMatcherConstruct`, `BoundaryMatcherConstruct`, `BackReferenceMatcherConstruct`, `EndMatcherConstruct`. Each node holds its own `dispatchMap`/`elseDispatch` and a `match(Matcher, int peeked)` method that consumes input and recurses into `getNext(...)`.
- Matching is therefore just: start at the compiled root node, and recursively call `match()`, each node consuming zero or more code points and dispatching to the next node based on a range lookup on the next code point. No backtracking stack is needed because ambiguity was already ruled out at compile time.

#### The `compile()` algorithm and cycle handling (per the project owner, 2026-09-05; implemented 2026-09-06 for the non-looping subset)

`MatcherConstruct` instances are meant to be deeply immutable once built — no self-referencing mutable fields (see "MethodHandle idea" below for why this matters). But the matcher graph *does* have cycles (a loop's body eventually dispatches back to the loop's own entry `MatcherConstruct`), so something has to break the cycle during construction without the constructed node ever seeing a half-built dependency. The intended mechanism:

- Every `PatternConstruct` has a `@MonotonicNonNull MatcherConstruct matcher` field (already present). `PatternConstruct.compile()`'s contract: if `matcher` is already non-null, return it immediately — don't rebuild. Otherwise, build `entryMap` (as today) and then construct the one `MatcherConstruct` this node compiles to.
- The key trick is in the `MatcherConstruct` subclass constructors, not in `compile()`: a `MatcherConstruct` constructor must, as its *very first* action, assign `this` to its owning `PatternConstruct`'s `matcher` field — *before* it does anything else, including looking up or compiling any of its own dependencies (e.g. what a loop dispatches back to, or what a union's branches dispatch to). Only after that assignment does the constructor walk the `PatternConstruct` graph (via each dependency's own `compile()`) to resolve the `MatcherConstruct`s it needs for its `dispatchMap`/`exitMap`, and accumulate those into its own dispatch map.
- This ordering is what makes cycles safe without any visited-set/recursion-guard bookkeeping: if compiling node A transitively needs to compile node B which loops back and needs A again, that second `compile()` call on A sees `matcher` already set (to the in-progress `A` instance) and returns it immediately, rather than recursing infinitely. The returned reference is to a real, fully-constructed-by-the-time-anyone-uses-it object — it's *only* used as a dispatch-map value (a reference to jump to), never dereferenced by the constructor that's still running, so returning a self-reference mid-construction is safe even though the object's own fields (its dispatch map) aren't filled in yet at the moment it's handed out.
- Compiling tail-to-front (i.e. `compile()` is always called with "what comes next" already known/passed in, starting from `EndConstruct` and working backwards through the pattern) is expected to make cycles rare in practice, even though the mechanism above handles them regardless.
- **Resolved 2026-09-06**: the constructor navigates via a reference to its owning `PatternConstruct`, not via extra constructor arguments per dependency. Concretely: `PatternConstruct` gained a `next` field (recorded in `compile()`); for an *acyclic* dependency, everything a `MatcherConstruct` constructor needs is already reachable off `owner` by direct field read (`owner.next.matcher`, or `owner.entryMap`'s `PatternConstruct` values' own `.matcher` fields) — no `.compile()` call needed. Loop compilation is the one case that genuinely needs the self-registration-then-*recurse* pattern (not just self-registration-then-read): `LoopDispatchMatcherConstruct`'s constructor self-registers into `owner.matcher` *first*, then calls `part.compile(owner)` for each body part — safe now, since a nested attempt by the body to read `owner.matcher` again finds the (still-being-built) `LoopDispatchMatcherConstruct` instance already there instead of recursing. This confirms the mechanism as designed: it was unnecessary complexity for every acyclic construct, and load-bearing for the one cyclic one.
- **`BoundaryConstruct`** (`\b`, `^`, `$`, etc.) has a `MatcherConstruct` (`BoundaryMatcherConstruct`) whose shape follows the same dispatch-node pattern as everything else, but its `match()` still throws `UnsupportedOperationException` — unlike the others (which are essentially "a dispatch map keyed by next code point"), a boundary match depends on matcher *state* (position, surrounding characters) rather than the next code point alone, so what `match()` actually needs to do is still open.

##### The MethodHandle idea (explicitly deferred, revived in a different form 2026-09-06)

- The original idea: instead of `dispatchMap` values being plain `MatcherConstruct` references (requiring a virtual `match()` call, i.e. a runtime vtable lookup the JIT may or may not manage to inline), pair each dispatch-map value with a `MethodHandle` bound to that node's `match` method. Conceived back when the character-range lookup was still expected to be a simple structure; once dispatch became a Guava `RangeMap` (a tree lookup) for *every* node, the trick's benefit looked moot — the range lookup itself is the bigger cost. That's why it stayed deferred through the loop/capture work above.
- **2026-09-06, revived in a different form** (per the project owner, after the loop/capture implementation landed): now that real node shapes exist, it's clear almost every `MatcherConstruct` (all but `EndLoopMatcherConstruct`; arguably `EndMatcherConstruct`, which has no successor at all) is only ever followed by exactly *one* possible next node — a `RangeMap` lookup is overkill for those specifically, not for the graph as a whole. Proposed split (not yet implemented — see remaining_work.md):
  - `MultiDispatchingMatcherConstruct` (extends `MatcherConstruct`, holds today's `dispatchMap`): only the nodes that genuinely branch on the next character — `LoopDispatchMatcherConstruct`, `DispatchMatcherConstruct`, `LoopMatcherConstruct`, `EndLoopMatcherConstruct` — extend this.
  - `SingleDispatchingMatcherConstruct` (extends `MatcherConstruct`, holds `final MatcherConstruct next` and, eventually, `final MethodHandle nextMethod`): every other node (`LiteralMatcherConstruct`, `SingleCharMatcherConstruct`, `BeginCaptureMatcherConstruct`, `EndCaptureMatcherConstruct`, `BackReferenceMatcherConstruct`, `BoundaryMatcherConstruct`) extends this instead. When such a node needs to hand off to something that *does* branch, its `next` simply points to a `MultiDispatchingMatcherConstruct` — nothing loses branching capability, only the nodes that never needed to pay for a `RangeMap` lookup stop paying for one.
  - This is exactly where the `MethodHandle` idea becomes viable again: with `next` genuinely fixed at construction time (not a per-character lookup), pairing it with a bound `MethodHandle` for the JIT is a real, measurable optimization opportunity, unlike under the all-nodes-have-a-`RangeMap` design.
  - This is a real architectural change touching most of `MatcherConstruct.java` — do it as its own focused pass, not opportunistically alongside unrelated work.

### Code point range representation

- `CodePointMap<V>` (interface) + `TreeCodePointMap<V>` (its implementation, delegating to Guava's `TreeRangeMap`) is the intended long-term replacement for ad-hoc uses of Guava `RangeSet`/`RangeMap<Integer, V>` throughout this codebase. The plan (confirmed with the project owner 2026-09-05): finish this piece first, then build the AST → matcher-graph compilation step (in particular, `QuantifiedUnion`'s branch-ambiguity detection) on top of it, rather than in parallel with it — the two were being done simultaneously before, which stalled progress.
- As of 2026-09-05 this piece is finished and tested (`TreeCodePointMapTest`, 23 cases): `[min, max)` range convention throughout, immutable `Range`, `put`/`get`/`remove`/`containsKeys`, `union`/`difference`/`intersection`, `compute`/`computeIfAbsent`, `complement`, and `intersectionRejectingConflicts` — the last one specifically added for the union/loop-ambiguity use case: it's like `intersection`, but throws `ConflictingMappingException` the moment two maps disagree on the value for an overlapping code point, which is exactly "these two branches both claim this character" in LL(1) terms.
- `CharacterClass` (a thin wrapper around `ImmutableRangeSet<Integer>`) and `PatternConstruct.ComplexCharacter`'s direct use of Guava `RangeSet<Integer>` still exist independently of `CodePointMap` — whether/how these should migrate onto `CodePointMap` is open (see below).
- `TreeCodePointMap` is deliberately not optimized for the Unicode code point domain — it's a thin adapter over a general-purpose range map. The project owner's stated intent is to swap in something more specialized (e.g. exploiting Unicode block/plane structure) later, once real usage patterns are known; the `CodePointMap` interface exists so that swap doesn't require touching any caller.

### Unicode support

- `NamedCharClass` maps regex-style named classes (`\p{Alpha}`, `\p{IsGreek}`, `\p{general_category=Lu}`, etc.) to underlying predicates/ranges.
- `UnicodePredicates` is a large (~12.9k line) generated-looking data file of Unicode category/script/block predicates. `unicodeanalyzer/` is presumably the code generator that produces it from Unicode Character Database source data — worth confirming its build wiring (is it run manually, or as part of the build?).

### Public API shape

- `Ll1Pattern` and `Matcher` are designed to mirror `java.util.regex.Pattern`/`Matcher`'s public method surface, so callers can largely swap one for the other.
- **Status as of 2026-09-06**: `matcher(CharSequence)`, `matches()`, `lookingAt()`, `find()`/`find(int)`, `group()`/`group(int)`/`group(String)`, `start()`/`start(int)`/`start(String)`, `end()`/`end(int)`/`end(String)`, `groupCount()`, `region(int,int)`, `reset()`/`reset(String)` are implemented. Still stubs: `replaceAll`/`replaceFirst`/`appendReplacement`/`appendTail`/`quoteReplacement`, `split`/`splitAsStream`, `toMatchResult`, `hitEnd`/`requireEnd`, the anchoring/transparent-bounds methods.
- **One compiled graph serves `matches()`, `lookingAt()`, and `find()`** — they don't need separate compilations. The difference between them is entirely about the `EndConstruct`/`EndMatcherConstruct` terminal: `matches()` requires the *whole region* to be consumed to succeed, while `lookingAt()`/`find()` only need a matched *prefix* (the rest of the string is allowed to be leftover). Rather than baking that choice into the compiled graph, it's a single `boolean requireFullMatch` field on `Matcher`, set immediately before each match attempt (`matches()` sets it true; `lookingAt()`/`find()` set it false) and read only by `EndMatcherConstruct.match()` (`return !matcher.requireFullMatch || matcher.pos == matcher.regionEnd;`). This mirrors how `java.util.regex`'s own NFA nodes take an "anchoring" flag rather than compiling two different automata.
- This surfaced a real bug in how `EndConstruct` (the compile-time sentinel `Ll1Pattern.compile()` passes as the outermost `next`) registered itself: it originally registered only the code point `-1` (Matcher's "no more input" sentinel — see `Matcher#peek()`) in its `entryMap`. That's sufficient for `matches()` (where reaching the terminal only ever happens at true end of input) but wrong for `lookingAt()`/`find()`: an *optional* loop's "exit" path (e.g. `a*` matched via `lookingAt()` against `"b"`) needs to be reachable at a position with real, valid leftover characters, not just at true end of string. Fixed by having `EndConstruct` set `entryElse = this` instead — reachable regardless of what character (or lack of one) comes next — with `requireFullMatch` enforcing the stricter check only when it's actually wanted.
- `Matcher#quantifiableCounts`/`captureGroups` are sized automatically from the compiled `Ll1Pattern` (`PatternParser` exposes the final quantifiable-construct count, capture-group count, and a name→`captureConstructIndex` map after `parse()` via `getQuantifiableCount()`/`getCaptureGroupCount()`/`getNamedGroups()`) — no more hand-sizing arrays in tests.
- `find()`'s unanchored search is a straightforward linear scan (`attemptMatch` at each candidate start position, `lookingAt()`-style, until one succeeds or the region is exhausted) — no special interaction with the "start at the compiled root node" design was actually needed; every candidate start position is just an ordinary `lookingAt()`-style attempt from a different `pos`.

## Open Questions

- **`SingleDispatchingMatcherConstruct`/`MultiDispatchingMatcherConstruct` split**: proposed 2026-09-06 (see "MethodHandle idea" above) to stop paying for a `RangeMap` lookup on the (large majority of) nodes that only ever have one successor. Not yet implemented.
- **Ambiguity-detection error quality**: the current `findFirstOverlap` helper in `QuantifiedUnion.buildEntryMap` does an O(branches × ranges) manual scan to find and report the first conflicting range, rather than using `CodePointMap.intersectionRejectingConflicts` directly — the latter throws immediately on any conflict but only carries stringified values, not the conflicting range/branch needed for a useful `PatternSyntaxException`. Worth revisiting if this becomes a real cost (unlikely for typical pattern sizes) or if `intersectionRejectingConflicts`'s exception is ever extended to carry structured conflict info.
- **`PatternSyntaxException.Reference`**: this type (meant to render a snippet of the pattern around an index) is constructed in a couple of places but was never actually handled in `PatternSyntaxException.throwWithReferences` — it falls through to the generic `Object` branch and prints as `Reference@<hashcode>`. Either implement it properly or stop constructing it; noted in remaining_work.md.
- **Two character-class representations**: decide whether/when to migrate `PatternConstruct.ComplexCharacter`'s direct `RangeSet<Integer>` usage onto the `CodePointMap` family, or keep them separate for different purposes (a character class is fundamentally "ranges → is a member", not "ranges → arbitrary value", so a dedicated type may still make sense even after `CodePointMap` exists).
- **`CodePointMap`'s eventual optimized implementation**: what data structure replaces `TreeCodePointMap`'s `TreeRangeMap` delegation? (e.g. sorted-array binary search, or a trie/radix structure exploiting Unicode block boundaries.) Deliberately deferred until real usage patterns from finishing the compiler are known.
- **Boundary matching (`BoundaryConstruct`/`BoundaryMatcherConstruct`)**: per the project owner, this was "the only real openish question" in the overall matcher-graph design — everything else is essentially a dispatch map keyed on the next code point, but a boundary (`\b`, `^`, `$`, `\A`, `\Z`, `\z`, ...) depends on matcher state (position, surrounding characters) rather than the next code point. How it fits the same node shape (or whether it needs a different one) is undecided.
- **Backreferences**: `BackReferenceMatcherConstruct` is unimplemented (`match()` throws), and is also noted as "not actually context-free" in the parser's grammar comments — worth revisiting whether/how they fit the LL(1) model at all, or whether they need a special-cased runtime check.
- **Reluctant/possessive quantifiers**: parser currently accepts and no-ops them (per comment, "reluctant and possessive quantifiers are no-ops in this Pattern"). Confirm this is the intended permanent semantic (i.e., this engine has one matching behavior, and the reluctant/possessive distinction from `java.util.regex` doesn't apply) and document it prominently for users migrating from `java.util.regex`.
