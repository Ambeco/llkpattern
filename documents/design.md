# Design

## Pipeline

`String pattern` → **`PatternParser`** (recursive descent) → **`PatternConstruct` AST** → **compile step** → **`MatcherConstruct` graph** → **`Matcher`** walks the graph against input, one code point at a time, with no backtracking.

### Parsing (`PatternParser` / `PatternConstruct`)

- Grammar is documented as regex-flavored BNF in comments at the top of `PatternParser.java`. It supports much of `java.util.regex.Pattern`'s syntax: groups (capturing, named, non-capturing), alternation, quantifiers (`?`, `*`, `+`, `{n,m}`, and their reluctant/possessive forms — accepted but treated as no-ops since this engine has no backtracking to be reluctant about), character classes (including nested `&&` intersection and `^` negation), escapes, boundaries (`\b`, `\B`, `\A`, `\G`, `\Z`, `\z`), and Unicode property/script/block/category classes (`\p{...}`).
- **The single-pass architecture, and what it rules out.** Matching never looks at the input string as a whole: it revolves entirely around a *position* between two code points, advanced by `Matcher#peek()` (the code point about to be consumed) and inspected one code point backward by `Matcher#peekPrevious()` (used by `\b`/`\B`, see "Boundary matching" below) — never more than one code point in either direction, never speculatively. This is what guarantees linear-time matching, and it's also the reason for several of this engine's intentional divergences from `java.util.regex` (see README's "Intentional differences" list for the full, corpus-checked catalogue):
  - **Every union branch and every loop's body-vs-exit choice must claim a distinct "next" code point** (`.` aside, which is defined as "whatever a sibling branch doesn't claim" specifically so it can coexist with one) — this is the compile-time disjointness check described below, and it's the direct consequence of a `Matcher` that can only ever look at *one* upcoming code point to decide which branch it's in, never several code points ahead.
  - **Positive lookahead (`(?=...)`) is rejected** as a direct side effect of that same constraint: a lookahead's body can match input of unknown, even variable, length before the engine would know whether it succeeded, which is exactly the "look arbitrarily far ahead before committing to a branch" the distinct-next-code-point rule exists to rule out.
  - **General lookbehind (`(?<=...)`/`(?<!...)`) is rejected**, except for a lookbehind whose body matches exactly one code point (`(?<=x)`/`(?<!x)` for a single character or character class) — not yet implemented, but planned, since it's a direct generalization of the one-code-point-backward check `\b`/`\B` already perform via `peekPrevious()`, requiring no new architectural capability. A lookbehind of more than one code point would need to look arbitrarily far backward, which `peekPrevious()`'s single-code-point contract doesn't support and isn't planned to be extended to, for the same "would require exploring several possible interpretations rather than reading one committed position" reason lookahead is rejected.
  - **A multi-code-point loop body that matches part of itself and then fails is not retried with fewer iterations** (e.g. `(ab)+` finds nothing in `"abac"`) — there is no way to un-consume input already read once the position has advanced past it, for the same reason a general lookahead/lookbehind can't be supported.
  - Rejecting lookahead/lookbehind is a permanent characteristic of this design, not a "not yet implemented" gap: supporting them in general would mean exploring a branch's possible outcome before committing to it, which is materially the same problem backtracking solves, and reintroducing it here would give up the single-pass guarantee this whole engine exists for. (`throwUnexpectedChar("lookahead/lookbehind not supported...")` at parse time.)
- Output is a `PatternConstruct` AST: `QuantifiedUnion` (alternation + optional quantifier + optional capture), `Sequence`, `LiteralString`, `ComplexCharacter` (a character class as a `CodePointSet`), `ComplexQuantifiedCharacter`, `BoundaryConstruct` (`\A`, `\Z`, `\z`), `LineBoundaryConstruct` (`^`, `$`), `WordBoundaryConstruct` (`\b`, `\B`) — the latter two split out separately, see "Boundary matching" below — `BackReference`, `EndConstruct`. `\G` produces no AST node at all — see "Boundary matching".

### Compilation (AST → matcher graph)

- Each `PatternConstruct` compiles itself plus its "what comes next" continuation into one or more `MatcherConstruct` nodes. This is the LL(1)-flavored core of the design: instead of a generic NFA, each construct's `buildEntryMap` computes the set of code points that count as *this construct's own* entry point — represented as a plain `CodePointSet` ("entryMap") plus a catch-all `entryElse`. It's a set, not a "code point -> owning construct" map, because every `entryMap` is built by exactly one construct for itself (never aliased from another), so "who owns this range" is always already known from context — every consumer either already has that construct in hand, or (when merging multiple candidates' entry points — see `mergeEntryPoints` below) unions each candidate's own entry set directly, by pulling, with no per-candidate identity tagging needed at all.
- The critical invariant the compiler must enforce: for any `QuantifiedUnion` (i.e. any `|` alternation, and any quantified construct's "keep looping vs. exit the loop" choice), the entry ranges of its branches must be pairwise disjoint. If two branches could both match the same next code point, that's a compile-time `PatternSyntaxException` (ambiguous branch), not a runtime backtrack. `PatternConstruct.mergeEntryPoints` (used by both plain alternation and a quantified construct's own entry point) computes each candidate's own entry ranges; `PatternConstruct.checkDisjoint` (called both from `buildFlattenedChain`, for a plain union's own dispatch, and directly from `QuantifiableConstruct.buildLoopMatcher`, for the loop-body-vs-`next` case) rejects the first pair of candidates whose entry ranges overlap with a `PatternSyntaxException` naming the candidate index and the conflicting characters — a plain pairwise `CodePointSet#intersects` scan, no map/allocation needed to find the conflict itself.
- **Quantifier/loop compilation**: a quantified construct (`QuantifiedUnion` or `ComplexQuantifiedCharacter` with `min != 1 || max != 1`) compiles to a small graph, built by `QuantifiableConstruct.buildLoopMatcher`:
  1. **The body's own dispatch chain** — one node per body part, each part's own compiled `MatcherConstruct` given an `entrySet`/`failedEntry` pair (see "Opcode set" below) rather than a separate wrapping node: on a membership miss, a part defers to the next part in priority order, and the last part defers to the loop's own exit node (below). This chain's head does DOUBLE DUTY as both the loop's externally-visible entry point (`owner.matcher`) and the loop-back target reached after a completed iteration — there is no separate entry-only chain the way an N-way dispatch table (or the old fork-chain design — see "Alternatives Considered") would need one: a fresh entry (zero iterations so far) and a re-check after some iterations both just mean "try the body head again," and the body's own `failedEntry` chain already correctly falls through to the exit node in either case — including the `min == 0` "skip the loop entirely" case, which needs no special-casing at all here (the exit node's own `min` check, not any entry-time logic, is what actually allows it — see point 3).
  2. **`LoopMatcherConstruct`**, self-registered onto a throwaway `LoopBackMarker` (not `owner`) *before* the body compiles against that marker, breaking the construction-time cycle every loop body creates (the body's own compiled matcher loops back to this node). Reached only as the body chain's own successor once an iteration finishes — never as the loop's entry point (that's the body chain's head, above) — so `match()` unconditionally counts one more completed iteration, then dispatches back to the body chain's head (another attempt) if under `max`, or straight to the exit node (forcing a stop) otherwise. It does no code-point membership test of its own at all; that decision now lives entirely in the body chain's own `entrySet` checks.
  3. **`LoopMatcherExit`** — this loop's "stop iterating" node, reached either because the body chain naturally didn't match (any position, first attempt or re-check alike) or because `LoopMatcherConstruct` forced a stop at `max`. Enforces `min` (failing the whole match if too few iterations happened) and, on success, resets the shared iteration counter before dispatching to `next`'s own matcher. Never itself gated by an `entrySet` — every code-point decision that used to live in a combined loop/exit dispatch lives entirely in the body chain now.

  Under `CASE_INSENSITIVE`, a body part's `entrySet` has any same-flags folding baked in at compile time (`MatcherConstruct#foldedEntrySet`, i.e. folded at the leaves: a literal's or backreference's entry set via `CaseFolding#expand`, a bracket class's at parse time, a named class's never, as in the JDK), keeping the match-time check a single plain, unfolded `contains` — see "Opcode set" below. `checkDisjoint` compares these already-folded sets, so a fold overlap between chain candidates (e.g. `(?i:[a-z]+)X`, `(?i:a|A)`) is a compile-time ambiguity like any other overlap, never resolved by chain priority; the only catch-all candidate is a `.`-style wildcard.
- **Capturing groups**: a capturing, unquantified `QuantifiedUnion` (`captureConstructIndex != -1`) wraps its compiled alternation-dispatch node in a `BeginCaptureMatcherConstruct` (which becomes `owner.matcher`, recording the start position), and compiles its branches against a `CaptureEndMarker` — a zero-width synthetic `PatternConstruct` standing in for the real `next` — whose own matcher is an `EndCaptureMatcherConstruct` (records the substring, then forwards unconditionally to the real `next`). Capture storage (`Matcher#captureGroups`) is a flat array indexed by a fixed `captureConstructIndex` known to both `BeginCapture` and `EndCapture` (not a stack — this engine has no recursion, so the same capture construct can never be open twice at once, and re-entering it naturally overwrites the previous `Group` — exactly regex's "last iteration wins" semantics — for free; this is exactly what the capturing-and-quantified case below relies on).
- **Capturing AND quantified at once** (e.g. `(a)*`): `buildLoopMatcher` takes a `captureConstructIndex` (`-1` when not capturing). The capture must re-fire every iteration, identically whether this is the very first attempt or a later re-check — but the `BeginCaptureMatcherConstruct` recording it must run strictly AFTER a body part's own `entrySet` gate passes, not before: a single shared `BeginCaptureMatcherConstruct` wrapping the whole body chain's head would record a capture start even on a `min == 0` loop's very first, ultimately-zero-iteration attempt, since it would run unconditionally before the body's own gate got a say. So each body part instead gets its own throwaway `LoopBodyPartGateMarker` carrying that part's `entrySet`/`failedEntry`, with a `BeginCaptureMatcherConstruct` wrapped INSIDE it (compiled ungated, since gating already happened by the time it runs) — the gate is checked, then the capture fires, then the part's own real content runs. Ambiguity detection is unaffected — it runs identically whether or not the loop is capturing, since capturing only changes what happens once a branch is chosen, not which branch gets chosen.
- `MatcherConstruct` subclasses (in `MatcherConstruct.java`) are the compiled, executable nodes — see "Opcode set" below for the full set. Every node carries an optional `entrySet`/`failedEntry` pair, checked before its own `matchBody(Matcher, int peeked)` runs: on a miss, dispatch defers to `failedEntry` instead (or fails outright if there isn't one); on a pass (or no `entrySet` at all — the common case), `matchBody` runs and consumes zero or more code points before advancing to its successor(s).
- Matching is therefore just: start at the compiled root node, and recursively call `match()`. No backtracking stack is needed because ambiguity was already ruled out at compile time.

#### The `compile()` algorithm and cycle handling

`MatcherConstruct` instances are deeply immutable once built — every field on every `MatcherConstruct` is genuinely `final` (see "Opcode set" below for why that's still possible even with a genuine construction-time cycle, in particular for `LoopMatcherConstruct`). But the matcher graph *does* have cycles (a loop's body eventually dispatches back to the loop's own entry `MatcherConstruct`), so something has to break the cycle during construction without the constructed node ever seeing a half-built dependency:

- Every `PatternConstruct` has a `@MonotonicNonNull MatcherConstruct matcher` field. `PatternConstruct.compile()`'s contract: if `matcher` is already non-null, return it immediately — don't rebuild. Otherwise, build `entryMap` and then construct the one `MatcherConstruct` this node compiles to.
- The key trick is in the `MatcherConstruct` subclass constructors, not in `compile()`: a `MatcherConstruct` constructor must, as its *very first* action, assign `this` to its owning `PatternConstruct`'s `matcher` field — *before* it does anything else, including looking up or compiling any of its own dependencies (e.g. what a loop dispatches back to, or what a union's branches dispatch to). Only after that assignment does the constructor walk the `PatternConstruct` graph (via each dependency's own `compile()`) to resolve the `MatcherConstruct`s it needs for its `dispatchMap`/`exitMap`, and accumulate those into its own dispatch map.
- This ordering is what makes cycles safe without any visited-set/recursion-guard bookkeeping: if compiling node A transitively needs to compile node B which loops back and needs A again, that second `compile()` call on A sees `matcher` already set (to the in-progress `A` instance) and returns it immediately, rather than recursing infinitely. The returned reference is to a real, fully-constructed-by-the-time-anyone-uses-it object — it's *only* used as a dispatch-map value (a reference to jump to), never dereferenced by the constructor that's still running, so returning a self-reference mid-construction is safe even though the object's own fields (its dispatch map) aren't filled in yet at the moment it's handed out.
- Compiling tail-to-front (i.e. `compile()` is always called with "what comes next" already known/passed in, starting from `EndConstruct` and working backwards through the pattern) makes cycles rare in practice, even though the mechanism above handles them regardless.
- The constructor navigates via a reference to its owning `PatternConstruct`, not via extra constructor arguments per dependency: `PatternConstruct` has a `next` field (recorded in `compile()`); for an *acyclic* dependency, everything a `MatcherConstruct` constructor needs is already reachable off `owner` by direct field read (`owner.next.matcher`, or `owner.entryMap`'s `PatternConstruct` values' own `.matcher` fields) — no `.compile()` call needed. Loop compilation is the one case that genuinely needs the self-registration-then-*recurse* pattern (not just self-registration-then-read): `QuantifiableConstruct.buildLoopMatcher` builds a `LoopBackMarker` and self-registers a `LoopMatcherConstruct` onto it *first*, then calls `part.compile(marker)` for each body part — safe, since a nested attempt by the body to read `marker.matcher` again finds the (still-being-built) `LoopMatcherConstruct` instance already there instead of recursing. The marker's own entry point (queried by a nullable construct nested in the body that needs to look past itself at "what comes next" — see below) delegates straight through to `owner`'s, since semantically "what follows a loop body" is the loop itself.

##### Entry-point computation vs. matcher compilation

A `PatternConstruct`'s `entryMap`/`entryElse` (its own advertised "what character(s) can follow me") and its `matcher` (the compiled `MatcherConstruct` graph) are two separate, independently-lazy computations, each memoized and cycle-guarded on its own:

- `getEntryPointMap()`/`getEntryElse()` are the only way anything reads another construct's entry set (never the raw `entryMap`/`entryElse` fields directly). The first call lazily invokes `buildEntryMap(next)`, guarded by a three-state flag (not started / constructing / constructed) on the construct itself: a re-entrant call made *while that same construct's own `buildEntryMap` is still running* throws (see below) instead of silently reading a half-built map or recursing forever. A call arriving after that construct has already finished (a completely ordinary case, not a re-entrant one) just returns the cached result.
- Critically, this guard is scoped to *entry-point construction specifically* -- not to matcher compilation, and not to "is this construct anywhere on the current call stack for any reason." A construct's `matcher` can be (and, for a loop's entry/re-entry node, always is) self-registered and sitting mid-construction while something else asks for that same construct's entry point for the first time; that's not re-entrance, it's simply the first, on-demand request, and it's resolved immediately by delegating structurally to whatever sub-part actually determines it.
- Because of that, `buildEntryMap` for `Sequence` and for a quantified construct (`QuantifiableConstruct.buildLoopEntryMap`) must never trigger anything's full `compile()`/`buildMatcher()` -- only entry-point getters, plus a cheap, direct assignment of each relevant sub-part's `next` field (bypassing `compile()` entirely) so a nullable sub-part can still fold in what follows it. `Sequence`'s own entry set is always exactly its *first* element's (entering the sequence means entering its first element); the tail-to-front `compile()` calls that actually wire up the matcher graph happen separately, in `buildMatcher()`. A quantified construct's own entry set is `FIRST(body)` (the union of its body parts' entry points, each body part's `next` pointed at `loopBodyTarget()` -- a `LoopBackMarker`, wrapped in a `CaptureEndMarker` when the loop itself captures -- rather than the construct itself; see the identity-sharing rule below for why) unioned with `next`'s own entry set when `min == 0` (skipping the construct entirely is valid) -- computed once, in `buildEntryMap`, well before `buildMatcher()` builds the real dispatch graph (which still needs the full body-plus-`next` candidate merge, since "continue vs. exit" routing is a different, larger question than "what's my own advertised entry set").
- This split is what makes a loop nested inside another loop's body resolve correctly: the nested loop's own dispatch construction needs the *outer* loop's entry set (since exiting the nested loop routes to the outer loop), and asking for it via `getEntryPointMap()` triggers the outer loop's cheap, structural `FIRST(body)` computation on the spot if nobody's asked yet -- which typically bottoms out immediately (e.g. in `(a(b)?)+`, the literal `a` pins the outer loop's entry set without ever needing to touch the inner `(b)?` loop at all). The one case that's a genuine, unbreakable cycle is a loop whose entire body can match zero characters (e.g. `(a?)+`): computing the loop's own entry set then requires its own not-yet-available entry set, and the guard converts that into a `PatternSyntaxException` naming the loop's start index, rather than a stack overflow or a silently wrong dispatch -- consistent with this engine's "unsatisfiable/indeterminate at compile time is an error, not a silent failure" philosophy elsewhere (see "Boundary matching" above). Note this is also just an infinite-loop hazard in its own right (a loop that can advance zero characters per iteration), so rejecting it at compile time isn't purely an artifact of the implementation technique.
- **Identity-sharing rule**: whenever a downstream construct bakes a `next` reference into a *fixed field* rather than re-reading it later -- the one example today is `CaptureEndMarker.realNext`, set once from `buildEntryMap`'s `next` argument and never revisited (`compile()` memoizes on `matcher != null`, so a later `buildEntryMap` re-run never happens even if a fresh `next` value is passed to a subsequent `compile()` call) -- then whatever object is used as `next` during entry-point computation MUST be the exact same object later reused as `next` during matcher compilation, not merely one that resolves to an equal *value*. `buildLoopMatcher` used to violate this by pointing a capturing loop's body parts at `this` (the loop construct) during `buildEntryMap`, then at a freshly-`new`-built `LoopBackMarker`/`CaptureEndMarker` pair during `buildMatcher` -- a nested capturing body part's own `CaptureEndMarker` (built once, during entry-point computation, from whichever object was `next` *then*) ended up permanently pointed at `this`, whose `.matcher` isn't set until the whole loop finishes compiling, throwing a `NullPointerException` the first time that marker's `buildMatcher()` ran (`((x))*`, `(?:(x))*`; see notes.md's 2026-09-21 entry). The fix -- `QuantifiableConstruct.loopBodyTarget()` -- is the general pattern: memoize the marker(s) as a field, computed once and reused identically by both `buildLoopEntryMap` and `buildLoopMatcher`, rather than constructing a fresh one in each. Any future change to what a loop (or similar identity-baking construct) points its parts' `next` at should re-check this specifically, not just "does the entry set still compute the right *characters*."

##### `entryMap` aliasing (avoiding a copy per AST level)

`entryMap` is `CodePointSet`, not `MutableCodePointSet` -- most `buildEntryMap()` overrides never build a new map at all, they just **alias** another construct's already-built one:

- A construct whose own entry point is defined to be exactly some other construct's -- `Sequence` (its first element's), `CaptureEndMarker` (`realNext`'s), a bare-flags-only `QuantifiedUnion` (`next`'s), `BackReference` (the referenced group's `firstCharSet()`), `ComplexCharacter`/`ComplexQuantifiedCharacter` (their own/their delegate's `validRanges()`) -- just assigns `entryMap = source.getEntryPointMap()` (or the equivalent already-in-hand map), a plain reference copy.
- This is safe specifically *because* `entryMap`'s value is always Boolean `true`, carrying zero information (see the field's own doc): two different constructs' entry-point maps holding the exact same object is indistinguishable, from every consumer's perspective, from holding two separately-built maps with identical content. Nothing mutates `entryMap` after `buildEntryMap()` returns (every other reader goes through `getEntryPointMap()`/`getEntryElse()`), so a shared reference can't be corrupted by one holder's later writes.
- The one place a genuinely `PatternConstruct`-valued map must NOT leak out as `entryMap`: `mergeEntryPoints`'s own internal merge (built purely to run the ambiguity check with a useful "candidate #N" error message) is real, multi-valued, and would corrupt downstream identity checks like a loop's continue-vs-exit classification (`e.getValue() == next`) if exposed directly -- doing so once caused a real bug (see notes.md's 2026-09-06 `CaptureEndMarker` entry). `mergeEntryPoints` itself now projects that transient merge down to a genuinely new Boolean-valued map exactly once (`MergedEntries.ranges`), before it's ever handed back to any caller -- so every caller (`QuantifiedUnion.buildEntryMap`, `QuantifiableConstruct.buildLoopEntryMap`) can just alias `result.ranges` straight into `entryMap`, with no per-caller re-projection and no risk of ever aliasing the raw, PatternConstruct-valued merge by mistake.
- `LiteralString` is the only true leaf (nothing to alias) -- if its `entryMap` is ever actually pulled (see `getEntryPointMap()`), building it is unavoidably a freshly-built single-entry map. Whether that pull ever happens for a given `LiteralString` depends on `needsEntryPointBeforeMatcher()` below.

##### `mergeEntryPoints`: merging by pulling, not tagging

Merging several candidates' entry points (a union's branches, a loop's body parts plus its own `next`) unions each candidate's own `getEntryPointMap()` straight into a fresh `ArrayCodePointSet` via `addAll` -- one plain call per candidate, no per-candidate identity tagging. This forces every candidate's `entryMap` to materialize (each pull goes through the ordinary cached, cycle-guarded `getEntryPointMap()`, so a quantified construct's own body pointing `next` back at itself for a nullable loop, e.g. `(a?)+`, is still caught by that pull path's three-state guard and converted into a `PatternSyntaxException` rather than infinite recursion). `mergeEntryPoints` doesn't check disjointness itself -- that's matcher-build time's job (`checkDisjoint`, run from `buildForkChainInternal` against real `MatcherConstruct`s, and directly from `validateDisjointness` for the loop-body-vs-`next` runtime-dispatch case), since it's a plain `CodePointSet#intersection` scan against real matchers, not something merging entry points needs to compute itself. `claimsEntryElse()` exists as a separate method from `getEntryElse() != null` purely to give `mergeEntryPoints` a clean loop body over `candidates.size() > 1`.

##### `needsEntryPointBeforeMatcher()`: not pulling what nothing needs

`compile()` itself calls `ensureEntryPointBuilt()` unconditionally before `buildMatcher()` for every construct -- required in general, since e.g. `QuantifiedUnion.buildMatcher`'s unquantified-with-branches case reads `compileTarget`/`rawEntryElse`, fields only `buildEntryMap()` populates. But for a construct whose `buildMatcher()` reads nothing `buildEntryMap()` sets, that call is pure waste whenever nothing else ever pulls this construct's entry point either -- exactly the case of a leaf/alias reached only as a merge candidate. `needsEntryPointBeforeMatcher()` (default `true`) lets such a construct opt out, so `compile()` skips `ensureEntryPointBuilt()` entirely: `LiteralString`, `ComplexCharacter` (true leaves, whose matchers are built entirely from their own constructor-supplied data), `CaptureEndMarker` (`buildMatcher()` reads only `realNext.matcher`), and `Sequence` (`buildMatcher()` does its own independent tail-to-front `next` wiring via each part's own `compile()` call, never touching `entryMap`/`entryElse`).

This matters in practice because every union/loop branch that's a bare literal or character class is actually parsed as a one-element `Sequence` wrapping it, not the leaf directly -- so `Sequence` needed the same opt-out as its leaf children for the win to reach real patterns; skipping it only on `LiteralString` itself was measured to change nothing; skipping it (also) on `Sequence` dropped `CorpusBenchmark.llkCompile`'s `gc.alloc.rate.norm` by 28% (4,958,552 → 3,566,024 B/op) and its time by 18% (1.872 → 1.534 ms/op). A construct left un-pulled after `compile()` isn't stuck: its `entryPointState` simply stays `ENTRY_POINT_NOT_STARTED`, and a later, genuine pull (an ancestor's `getEntryPointMap()`) computes it fresh at that point -- `compile()` already unconditionally sets `this.next` before checking this flag, so nothing that `buildEntryMap()` would need is missing when that eventually happens.

The quantified-loop case (`QuantifiedUnion`/`ComplexQuantifiedCharacter` with `min`/`max` making it a real loop) and the unquantified-with-branches union case both still need the pull, since both `buildMatcher()`s read fields only `buildEntryMap()` populates: the former's `buildLoopMatcher` reads `rawEntryElse` directly (to build `owner`'s own entry fork chain, once every body candidate is compiled), and the latter reads `compileTarget`/`rawEntryElse`.

##### Opcode set

The matcher graph is a small "opcode" virtual machine. Every `MatcherConstruct` carries an optional `final @Nullable CodePointSet entrySet`/`final @Nullable MatcherConstruct failedEntry` pair (both usually `null`), checked by a single, non-overridable `match(Matcher, int peeked)` template method BEFORE a node's own `matchBody(Matcher, int peeked)` runs: a plain (unfolded), `-1`-guarded `entrySet.contains(peeked)` check, deferring to `failedEntry.match(...)` on a miss (or failing outright if `failedEntry` is `null`). `entrySet`/`failedEntry` are populated via the OWNING `PatternConstruct`'s own `dispatchEntrySet`/`dispatchFailedEntry` fields (read by `MatcherConstruct`'s owner-based constructor), set by a chain builder just before that construct's first `compile()` call — this is what lets ANY existing node type become a chain candidate with no constructor changes of its own, and is the mechanism that replaced a separate `ForkingMatcherConstruct` node wrapping each candidate (see "Alternatives Considered"):

- **`SingleDispatchingMatcherConstruct`** (abstract, holds `final MatcherConstruct next`, called via a plain virtual `next.match(...)`): the base for every node whose successor is fixed at construction time and never depends on which character was seen. Subclasses: `SingleCharMatcherConstruct` (character-class membership test via its own `validRanges`, folded at match time — distinct from any `entrySet` gating that might additionally wrap it as a chain candidate), `LiteralMatcherConstruct`, `BeginCaptureMatcherConstruct`, `EndCaptureMatcherConstruct`, `WordBoundaryMatcherConstruct`, `BackReferenceMatcherConstruct`/`BoundaryMatcherConstruct`, and `PassThroughMatcherConstruct` (a zero-width forwarder — see below). `next` is safe to be `final` here because none of these nodes are ever the self-referential node in a cycle — that role belongs exclusively to a loop's own `LoopMatcherConstruct` (below).
- **Chain building** (`PatternConstruct.buildFlattenedChain`, for a plain union's own dispatch; `QuantifiableConstruct.buildLoopMatcher`'s own body-part loop, for a loop's) compiles candidates tail-to-front, giving each one's OWN compiled node the next candidate's already-resolved matcher as its `dispatchFailedEntry` before compiling it — so a candidate's own node IS the fork, with no extra object allocated per candidate. A plain union's last candidate, when there's no catch-all branch, is left entirely ungated (no `entrySet` at all): its own compiled matcher already re-verifies membership as its own first action, so a redundant gate would only test something whose answer is already implied. A loop body part can never be left ungated this way, since it always has somewhere real to defer to (the loop's own exit node, below) — "doesn't match" is never simply "the whole match fails" the way it can be for a catch-all-less union's last branch.
- **`PassThroughMatcherConstruct`** (a `SingleDispatchingMatcherConstruct` with a no-op `matchBody`): needed anywhere a construct's own `buildMatcher()` would otherwise just alias `matcher = someOtherConstruct.matcher` (e.g. `Sequence`, a bare flags-only `QuantifiedUnion`) AND that construct is itself gated as some OUTER chain's own candidate — `someOtherConstruct` may already be fully compiled (or gated for an unrelated, INNER reason), so the outer gating can't be retrofitted onto it after the fact and needs a node of its own instead. `MatcherConstruct.aliasOrPassThrough(owner, target)` picks the plain alias when `owner` has no gating of its own (the common case, no extra node) or wraps `target` in one of these when it does.
- **`LoopMatcherConstruct`** is reached only as a loop body's own continuation, once a body pass finishes (never as the loop's own entry point — see "Quantifier/loop compilation" above for why the body chain's own head serves that role too). It does no code-point membership test at all: `match()`'s `entrySet` is always `null` (it's reached only via `LoopBackMarker`'s own, ungated, dispatch fields), and its `matchBody` just counts one more completed iteration, then dispatches back to the body chain's head if under `max`, or to the loop's `LoopMatcherExit` otherwise. Kept as its own top-level class rather than participating in the ordinary chain mechanism, because its "continue" successor — the body chain's own head — genuinely isn't known until *after* it self-registers to break the construction-time cycle every loop body creates; rather than a mutable (or otherwise indirected) field on the node itself, it holds a `final PatternConstruct continuation` and reads `continuation.matcher` at match time — reusing `PatternConstruct.matcher`'s own already-mutable-once nature (the SAME mechanism the rest of this section's cycle-breaking discussion relies on) instead of inventing an equivalent one scoped to this class.
- **`LoopMatcherExit`** is a loop's "stop iterating" node — enforces `min`, resets the shared iteration counter on success, and dispatches to `next`'s own matcher. Never itself gated (`entrySet` always `null`); reached via `LoopMatcherConstruct` (forced, at `max`) or via the body chain's own `failedEntry` fallthrough (a genuine non-match, at any iteration count).
- **`BeginCaptureMatcherConstruct`/`EndCaptureMatcherConstruct`** are pure single-successor opcodes, unrelated to looping, with the flat `captureGroups` array + fixed `captureConstructIndex` design described above (not a stack). The capturing-and-quantified case composes existing opcodes rather than giving `BeginCapture` a second, branching role — see "Alternatives Considered": each capturing loop body part gets its own `LoopBodyPartGateMarker` (carrying that part's `entrySet`/`failedEntry`) wrapping a `BeginCaptureMatcherConstruct` (single successor) → that part's own (ungated) compiled matcher → ... → `EndCaptureMatcherConstruct` → loops back to the `LoopBackMarker`.
- **`EndMatcherConstruct`** has no successor at all, so it extends neither base directly.

`SingleDispatchingMatcherConstruct.next.match(...)` is called as a plain virtual call — see "Alternatives Considered" for why a bound-`MethodHandle` form was tried and rejected.

#### Boundary matching (`BoundaryConstruct`/`WordBoundaryConstruct`/`LineBoundaryConstruct`)

Unlike every other construct (essentially "a dispatch map keyed by the next code point"), a boundary depends on matcher *state* — position, surrounding characters — not just the upcoming code point. Two boundary types have grown a real implementation with their own logic distinct enough that each got pulled out of the original single `BoundaryConstruct`/`BoundaryEnum`-keyed dispatch into its own `PatternConstruct`/`MatcherConstruct` pair: `\b`/`\B` (`WordBoundaryConstruct`/`WordBoundaryMatcherConstruct`) and `^`/`$` (`LineBoundaryConstruct`/`LineBoundaryMatcherConstruct`). `BoundaryConstruct`/`BoundaryMatcherConstruct` now only cover `\A`, `\z`, and `\Z`.

All three boundary constructs report their own entry point as `entryElse = this`, no explicit ranges -- a catch-all claim that "I might succeed here regardless of the next code point." That's the right treatment for ordinary union/sequence dispatch (a plain union never commits any input before a zero-width assertion's own runtime check can veto it, so treating it as a low-priority catch-all fallback is safe -- the same reasoning `.`'s own explicit-but-total range relies on) but it's UNSAFE for a loop's own "continue vs. exit" ambiguity check specifically: a loop has already irreversibly consumed a code point once it decides to continue, so if a zero-width assertion sits between the loop and a later real character (e.g. `a*^a`), the coarse catch-all entry set hides the real question -- "does exiting the loop, through this assertion, eventually require the SAME code point the loop's own body would also accept?" `QuantifiableConstruct.buildLoopMatcher`'s ambiguity check therefore uses `PatternConstruct.skipZeroWidthEntrySet` instead of the assertion's raw entry point when computing its own `next`-side comparison: a recursive walker (same shape as `firstCharSet`/`lastCharSet` below) that sees straight through a chain of zero-width assertions -- and through a `Sequence`'s first element or an unquantified `QuantifiedUnion`'s own branches, so a boundary buried inside a nested group or alternation is still seen through -- to whatever construct actually determines which code points can follow. This is deliberately scoped to the loop-ambiguity call site only; ordinary union dispatch keeps the coarse catch-all treatment, which is still correct there.

`\G` is a different case entirely: per the project owner, it doesn't actually match any specific position in the input at all -- it's really just a flag meaning "anchor `find()` to exactly where the previous match ended, don't scan forward for a later one," and `Matcher#matchEnd` already tracks that position (for `group(0)`/`end()`). So `\G` gets no `PatternConstruct`/`MatcherConstruct` representation whatsoever: `PatternParser` recognizes it directly (not through the generic boundary-parsing path) and sets a `boolean anchorsToPreviousMatchEnd` flag, carried onto `Ll1Pattern`, consulted only by `Matcher#find(int)` -- when set, `find(int start)` tries `attemptMatch(start, false)` exactly once instead of scanning `[start, regionEnd]`. `matches()`/`lookingAt()` are unaffected, since they never scan for a later start position in the first place, so `\G` has nothing to change there. `\G` is only accepted as the very first thing in the whole pattern (a raw index-0 check on the pattern string, before any other parsing) -- anywhere else it's rejected at compile time with a `PatternSyntaxException`, rather than silently doing nothing there the way `java.util.regex` does.

`\b`/`\B` (word boundary / non-word-boundary) are implemented via `Matcher#peekPrevious()` (mirrors `peek()`, looking one code point backward instead of forward, bounded at `lookFloor` rather than `0` -- see `useTransparentBounds()` below) and a dedicated `WordBoundaryMatcherConstruct`. It's a plain `SingleDispatchingMatcherConstruct` — it doesn't consume input, so it still has exactly one successor, just like every other single-dispatch node; branching on matcher state didn't require a new node *shape*, only a new field (`peekPrevious()`) to read.

On top of that, `WordBoundaryConstruct.buildMatcher()` applies a compile-time optimization: `\b`/`\B` very often sit next to a literal/character-class with a statically known "is this a word character" answer, so only one side needs checking at match time in that case. It classifies both the character just consumed and the one about to be consumed as always-word/always-non-word/unknown:
- **Peek side** (the character about to be consumed): read directly off the already-built `entryMap`/`entryElse` of `next` — no new analysis needed. If `next.entryElse != null`, or its `entryMap` ranges are a mix of word and non-word code points, the side is unknown.
- **Prior side** (the character just consumed): a `PatternConstruct.lastCharSet()` recursion, walking `LiteralString`/`ComplexCharacter`/`ComplexQuantifiedCharacter`/unquantified `QuantifiedUnion`/`Sequence`. Returns `null` (a safe "not statically known" fallback) for anything that could match zero-width, or for any construct type it doesn't recognize. `Sequence.buildEntryMap` sets this (via `lastCharSet()` on the preceding sibling) before compiling a `WordBoundaryConstruct` that isn't the first element of its `Sequence`; it's left `null` (safe, just unoptimized) otherwise.

If both sides are statically known, the boundary either always holds (compiles to a zero-width no-op, `matcher = next.matcher`) or never can (a compile-time `PatternSyntaxException` — e.g. `a\bb` is rejected, since two word characters can never have a word boundary between them; this is consistent with this project's general "unsatisfiable at compile time is an error, not a silent always-fail" philosophy, unlike `java.util.regex`, which would compile `a\bb` and just never match it). Otherwise, `WordBoundaryMatcherConstruct` only checks whichever side isn't statically known, via a small pair of enums (`PriorWordBoundaryMatchType`/`PeekWordBoundaryMatchType`) whose combinations are constructed by `WordBoundaryConstruct.buildMatcher()` so the nonsensical ones are unconstructible, and only calls the (slightly more expensive, backward-looking) `peekPrevious()` when the preceding side is the one left unresolved.

`BoundaryConstruct`'s `BoundaryEnum` values (`\A`, `\z`, `\Z` -- `\G` no longer among them, see above) are all implemented:

- **`InputBegin`/`InputEnd`** (`\A`/`\z`): always the true start/end of input (`pos == regionStart`/`pos == regionEnd`) -- `MULTILINE` has no effect on either.
- **`InputEndExceptTerminator`** (`\Z`): the end of input, or immediately before the input's own *final* line terminator, if it has one -- checked by scanning forward from `pos` for a line terminator that reaches exactly to `regionEnd` (not merely one somewhere in the remaining input), via the package-private `MatcherConstruct.matchesEndExceptTerminator` helper (shared with `LineBoundaryMatcherConstruct`, below). This is a zero-width assertion that does not consume the terminator, so `matches()` (which requires the whole region, terminator included) still fails whenever one is present; only `find()`/`lookingAt()` (a prefix match) see the exemption -- verified directly against `java.util.regex` while implementing this, since it's easy to misremember `matches()` as tolerating it too.

`LineBoundaryConstruct`/`LineBoundaryMatcherConstruct` (`^`/`$`, a `boolean isLineBegin` distinguishing them instead of a shared enum): without `MULTILINE`, exactly `InputBegin`/`InputEndExceptTerminator` (`^` reuses the plain `pos == regionStart` check; `$` reuses `matchesEndExceptTerminator`). Under `MULTILINE`, `^` also matches immediately after any line terminator (a backward scan, `MatcherConstruct.lineTerminatorLengthBefore` -- the mirror image of the forward `lineTerminatorLengthAt` scan `\Z`/multiline-`$` use, treating a `"\r\n"` pair as ending at one position, not creating a second match point between the `\r` and the `\n`), and `$` also matches immediately before any line terminator. Line-terminator recognition (`\n`, `\r`, `"\r\n"` as one unit, `\u0085`, `\u2028`, `\u2029` by default; only `\n` under `UNIX_LINES`) is implemented once, symmetrically, as two `MatcherConstruct`-level static helpers shared by both `BoundaryMatcherConstruct` and `LineBoundaryMatcherConstruct` rather than duplicated.

`Matcher.useAnchoringBounds(false)` makes `^ $ \A \z \Z` see the true edges of the input instead of the region's: `Matcher` keeps `anchorStart`/`anchorEnd` (`regionStart`/`regionEnd` when anchoring, else `0`/`input.length()`), recomputed by `syncAnchors()` from `region`/`reset`/`useAnchoringBounds`, and only the boundary constructs read them (the character-consuming code still stops at `regionEnd`, so `lineTerminatorLengthAt` reads `input` directly when `pos == regionEnd < anchorEnd`). The setting survives `reset()`/`usePattern()`, like `java.util.regex`. A MULTILINE `^` never matches at `anchorEnd` and counts as hitting the end, as in the JDK. `AnchoringBoundsTest` diffs match results and both hit-end flags against `java.util.regex` over every region of many inputs.

`Matcher.useTransparentBounds(true)` lets `\b`/`\B` see outside the region: `Matcher` keeps `lookFloor`/`lookCeil` (region edges, or `0`/`input.length()` when transparent), `peekPrevious()` stops at `lookFloor`, and `peekForBoundary()` reads past `regionEnd`. When `pos == regionEnd` with a real character beyond, `WordBoundaryMatcherConstruct` tests the real boundary itself, because its compile-time classification of the following character assumes that character is the one about to be consumed. Known divergence: a `\b`/`\B` whose both neighbours are statically known is elided at compile time, so under transparent bounds at `regionEnd` `hitEnd` can differ from `java.util.regex` (never the match result); `TransparentBoundsTest` skips the `hitEnd` comparison for those patterns.

### `hitEnd` / `requireEnd`

`Matcher.hitEnd`/`requireEnd` are plain booleans, cleared at the start of each `matches()`/`lookingAt()`/`find(int)` and sticky across every start position one `find()` tries (same as `java.util.regex`). They are only ever written from cold paths, so the match hot path is unchanged: a gated dispatch miss whose input is the end-of-input sentinel (`MatcherConstruct.match`), a `SingleChar` miss on the sentinel, a literal that runs off the region end while the remaining input still agrees with its prefix (a mismatch before the end is not a hit-end), a backreference whose group is longer than the remaining input, `$`/end-of-input boundaries that matched at the end, `\b`/`\B` reached at the end, and a failed `find()`. Java's `requireEnd` is set by `$` and the end-except-terminator boundary (both flags) but the plain end-of-input boundary sets only `hitEnd`. A failed `find()` is always a hit-end except when the whole pattern is a single alternative starting with the begin-of-input anchor or a non-`MULTILINE` line-begin anchor (`Ll1Pattern.startsWithBeginAnchor`): `java.util.regex` tries only the search start for those, so nothing scans to the end. There is no backtracking here, so flags set in a branch Java would have abandoned and re-tried are not reproduced; `HitEndRequireEndTest` diffs both flags against `java.util.regex` across patterns, inputs and flag sets to guard this.

### Code point range representation

- `CodePointSet` (interface, no type parameter) is the single representation for a range of Unicode code points
  throughout this codebase -- pure membership ("is this code point in the set", nothing more), not a
  code-point-to-value map: this engine's entry-point/dispatch machinery and every `NamedCharClass`/generated
  `UnicodePredicates` constant only ever needed a boolean answer, so there's no generic value-carrying map
  underneath it, and no Guava `RangeMap`/`RangeSet` remains anywhere in `llkpattern/src/main` (an earlier design
  had one, `CodePointMap<V>`, generic over an arbitrary value type fixed to `Boolean` almost everywhere it was
  used -- see notes.md's 2026-09-12/2026-09-14 entries for that migration and its later full removal). Dropping
  the value entirely, rather than keeping a generic map with `V` fixed to `Boolean`, removes a whole parallel
  values array and the null-valued "punched hole" trick a generic map's `complement` would otherwise need: since
  a set's only two states at any code point are "in" and "out", a negated set is just this same set with the two
  states swapped (`invert()`), not a rebuild.
- `[min, max)` range convention throughout, immutable `Range`, `contains`/`containsAll`/`add`/`remove`,
  `union`/`difference`/`intersection`/`complement`, `invert`. Ambiguity detection's own "these two branches both
  claim this character" conflict check is a plain pairwise `CodePointSet#intersects` scan (`PatternConstruct.checkDisjoint`,
  see "Compilation" above), not a property of `CodePointSet` itself.
- `forEachRange(RangeConsumer)` visits every range as a plain `(int min, int max)` callback -- no `Range`/`Entry`/
  `Iterator` allocated per range for `ArrayCodePointSet`'s common case. `rangeSet()` is a `CodePointSet`-interface
  default built *from* `forEachRange` (eagerly, into a `LinkedHashSet`) rather than the other way around --
  `ArrayCodePointSet` overrides `forEachRange`/`first` directly instead of `rangeSet()`. Preferred over `rangeSet()`
  on any hot path that just wants to visit ranges and has no actual use for a `Range` object -- `PatternParser`'s
  `intersect` (`&&`) helper and most of `PatternConstruct`/`MatcherConstruct`'s own compile-time range-merging
  loops all use it.
- `first(RangePredicate)` is `forEachRange`'s short-circuiting counterpart: same zero-allocation range visitation,
  but stops at (and returns `true` from) the first range the predicate accepts, instead of always visiting every
  range. Worth it specifically for a query that can stop early -- `WordBoundaryConstruct`'s `isSubsetOf`/
  `isDisjointFrom` (bail out on the first violation) are the only two current callers; `forEachRange` would have
  kept scanning the rest of a large character class after the answer was already known.
- `PatternConstruct.ComplexCharacter.ranges` (and everything downstream of it -- `SingleCharMatcherConstruct.validRanges`, `firstCharSet`/`lastCharSet`/`WordBoundaryConstruct.priorCharSet`/`wordSet`) is a `CodePointSet`, not a Guava `RangeSet<Integer>`, and is `final`/effectively immutable: every constructor sets it exactly once, from a set `PatternParser` finished building beforehand (`PatternParser#parseComplexCharacterRanges` builds into its own local accumulator throughout a bracket expression's parse, only handing the finished set to a `ComplexCharacter` at the end), so a caller with a source set it's sure won't be mutated again (a `NamedCharClass`/`RegexCharacterClass` constant, `parseComplexEscape`'s return value) can assign it in directly with no defensive copy. Within a single bracket-expression run, `PatternParser#parseComplexCharacterRanges` unions in large contributions (an escape's or nested class's `CodePointSet`) by reference via `UnionCodePointSet` while the run is still being parsed, rather than copying each one into the run's `CodePointSetBuilder` immediately -- but always collapses back to a concrete `ArrayCodePointSet` (`mergeRun`) before the run's result can reach `ComplexCharacter.ranges` or any compiled matcher, since `UnionCodePointSet`'s membership/range operations are real virtual dispatch (or a full materialize), not `ArrayCodePointSet`'s single binary search, and this field sits on the match-time hot path. `[^...]`/DOTALL negation goes through `CodePointSet#complement` directly (an `invert` flag flip plus a cheap array copy -- see `CodePointSet`'s own doc); `&&` intersection is a real intersection (`b.intersection(min, max)` per `a`-entry, inversion-aware on either side) rather than the old `a.removeAll(b.complement())` formula, which would otherwise force materializing a complement just to subtract it. `SingleCharMatcherConstruct` guards the `-1` end-of-input sentinel explicitly before consulting the set -- a negated class legitimately matches everything it doesn't exclude, so `-1` is simply never a real code point, checked first, unconditionally, rather than relying on the set's own membership query to keep it out.
- `NamedCharClass`/`UnicodePredicates` (and the `RegexCharacterClass` enum nested in the former) are `CodePointSet` throughout now too -- no Guava `RangeSet`/`RangeMap` remains anywhere in `llkpattern/src/main`. Every constant's `ascii`/`unicode` field is a `CodePointSet`; hand-written literal sets use a small `build(Consumer<MutableCodePointSet>)` helper (an `ArrayCodePointSet` filled via ordinary `add`, which -- unlike the generated file's `appendSorted` -- tolerates entries added out of order); `unionOf`/`difference` are thin wrappers over `CodePointSet#union`/`#difference`. A constant that's logically a complement (`Assigned`, `Graph`, `\D`, `\H`, `\S`, `\V`, `\W`, `DOT`) is built via `CodePointSet#complement` directly (`DOT` is simply `{'\n'}.complement()`) -- cheap even at class-init time, since `ArrayCodePointSet#complement`'s fast path is a plain array copy plus a flipped `invert` bit, never a domain walk. `PatternParser`/`WordBoundaryConstruct` consume `NamedCharClass`/`RegexCharacterClass` constants directly now (no adapter step) -- `get(prefix, flags)`/`get(flags)` already return a `CodePointSet`, and a standalone escape atom (a bare `\D`/`\p{...}` in running pattern text, not inside `[...]`) aliases the constant straight into a fresh `ComplexCharacter.ranges` with no copy at all, since that field is effectively immutable once constructed (see `PatternConstruct.ComplexCharacter` below).
- `CharacterClass.java` (the old, confirmed-dead `ImmutableRangeSet`-wrapper design that predated `ComplexCharacter`'s own ranges) has been deleted.
- `ArrayCodePointSet` is `CodePointSet`'s one implementation, specialized to the Unicode code point domain: a
  single flat `int[] keys` array (each entry packing `(min << 11) | count`, where `count` is the number of
  *additional* code points after `min` in the same run — 21 bits for `min` plus 11 for `count` fits an `int`
  exactly, no `long` and no parallel "value" array needed, since a set has nothing to store per entry but the run
  itself), kept sorted by `min` for lookup (a binary/linear-search hybrid, see `floorIndex` -- linear below
  `LINEAR_SEARCH_THRESHOLD` entries, since a real binary search costs more than it saves for the small sets this
  library builds most). This avoids a tree structure's per-entry node/object overhead in favor of one flat array
  (starting at capacity 1 and growing by 1.5x), which is both smaller and more cache-friendly during matching.
  `invert()` (backing `complement()`) is a flipped `boolean` bit plus a cheap array copy, not a rebuild -- see
  `ArrayCodePointSet`'s own class doc for the full membership-testing story. The binary search compares each
  key's *extracted* `min` (always a non-negative `int` in `[0, MAX_CODE_POINT]`), never the raw packed key
  itself, specifically to sidestep any sign-bit concern from packing `min` into high bits (a code point at/above
  `0x100000`, plane 16, does land on the sign bit when packed).
- Every mutator (`add`, `remove`, the bulk-append `appendSorted`) is localized to just the region of the array it
  actually touches, found via the same lookup reads use — a single touched entry is a plain field edit or lone
  insert/delete, and multiple touched entries trim the first/last in place and shift out whatever's strictly
  between, all without scanning the rest of the array. Building an n-entry set via n `add`/`appendSorted` calls is
  therefore O(n) amortized, not O(n^2) — an earlier version that rescanned the whole array on every mutation
  regressed a JMH benchmark by 3.4x before this was caught (see notes.md's 2026-09-08 entry, from before this
  class's rename from `ArrayCodePointMap`).
- `rangeSet()`/`forEachRange` always yield ranges in ascending `min` order — a `CodePointSet`-interface-level
  contract (every implementation satisfies it for free, being a set of disjoint ranges over an ordered domain),
  not just an `ArrayCodePointSet` detail. `MutableCodePointSet.addAll`'s optimized override relies on it directly:
  rather than one `add()` call per source entry, it's a single sorted merge sweep over this set's own entries and
  the source's, degenerating automatically to a plain bulk append when the target starts empty. Every compile-time
  site that copies an already-known-sorted source into a fresh, empty destination set — every
  `PatternConstruct.buildEntryMap`/`buildMatcher` and `MatcherConstruct.populate`/loop-dispatch site that walks a
  child's or a merge result's ranges via `forEachRange` — uses `appendSorted` rather than `add`/`addAll` for
  exactly this reason: `add()`'s binary-search-and-splice is wasted work when the destination is empty and the
  entries already arrive in order (a plain filter, i.e. skipping some source entries, doesn't break this — the
  ones kept are still ascending). Only genuinely irregular, out-of-order construction (e.g. `NamedCharClass`'s
  hand-written literals, see below) still needs `add`.
- Adjacent entries are always coalesced together on mutation (there's no "value" to disagree on, unlike an
  earlier generic-map design would have had — see this section's first bullet), except where doing so would
  exceed a single entry's 2048-code-point capacity (the 11-bit count field's range) — a longer logical range
  unavoidably splits across multiple consecutive entries, which is observable through `rangeSet()` even though it
  represents one contiguous run.

### Unicode support

- `NamedCharClass` maps regex-style named classes (`\p{Alpha}`, `\p{IsGreek}`, `\p{general_category=Lu}`, etc.) to underlying `CodePointSet` predicates/ranges.
- `UnicodePredicates` is a ~14k line generated data file of Unicode category/script/block predicates (one `CodePointSet` field per predicate), produced by the `unicodeanalyzer` module's `UnicodeAnalyzer` from the running JDK's own `Character` tables. It carries a "DO NOT EDIT" javadoc and a `javax.annotation.processing.Generated` annotation recording the generation date; regenerate it with `./gradlew :unicodeanalyzer:generateUnicodePredicates` (run manually, as needed -- e.g. after a JDK upgrade changes Unicode data -- not part of the normal build). To pick up a *newer* JDK's Unicode data than whichever JDK Gradle's own daemon happens to be running on, run `UnicodeAnalyzer` against that newer JDK directly instead of through the Gradle task: compile via `./gradlew :unicodeanalyzer:classes` (a JDK Gradle itself can run on, e.g. 17 or 21), then invoke the compiled class directly with the newer JDK's own `java` (its classpath needs the `unicodeanalyzer` module's compiled classes plus the Guava jar under `~/.gradle/caches/modules-2/files-2.1/com.google.guava/`), and copy its output over the checked-in file with CRLF line endings. This sidesteps a real compatibility issue: Gradle's own Groovy buildscript compiler has crashed intermittently when run directly on some newer JDKs (seen on 25). Script predicates are generated one field per `Character.UnicodeScript` value, named exactly `UnicodeScript#name()`; `NamedCharClass#scriptByName` resolves `\p{IsLatin}`/`\p{script=Latin}` (full names or ISO 15924 aliases, case-insensitively) through a generated `UnicodePredicates.scriptByEnumName` string switch (shrinker-safe, unlike reflection) rather than ~160 enum constants. Block predicates are generated the same way, as `BLOCK_`-prefixed fields (prefixed because several block names collide with script names, e.g. `GREEK`) plus a `blockByEnumName` switch keyed by `UnicodeBlock#toString()`, resolved by `NamedCharClass#blockByName` for `\p{InGreek}`/`\p{block=Greek}`. The name scanner in `PatternParser` accepts digits and `-` so names like `Latin-1Supplement`/`Latin_1_Supplement` reach the lookup.

### Backreferences

- Backreferences (`\1`, `\k<name>`) are supported, with disjointness checked at **compile time** using a precise, statically-computed entry set.
- A backreference's possible first characters are exactly the *referenced group's* possible first characters, computed by a new `firstCharSet()` AST helper mirroring the existing `lastCharSet()` used for `\b`/`\B`'s prior-character classification (same recursion shape: literal → first code point, character class → its ranges, sequence → first element, unquantified union → union of branches). Feeding this into the normal `RangeMap` disjointness check makes ordinary backreference usage (e.g. `(\w+)\s+\1`) compile with no special-casing, while genuinely ambiguous uses (e.g. `(a+)\1`, where the loop's continue-branch and the backreference's entry set both include `a`) are correctly rejected as a compile error, exactly like any other ambiguous alternation.
- Possibly-empty referenced groups (e.g. `(a*)\1`, where `\1` can be zero-width) make `firstCharSet()` return unknown, falling back to the catch-all entry set. Fed into the normal disjointness check, this correctly rejects two such backreferences (or a backreference and any other catch-all construct) sharing the same alternation/loop-tail dispatch, since two catch-alls are always ambiguous; a single catch-all backreference alongside sibling branches with specific, disjoint entry sets isn't itself ambiguous (the specific branches simply take priority) and compiles fine, matching zero-width handling's existing "rare and probably not what you want, but not unsound" treatment elsewhere in this engine.
- Forward references (`\1` before its group is defined, e.g. `\1(a)`) are rejected at compile time. So is a
  reference to a group number with no group of that number open yet at all (e.g. `\141`, parsed the same way
  `java.util.regex` parses it -- `\1` greedily extended by further digits only while doing so stays within the
  number of groups opened so far, so `\141` is `\1` followed by literal `"41"`, not octal 0141): `java.util.regex`
  compiles this as a backreference node that structurally can never match any input (`BackRef.match` bails out the
  instant the referenced group index is out of range), the same "unsatisfiable at compile time is an error, not a
  silent always-fail" treatment this project already gives `a\bb` (see "Boundary matching" above) and forward
  references themselves -- so llk rejects it outright too, rather than compiling a node that's dead on arrival.

### Quotation, atomic groups, and negative-only flag groups

- `\Q...\E` is removed by a pre-pass in the `PatternParser` constructor (`removeQuoting`), as `java.util.regex` does: quoted ASCII non-alphanumerics get a backslash, everything else is copied verbatim, and an unterminated `\Q` quotes to the end. The rest of the parser never sees quotation, so it works inside brackets and groups, keeps whitespace/`#` literal under `COMMENTS`, and a following quantifier applies to the last quoted character. The cost is that error positions in a pattern containing quotation refer to the rewritten text.
- `(?>X)` parses as `(?:X)`: with no backtracking, every group already matches atomically.
- Inline flag groups apply as `(flags | enabled) & ~disabled`, so `(?-i)` and `(?-i:X)` are accepted.

### `LITERAL` and `CANON_EQ`

- `LITERAL`: `PatternParser.parse()` short-circuits to a bare `Sequence` holding one `LiteralString` of the whole pattern text (no `\Q...\E` pre-pass, no metacharacters, no inline flags). `CASE_INSENSITIVE`/`UNICODE_CASE` still apply through the literal's own flags. An empty pattern is rejected like any empty sequence. `LITERAL` takes precedence over `CANON_EQ`.
- `CANON_EQ` is a text pre-pass (`CanonicalEquivalence.rewrite`, run right after `removeQuoting`), never a matcher feature, so `Matcher` and the compiled graph are unchanged and offsets stay in input coordinates. The pattern is NFD-normalized; each starter followed by combining marks (non-spacing marks, Hangul vowel/trailing jamo) becomes `(?:...)` over every canonically equivalent spelling: every mark ordering that NFD maps back to the same string, plus every single-code-point composition of a prefix of any such ordering followed by the remaining marks, plus any code point written in the original pattern whose decomposition is exactly the cluster (singletons and composition exclusions such as U+212B and U+0958 never come out of composing). The group wraps the whole cluster so a following quantifier applies to all of it.
- The spellings are left-factored into a trie before being emitted. A flat alternation would have several branches starting with the same base character whenever a cluster has two or more reorderable marks, which is exactly the ambiguity this engine rejects. Spellings of one cluster are never prefixes of each other, so every trie level has disjoint first characters and the result is always LL(1)-valid on its own; ambiguity can still arise with neighbouring constructs (`e|é`, `(?:é|è)`) and is rejected as usual.
- Inside a bracket expression a cluster can't be a member, so the clusters of one class are merged into one trie and emitted as alternatives next to the class of its plain members. A cluster in a negated class, a nested class, or next to a range `-` is a compile error with an explanation. Under `CASE_INSENSITIVE`+`UNICODE_CASE`, an original spelling that folds to an already-present single-code-point spelling is dropped (U+212B and U+00C5 would otherwise be duplicate branches).
- The rewrite runs on raw text before escapes are decoded, so an escaped `\u00e9` is not a cluster. Classes, `.` and `\w` never consume trailing combining marks, and error positions refer to the rewritten text.

### Public API shape

- `Ll1Pattern` and `Matcher` are designed to mirror `java.util.regex.Pattern`/`Matcher`'s public method surface, so callers can largely swap one for the other. See remaining_work.md for the current list of implemented vs. stubbed methods.
- **One compiled graph serves `matches()`, `lookingAt()`, and `find()`** — they don't need separate compilations. The difference between them is entirely about the `EndConstruct`/`EndMatcherConstruct` terminal: `matches()` requires the *whole region* to be consumed to succeed, while `lookingAt()`/`find()` only need a matched *prefix* (the rest of the string is allowed to be leftover). Rather than baking that choice into the compiled graph, it's a single `boolean requireFullMatch` field on `Matcher`, set immediately before each match attempt (`matches()` sets it true; `lookingAt()`/`find()` set it false) and read only by `EndMatcherConstruct.match()` (`return !matcher.requireFullMatch || matcher.pos == matcher.regionEnd;`). This mirrors how `java.util.regex`'s own NFA nodes take an "anchoring" flag rather than compiling two different automata.
- `EndConstruct` (the compile-time sentinel `Ll1Pattern.compile()` passes as the outermost `next`) registers `entryElse = this` in its own `entryMap` — reachable regardless of what character (or lack of one) comes next — rather than only the code point `-1` (Matcher's "no more input" sentinel — see `Matcher#peek()`). The latter would be sufficient for `matches()` (where reaching the terminal only ever happens at true end of input) but wrong for `lookingAt()`/`find()`: an *optional* loop's "exit" path (e.g. `a*` matched via `lookingAt()` against `"b"`) needs to be reachable at a position with real, valid leftover characters, not just at true end of string. `requireFullMatch` enforces the stricter check only when it's actually wanted.
- `Matcher#quantifiableCounts`/`captureGroups` are sized automatically from the compiled `Ll1Pattern` (`PatternParser` exposes the final quantifiable-construct count, capture-group count, and a name→`captureConstructIndex` map after `parse()` via `getQuantifiableCount()`/`getCaptureGroupCount()`/`getNamedGroups()`).
- `find()`'s unanchored search is a straightforward linear scan (`attemptMatch` at each candidate start position, `lookingAt()`-style, until one succeeds or the region is exhausted) — every candidate start position is just an ordinary `lookingAt()`-style attempt from a different `pos`.

### Case folding in character classes

`CASE_INSENSITIVE` is applied to a class's members at parse time, never at match time, so `SingleCharMatcherConstruct` is a plain membership test. `PatternParser#addLiteral`/`addLiteralRange` (per bracket member) and `#singleCharacter` (a lone literal that had to become a class) expand each literal member through `CaseFolding`, mirroring `java.util.regex`: a lone character matches its whole case-equivalence class (`lower(upper(x))` key, so `(?iu)[s]` matches `ſ`), a `lo-hi` range matches any `x` with `x`, `upper(x)` or that key inside it. Without `UNICODE_CASE` only ASCII letters fold; `UNICODE_CHARACTER_CLASS` implies `UNICODE_CASE`. Folding is per literal member because the JDK never folds a named class (`\w`, scripts, blocks) or a nested class: it *substitutes* sets instead (`NamedCharClass#caseInsensitive`: `Lu`/`Ll`/`Lt` become `LC`, the case properties and POSIX `Upper`/`Lower` become the union of all cased letters or `[A-Za-z]`). A negated class is therefore a plain complement of the already-folded members. `CaseFolding` finds a set's preimage under `upper`/`key` through two sorted tables built once, lazily, from `Character`, so its cost does not grow with the size of the class.

## Alternatives Considered

### Successor dispatch via bound `MethodHandle` (`findSpecial`) instead of a plain virtual call

Considered for `SingleDispatchingMatcherConstruct.next.match(...)`: bind a `MethodHandle` to the successor's exact `match` override at construction time (via `findSpecial`, an `invokespecial`-style direct call — `findVirtual` + `bindTo` was also tried and rejected on the same grounds, since it's still an ordinary virtual dispatch under the hood) and invoke that instead of `next.match(matcher, peeked)`.

- **Pros**: in principle, skips a virtual-dispatch lookup per match step; `findSpecial`'s `invokespecial` semantics are exactly "call this one exact method," which is all a fixed `next` reference ever needs.
- **Cons**: a `MethodHandle` invocation on a non-static receiver isn't reliably inlined by any JVM, and is frequently *slower* than a plain virtual call even on newer Android runtimes — the entire performance premise doesn't hold. Getting a working, Android-API-26-compatible form at all required real complexity: `findSpecial` requires its `specialCaller` argument to be the calling `Lookup`'s own `lookupClass()` (or a subclass) — it emulates `super.foo()` from a specific class, not "call this concrete method on some unrelated object" — which fails for the common case of a `SingleDispatchingMatcherConstruct` whose successor is a sibling-hierarchy `ForkingMatcherConstruct`/`LoopMatcherConstruct`. The only fully-general fix, `MethodHandles.Lookup.privateLookupIn`, is Java 9+/Android API 33+ — below this project's Android floor of API 26 (worth over half of live Android devices vs. under half on API 33) — so avoiding it meant every concrete leaf class supplying its own one-line `findSpecial` call (exploiting `MethodHandles.lookup()`'s caller-sensitivity), real per-class boilerplate for no realized benefit.
- **Decision**: rejected. `SingleDispatchingMatcherConstruct.matchNext` uses a plain `next.match(matcher, peeked)`.

### `BeginCaptureMatcherConstruct` with a built-in branching role, for capturing-and-quantified loops

Considered for compiling a capturing, quantified construct (e.g. `(a)*`): give `BeginCaptureMatcherConstruct` a second mode where it itself holds a `dispatchMap` and does the per-branch routing among the loop's body parts, rather than being a pure single-successor node.

- **Pros**: one fewer node type actually allocated per capturing-loop iteration (no separate internal fork chain).
- **Cons**: breaks the clean single-vs-branching split — a node meant to be single-successor gains a dispatch role, undermining the invariant that only `ForkingMatcherConstruct`/`LoopMatcherConstruct` ever branch on the next code point, and complicating `BeginCaptureMatcherConstruct` for every non-capturing-loop caller too.
- **Decision**: rejected. The capturing-and-quantified case instead composes existing opcodes: `LoopMatcherConstruct` → `BeginCaptureMatcherConstruct` (plain single successor) → an internal (non-self-registering) `ForkingMatcherConstruct` chain → ... → `EndCaptureMatcherConstruct` → back to the loop's entry node.

### A separate `ForkingMatcherConstruct` node per candidate, instead of `entrySet`/`failedEntry` on every node

The matcher graph's dispatch used to be a chain of dedicated fork nodes (`ForkingMatcherConstruct`: `memberSet`/`next`/`otherwise`) wrapping each candidate's own compiled matcher, rather than folding the fork into every node via an `entrySet`/`failedEntry` pair (see "Opcode set" above).

- **Pros**: a clean separation of concerns — a candidate's own compiled node never needs to know it's part of a chain at all, so no `PatternConstruct.dispatchEntrySet`/`dispatchFailedEntry` threading, no `PassThroughMatcherConstruct`/`LoopBodyPartGateMarker` machinery for constructs that alias another's matcher or need gating checked before a side effect fires. A loop's own entry point could be built as a wholly separate fork chain from its loop-back continuation, without needing the two to be proven equivalent.
- **Cons**: one extra allocated node per candidate beyond the last (an N-branch union or N-part loop body allocates N-1 fork nodes purely for dispatch, on top of the candidates' own nodes), and — for a loop specifically — a *second*, separately-built fork chain for the loop's own entry point, duplicating the routing logic the loop-back continuation already expresses. `CASE_INSENSITIVE` correctness needed a whole second pass (an exact-only chain falling through to a fold-only chain) built by `buildForkChain` itself, rather than being resolved once at chain-construction time into each candidate's own `entrySet`.
- **Decision**: rejected in favor of the current design (2026-09-18, branch `flatten-matcher-dispatch`) — see this file's "Opcode set" section. Measured effect: a small real compile-time improvement on desktop JMH (~3%) and Pixel 3a (~4%), match time an effective wash on both devices — see README's benchmark section and notes.md for the numbers. The `entrySet`/`failedEntry`-on-every-node model does cost some of what this alternative avoided: `PassThroughMatcherConstruct`/`LoopBodyPartGateMarker` exist specifically to paper over the cases where a node can't simply carry its own gating (an alias to an already-compiled or differently-gated target, or a side effect that must not fire before the gate passes).

### Inline per-node comparison (no `entrySet`), instead of a precomputed entry gate

Each node would compare `peeked` against its own data inline and, on rejection before consuming, defer to `failedEntry`; on acceptance it commits and delegates to `next`, never branching on a delegated call's result (an opcode-chain model).

- **Pros**: no `entrySet`/`dispatchEntrySet` at all, so no `CodePointSet` aggregation for dispatch, no fold-expansion of `entrySet`, and no `PassThroughMatcherConstruct`/`LoopBodyPartGateMarker`. A speculative-vs-confirmed capture split (`startedGroups` promoted by `EndCapture`) cleanly handles captures on attempts that never complete.
- **Cons**: a leaf's own comparison only answers "do I match here?", not "can anything in this subtree start here?". A `Sequence` with a nullable prefix needs the outer fallback threaded onto later elements too (`((a?b)c)?` vs `""` failed), which needs either combinatorial matcher duplication, a per-attempt "would you accept" query (re-adding the membership check), or a commit signal breaking `final` fields.
- **Decision**: rejected (2026-09-18, implemented and reverted) -- see notes.md.

### Backreferences: catch-all entry set, dropping support, or a match-time check, instead of a precise compile-time entry set

A backreference's possible first characters depend on what was actually captured at match time, so a naive compile-time treatment has to either give up precision or give up on compile time entirely. Considered instead of the precise `firstCharSet()` approach described above:

- **(A) Drop backreferences entirely.** Simplest, and sidesteps the whole problem, but backreferences are commonly used (e.g. matching a repeated delimiter or tag) and most uses (anything not conditional/loop-tail) aren't actually ambiguous — dropping them unconditionally penalizes the common case to avoid the rare one.
- **(B) Keep a catch-all entry set (`entryElse = this`, today's actual behavior) and document backreferences as always lowest-priority relative to sibling branches.** Requires no new AST analysis. But it's not really a *design* — it's documenting an accident of `BackReference`'s current stub implementation — and it produces silently-wrong-relative-to-`java.util.regex` results for any pattern where a sibling branch should legitimately win: e.g. `(a)(?:\1|b)` against `"ab"` would always try `\1` first, when the two branches are in fact statically disjoint (`{a}` vs `{b}`) and should dispatch exactly.
- **(C) Defer the disjointness check to match time.** Would allow accepting patterns whose ambiguity can't be resolved statically at all, but makes matching non-total in a way nothing else in this engine is — every other construct's validity is fully known at compile time, and match failures are only ever "input didn't match," never "pattern itself turned out to be unsupported here." Introducing a runtime-detected-ambiguity failure mode breaks that guarantee for a single construct type.
- **Decision**: rejected all three in favor of the precise `firstCharSet()`-based entry set (see "Backreferences" above), which is strictly more permissive than (A), doesn't require documenting (B)'s surprising priority rule since real disjointness is checked instead, and keeps ambiguity detection fully at compile time unlike (C).

### Client-runnable Unicode generator with an external data file, instead of the checked-in `UnicodePredicates`

Let a client run `UnicodeAnalyzer` themselves, emitting script/category/property ranges to a non-code data file (e.g. from a newer JDK's Unicode tables), which this library would load at startup and prefer over its built-in `UnicodePredicates` when present.

- **Pros**: clients could get newer Unicode data without waiting for a library release or JDK-matched regeneration; the built-in data could shrink to a minimal fallback.
- **Cons**: a fair amount of work (a file format, a parser/loader, a discovery mechanism, versioning/validation of the file against the library); slower startup and likely slower matching/compilation, since the current sets are plain compiled-in `ArrayCodePointSet`s built by generated code while a loaded file needs a runtime parse and can't be constant-folded or class-loaded lazily the same way; a new failure mode (missing/corrupt/mismatched data file) and a shrinker/packaging question on Android; and very little practical value, since Unicode data changes rarely and regenerating `UnicodePredicates.java` (see notes.md) is already a small, documented step.
- **Decision**: rejected (2026-09-19) -- not worth the work or the speed cost.

### `CANON_EQ` by normalizing the input instead of rewriting the pattern

Normalize both the pattern and the input to NFD and match the normalized forms.

- **Pros**: canonical ordering makes mark permutations identical, so there is no alternation and no ambiguity at all.
- **Cons**: every `start()`/`end()`/`group()` must be mapped back to original-input offsets; and `java.util.regex`'s own behaviour needs a rule that a match can't end in the middle of a combining sequence for a class (`[a-z]` doesn't match the `e` of `e` + U+0301) but can for `.`, which normalizing the input erases. Needs surgery across `Matcher`, regions, bounds and `hitEnd`.
- **Decision**: rejected; the pattern rewrite needs no `Matcher` changes at all.

### `CANON_EQ` with a flat alternation of spellings, as `java.util.regex` does

Emit every equivalent spelling of a cluster as its own branch.

- **Pros**: simplest possible rewrite.
- **Cons**: with two or more reorderable marks, several branches begin with the same base character, so the pattern is rejected as ambiguous.
- **Decision**: rejected in favour of the left-factored trie above, which accepts every cluster.
