# Design

## Pipeline

`String pattern` → **`PatternParser`** (recursive descent) → **`PatternConstruct` AST** → **compile step** → **`MatcherConstruct` graph** → **`Matcher`** walks the graph against input, one code point at a time, with no backtracking.

### Parsing (`PatternParser` / `PatternConstruct`)

- Grammar is documented as regex-flavored BNF in comments at the top of `PatternParser.java`. It supports much of `java.util.regex.Pattern`'s syntax: groups (capturing, named, non-capturing), alternation, quantifiers (`?`, `*`, `+`, `{n,m}`, and their reluctant/possessive forms — accepted but treated as no-ops since this engine has no backtracking to be reluctant about), character classes (including nested `&&` intersection and `^` negation), escapes, boundaries (`\b`, `\B`, `\A`, `\G`, `\Z`, `\z`), and Unicode property/script/block/category classes (`\p{...}`).
- Lookahead and lookbehind are explicitly rejected at parse time (`throwUnexpectedChar("lookahead/lookbehind not supported...")`) because they can't be guaranteed to execute in linear time.
- Output is a `PatternConstruct` AST: `QuantifiedUnion` (alternation + optional quantifier + optional capture), `Sequence`, `LiteralString`, `ComplexCharacter` (a character class as a `CodePointMap<Boolean>`), `ComplexQuantifiedCharacter`, `BoundaryConstruct` (`\A`, `\Z`, `\z`), `LineBoundaryConstruct` (`^`, `$`), `WordBoundaryConstruct` (`\b`, `\B`) — the latter two split out separately, see "Boundary matching" below — `BackReference`, `EndConstruct`. `\G` produces no AST node at all — see "Boundary matching".

### Compilation (AST → matcher graph)

- Each `PatternConstruct` compiles itself plus its "what comes next" continuation into one or more `MatcherConstruct` nodes. This is the LL(1)-flavored core of the design: instead of a generic NFA, each construct's `buildEntryMap` computes the set of code points that count as *this construct's own* entry point — represented as a `CodePointMap<Boolean>` ("entryMap", every value `true`) plus a catch-all `entryElse`. The value is `Boolean`, not the owning `PatternConstruct`, because every `entryMap` is built by exactly one construct for itself (never aliased from another), so "who owns this range" is always already known from context — every consumer either already has that construct in hand, or (when merging multiple candidates' entry points — see `mergeEntryPoints` below) reads it from a genuinely multi-valued `CodePointMap<PatternConstruct>` built separately for that purpose, never from a single construct's own `entryMap`.
- The critical invariant the compiler must enforce: for any `QuantifiedUnion` (i.e. any `|` alternation, and any quantified construct's "keep looping vs. exit the loop" choice), the entry ranges of its branches must be pairwise disjoint. If two branches could both match the same next code point, that's a compile-time `PatternSyntaxException` (ambiguous branch), not a runtime backtrack. `PatternConstruct.compileAndMergeCandidates` (used by both plain alternation and loop dispatch) compiles each candidate, converts its entry ranges to a `CodePointMap`, and rejects the first overlapping range with a `PatternSyntaxException` naming the candidate index and the conflicting characters.
- **Quantifier/loop compilation**: a quantified construct (`QuantifiedUnion` or `ComplexQuantifiedCharacter` with `min != 1 || max != 1`) compiles to a plain `DispatchMatcherConstruct` (built via its loop-flavored constructor — see "Opcode set" below; this is the externally-visible entry point, self-registering into `owner.matcher` to break the cycle described below) whose one dispatch map routes "continue" characters through a `LoopMatcherConstruct` (enforces `max`, then dispatches to whichever body part matched) and "exit" characters through an `EndLoopMatcherConstruct` (enforces `min`, then dispatches to `next`). The *same* map serves both the first attempt and every re-check after a successful iteration — no special-casing for `min == 0` vs `min >= 1` is needed in the dispatch map itself, because the runtime min/max counters (not two different static maps) are what make one map correct for every bound: even on the very first attempt, if the input's next character happens to look like "exit", the dispatch correctly routes there and `EndLoopMatcherConstruct` correctly rejects it if `min` hasn't been satisfied yet.
- **Capturing groups**: a capturing, unquantified `QuantifiedUnion` (`captureConstructIndex != -1`) wraps its compiled alternation-dispatch node in a `BeginCaptureMatcherConstruct` (which becomes `owner.matcher`, recording the start position), and compiles its branches against a `CaptureEndMarker` — a zero-width synthetic `PatternConstruct` standing in for the real `next` — whose own matcher is an `EndCaptureMatcherConstruct` (records the substring, then forwards unconditionally to the real `next`). Capture storage (`Matcher#captureGroups`) is a flat array indexed by a fixed `captureConstructIndex` known to both `BeginCapture` and `EndCapture` (not a stack — this engine has no recursion, so the same capture construct can never be open twice at once, and re-entering it naturally overwrites the previous `Group` — exactly regex's "last iteration wins" semantics — for free; this is exactly what the capturing-and-quantified case below relies on).
- **Capturing AND quantified at once** (e.g. `(a)*`): `DispatchMatcherConstruct`'s loop-flavored constructor takes a `captureConstructIndex` (`-1` when not capturing). When capturing: each loop body part compiles against a `CaptureEndMarker` standing in for the loop's own `owner` (instead of `owner` directly), so finishing one iteration records the captured substring before looping back rather than looping back directly; `LoopMatcherConstruct` dispatches unconditionally to a `BeginCaptureMatcherConstruct`, whose one successor is an internal (non-self-registering) `DispatchMatcherConstruct` that does the by-character dispatch among body parts (`BeginCapture`/`EndCapture` stay pure single-successor opcodes — see "Opcode set" below; this composes them rather than giving `BeginCapture` a second, branching role — see "Alternatives Considered"). Ambiguity detection is unaffected — it runs identically whether or not the loop is capturing, since capturing only changes what happens once a branch is chosen, not which branch gets chosen.
- `MatcherConstruct` subclasses (in `MatcherConstruct.java`) are the compiled, executable nodes — see "Opcode set" below for the full set and the Single/Multi-dispatching split. Each node's `match(Matcher, int peeked)` method consumes zero or more code points and advances to its successor(s), either an unconditional single successor or (for the handful of genuinely branching nodes) a range lookup on the next code point via `getNext(...)`.
- Matching is therefore just: start at the compiled root node, and recursively call `match()`. No backtracking stack is needed because ambiguity was already ruled out at compile time.

#### The `compile()` algorithm and cycle handling

`MatcherConstruct` instances are deeply immutable once built — no self-referencing mutable fields (see "Opcode set: Single/Multi dispatch split" below for why this matters, in particular for `MultiDispatchingMatcherConstruct`). But the matcher graph *does* have cycles (a loop's body eventually dispatches back to the loop's own entry `MatcherConstruct`), so something has to break the cycle during construction without the constructed node ever seeing a half-built dependency:

- Every `PatternConstruct` has a `@MonotonicNonNull MatcherConstruct matcher` field. `PatternConstruct.compile()`'s contract: if `matcher` is already non-null, return it immediately — don't rebuild. Otherwise, build `entryMap` and then construct the one `MatcherConstruct` this node compiles to.
- The key trick is in the `MatcherConstruct` subclass constructors, not in `compile()`: a `MatcherConstruct` constructor must, as its *very first* action, assign `this` to its owning `PatternConstruct`'s `matcher` field — *before* it does anything else, including looking up or compiling any of its own dependencies (e.g. what a loop dispatches back to, or what a union's branches dispatch to). Only after that assignment does the constructor walk the `PatternConstruct` graph (via each dependency's own `compile()`) to resolve the `MatcherConstruct`s it needs for its `dispatchMap`/`exitMap`, and accumulate those into its own dispatch map.
- This ordering is what makes cycles safe without any visited-set/recursion-guard bookkeeping: if compiling node A transitively needs to compile node B which loops back and needs A again, that second `compile()` call on A sees `matcher` already set (to the in-progress `A` instance) and returns it immediately, rather than recursing infinitely. The returned reference is to a real, fully-constructed-by-the-time-anyone-uses-it object — it's *only* used as a dispatch-map value (a reference to jump to), never dereferenced by the constructor that's still running, so returning a self-reference mid-construction is safe even though the object's own fields (its dispatch map) aren't filled in yet at the moment it's handed out.
- Compiling tail-to-front (i.e. `compile()` is always called with "what comes next" already known/passed in, starting from `EndConstruct` and working backwards through the pattern) makes cycles rare in practice, even though the mechanism above handles them regardless.
- The constructor navigates via a reference to its owning `PatternConstruct`, not via extra constructor arguments per dependency: `PatternConstruct` has a `next` field (recorded in `compile()`); for an *acyclic* dependency, everything a `MatcherConstruct` constructor needs is already reachable off `owner` by direct field read (`owner.next.matcher`, or `owner.entryMap`'s `PatternConstruct` values' own `.matcher` fields) — no `.compile()` call needed. Loop compilation is the one case that genuinely needs the self-registration-then-*recurse* pattern (not just self-registration-then-read): `DispatchMatcherConstruct`'s loop-flavored constructor self-registers into `owner.matcher` *first*, then calls `part.compile(owner)` for each body part — safe, since a nested attempt by the body to read `owner.matcher` again finds the (still-being-built) `DispatchMatcherConstruct` instance already there instead of recursing.

##### Entry-point computation vs. matcher compilation

A `PatternConstruct`'s `entryMap`/`entryElse` (its own advertised "what character(s) can follow me") and its `matcher` (the compiled `MatcherConstruct` graph) are two separate, independently-lazy computations, each memoized and cycle-guarded on its own:

- `getEntryPointMap()`/`getEntryElse()` are the only way anything reads another construct's entry set (never the raw `entryMap`/`entryElse` fields directly). The first call lazily invokes `buildEntryMap(next)`, guarded by a three-state flag (not started / constructing / constructed) on the construct itself: a re-entrant call made *while that same construct's own `buildEntryMap` is still running* throws (see below) instead of silently reading a half-built map or recursing forever. A call arriving after that construct has already finished (a completely ordinary case, not a re-entrant one) just returns the cached result.
- Critically, this guard is scoped to *entry-point construction specifically* -- not to matcher compilation, and not to "is this construct anywhere on the current call stack for any reason." A construct's `matcher` can be (and, for a loop's entry/re-entry node, always is) self-registered and sitting mid-construction while something else asks for that same construct's entry point for the first time; that's not re-entrance, it's simply the first, on-demand request, and it's resolved immediately by delegating structurally to whatever sub-part actually determines it.
- Because of that, `buildEntryMap` for `Sequence` and for a quantified construct (`QuantifiableConstruct.buildLoopEntryMap`) must never trigger anything's full `compile()`/`buildMatcher()` -- only entry-point getters, plus a cheap, direct assignment of each relevant sub-part's `next` field (bypassing `compile()` entirely) so a nullable sub-part can still fold in what follows it. `Sequence`'s own entry set is always exactly its *first* element's (entering the sequence means entering its first element); the tail-to-front `compile()` calls that actually wire up the matcher graph happen separately, in `buildMatcher()`. A quantified construct's own entry set is `FIRST(body)` (the union of its body parts' entry points, each body part's `next` pointed at the construct itself) unioned with `next`'s own entry set when `min == 0` (skipping the construct entirely is valid) -- computed once, in `buildEntryMap`, well before `buildMatcher()` builds the real dispatch graph (which still needs the full body-plus-`next` candidate merge, since "continue vs. exit" routing is a different, larger question than "what's my own advertised entry set").
- This split is what makes a loop nested inside another loop's body resolve correctly: the nested loop's own dispatch construction needs the *outer* loop's entry set (since exiting the nested loop routes to the outer loop), and asking for it via `getEntryPointMap()` triggers the outer loop's cheap, structural `FIRST(body)` computation on the spot if nobody's asked yet -- which typically bottoms out immediately (e.g. in `(a(b)?)+`, the literal `a` pins the outer loop's entry set without ever needing to touch the inner `(b)?` loop at all). The one case that's a genuine, unbreakable cycle is a loop whose entire body can match zero characters (e.g. `(a?)+`): computing the loop's own entry set then requires its own not-yet-available entry set, and the guard converts that into a `PatternSyntaxException` naming the loop's start index, rather than a stack overflow or a silently wrong dispatch -- consistent with this engine's "unsatisfiable/indeterminate at compile time is an error, not a silent failure" philosophy elsewhere (see "Boundary matching" above). Note this is also just an infinite-loop hazard in its own right (a loop that can advance zero characters per iteration), so rejecting it at compile time isn't purely an artifact of the implementation technique.

##### Opcode set: Single/Multi dispatch split

The matcher graph is a small "opcode" virtual machine:

- **`SingleDispatchingMatcherConstruct`** (abstract, holds `final MatcherConstruct next`, called via a plain virtual `next.match(...)`): the base for every node whose successor is fixed at construction time and never depends on which character was seen. Subclasses: `SingleCharMatcherConstruct` (character-class membership test via `CodePointMap#get`, not a dispatch lookup), `LiteralMatcherConstruct`, `BeginCaptureMatcherConstruct`, `EndCaptureMatcherConstruct`, `EndLoopMatcherConstruct`, `WordBoundaryMatcherConstruct`, `BackReferenceMatcherConstruct`/`BoundaryMatcherConstruct` (the latter two still stub `match()`s for their unimplemented cases, but are structurally single-successor). `next` is safe to be `final` here because none of these nodes are ever the self-referential node in a cycle — only a loop's entry dispatch node is, and that's `MultiDispatchingMatcherConstruct`'s job (below).
- **`MultiDispatchingMatcherConstruct`** (abstract, holds a `CodePointMap`-based `dispatchMap` whose own else-value (`CodePointMap#getElseValue`/`#setElseValue`) is the "else" successor, deliberately not `final` — a self-referential dispatch entry, a loop dispatching back to its own entry node, is unavoidably written by a *different*, nested constructor call while this one is still running; see the class doc for the full argument for why the whole graph is still safely published): the base for the two node *shapes* that genuinely branch on the next code point: `DispatchMatcherConstruct` (a union's `|`; also, via a second, loop-flavored constructor, a quantified construct's entry/re-entry dispatch — it's literally the same class as a union's dispatch, not a separate opcode, since both are exactly "route by next character without consuming it") and `LoopMatcherConstruct` (bolts a counter/max check onto multi-dispatch, since after that check it must still route to whichever body part matched).
- **`EndLoopMatcherConstruct`** is single-successor: it checks `min`, resets the loop's counter slot to 0, then advances — the reset-on-exit is sufficient without a separate reset-on-entry step because this engine never backtracks: a failed loop attempt aborts the whole match rather than retrying with stale counter state, so the slot is already 0 whenever a loop is freshly (re-)entered.
- **`BeginCaptureMatcherConstruct`/`EndCaptureMatcherConstruct`** are pure single-successor opcodes, unrelated to looping, with the flat `captureGroups` array + fixed `captureConstructIndex` design described above (not a stack). The capturing-and-quantified case composes existing opcodes rather than giving `BeginCapture` a second, branching role — see "Alternatives Considered": `LoopMatcherConstruct` → `BeginCaptureMatcherConstruct` (single successor) → an internal `DispatchMatcherConstruct` doing the actual per-branch routing → ... → `EndCaptureMatcherConstruct` → loops back to the entry node.
- **`EndMatcherConstruct`** has no successor at all, so it extends neither base directly.

`SingleDispatchingMatcherConstruct.next.match(...)` is called as a plain virtual call — see "Alternatives Considered" for why a bound-`MethodHandle` form was tried and rejected.

#### Boundary matching (`BoundaryConstruct`/`WordBoundaryConstruct`/`LineBoundaryConstruct`)

Unlike every other construct (essentially "a dispatch map keyed by the next code point"), a boundary depends on matcher *state* — position, surrounding characters — not just the upcoming code point. Two boundary types have grown a real implementation with their own logic distinct enough that each got pulled out of the original single `BoundaryConstruct`/`BoundaryEnum`-keyed dispatch into its own `PatternConstruct`/`MatcherConstruct` pair: `\b`/`\B` (`WordBoundaryConstruct`/`WordBoundaryMatcherConstruct`) and `^`/`$` (`LineBoundaryConstruct`/`LineBoundaryMatcherConstruct`). `BoundaryConstruct`/`BoundaryMatcherConstruct` now only cover `\A`, `\z`, and `\Z`.

`\G` is a different case entirely: per the project owner, it doesn't actually match any specific position in the input at all -- it's really just a flag meaning "anchor `find()` to exactly where the previous match ended, don't scan forward for a later one," and `Matcher#matchEnd` already tracks that position (for `group(0)`/`end()`). So `\G` gets no `PatternConstruct`/`MatcherConstruct` representation whatsoever: `PatternParser` recognizes it directly (not through the generic boundary-parsing path) and sets a `boolean anchorsToPreviousMatchEnd` flag, carried onto `Ll1Pattern`, consulted only by `Matcher#find(int)` -- when set, `find(int start)` tries `attemptMatch(start, false)` exactly once instead of scanning `[start, regionEnd]`. `matches()`/`lookingAt()` are unaffected, since they never scan for a later start position in the first place, so `\G` has nothing to change there. `\G` is only accepted as the very first thing in the whole pattern (a raw index-0 check on the pattern string, before any other parsing) -- anywhere else it's rejected at compile time with a `PatternSyntaxException`, rather than silently doing nothing there the way `java.util.regex` does.

`\b`/`\B` (word boundary / non-word-boundary) are implemented via `Matcher#peekPrevious()` (mirrors `peek()`, looking one code point backward instead of forward, bounded at `regionStart` rather than `0` since `useTransparentBounds()` is still a stub) and a dedicated `WordBoundaryMatcherConstruct`. It's a plain `SingleDispatchingMatcherConstruct` — it doesn't consume input, so it still has exactly one successor, just like every other single-dispatch node; branching on matcher state didn't require a new node *shape*, only a new field (`peekPrevious()`) to read.

On top of that, `WordBoundaryConstruct.buildMatcher()` applies a compile-time optimization: `\b`/`\B` very often sit next to a literal/character-class with a statically known "is this a word character" answer, so only one side needs checking at match time in that case. It classifies both the character just consumed and the one about to be consumed as always-word/always-non-word/unknown:
- **Peek side** (the character about to be consumed): read directly off the already-built `entryMap`/`entryElse` of `next` — no new analysis needed. If `next.entryElse != null`, or its `entryMap` ranges are a mix of word and non-word code points, the side is unknown.
- **Prior side** (the character just consumed): a `PatternConstruct.lastCharSet()` recursion, walking `LiteralString`/`ComplexCharacter`/`ComplexQuantifiedCharacter`/unquantified `QuantifiedUnion`/`Sequence`. Returns `null` (a safe "not statically known" fallback) for anything that could match zero-width, or for any construct type it doesn't recognize. `Sequence.buildEntryMap` sets this (via `lastCharSet()` on the preceding sibling) before compiling a `WordBoundaryConstruct` that isn't the first element of its `Sequence`; it's left `null` (safe, just unoptimized) otherwise.

If both sides are statically known, the boundary either always holds (compiles to a zero-width no-op, `matcher = next.matcher`) or never can (a compile-time `PatternSyntaxException` — e.g. `a\bb` is rejected, since two word characters can never have a word boundary between them; this is consistent with this project's general "unsatisfiable at compile time is an error, not a silent always-fail" philosophy, unlike `java.util.regex`, which would compile `a\bb` and just never match it). Otherwise, `WordBoundaryMatcherConstruct` only checks whichever side isn't statically known, via a small pair of enums (`PriorWordBoundaryMatchType`/`PeekWordBoundaryMatchType`) whose combinations are constructed by `WordBoundaryConstruct.buildMatcher()` so the nonsensical ones are unconstructible, and only calls the (slightly more expensive, backward-looking) `peekPrevious()` when the preceding side is the one left unresolved.

`BoundaryConstruct`'s `BoundaryEnum` values (`\A`, `\z`, `\Z` -- `\G` no longer among them, see above) are all implemented:

- **`InputBegin`/`InputEnd`** (`\A`/`\z`): always the true start/end of input (`pos == regionStart`/`pos == regionEnd`) -- `MULTILINE` has no effect on either.
- **`InputEndExceptTerminator`** (`\Z`): the end of input, or immediately before the input's own *final* line terminator, if it has one -- checked by scanning forward from `pos` for a line terminator that reaches exactly to `regionEnd` (not merely one somewhere in the remaining input), via the package-private `MatcherConstruct.matchesEndExceptTerminator` helper (shared with `LineBoundaryMatcherConstruct`, below). This is a zero-width assertion that does not consume the terminator, so `matches()` (which requires the whole region, terminator included) still fails whenever one is present; only `find()`/`lookingAt()` (a prefix match) see the exemption -- verified directly against `java.util.regex` while implementing this, since it's easy to misremember `matches()` as tolerating it too.

`LineBoundaryConstruct`/`LineBoundaryMatcherConstruct` (`^`/`$`, a `boolean isLineBegin` distinguishing them instead of a shared enum): without `MULTILINE`, exactly `InputBegin`/`InputEndExceptTerminator` (`^` reuses the plain `pos == regionStart` check; `$` reuses `matchesEndExceptTerminator`). Under `MULTILINE`, `^` also matches immediately after any line terminator (a backward scan, `MatcherConstruct.lineTerminatorLengthBefore` -- the mirror image of the forward `lineTerminatorLengthAt` scan `\Z`/multiline-`$` use, treating a `"\r\n"` pair as ending at one position, not creating a second match point between the `\r` and the `\n`), and `$` also matches immediately before any line terminator. Line-terminator recognition (`\n`, `\r`, `"\r\n"` as one unit, `\u0085`, `\u2028`, `\u2029` by default; only `\n` under `UNIX_LINES`) is implemented once, symmetrically, as two `MatcherConstruct`-level static helpers shared by both `BoundaryMatcherConstruct` and `LineBoundaryMatcherConstruct` rather than duplicated.

### Code point range representation

- `CodePointMap<V>` (interface) is the intended long-term replacement for ad-hoc uses of Guava `RangeSet`/`RangeMap<Integer, V>` throughout this codebase, and — as of 2026-09-08 — the *only* code-point-to-value map anywhere in the compiled-graph/entry-point/runtime-dispatch family; no Guava `RangeMap` remains anywhere in it. Two implementations exist: `ArrayCodePointMap<V>` is the one actual callers use -- `PatternConstruct.entryMap` (every construct's own entry point, `CodePointMap<Boolean>`), `QuantifiedUnion.rawEntryMap` (the genuinely multi-valued `CodePointMap<PatternConstruct>` `DispatchMatcherConstruct` needs to build the runtime dispatch graph -- assigned directly from `mergeEntryPoints`'s own result, no copy needed), the ambiguity-detection/entry-map merging in between, and — the actual match-time hot path — `MultiDispatchingMatcherConstruct.dispatchMap` (`CodePointMap<MatcherConstruct>`, consulted by `getNext()` on every `find()`/`matches()` call) all go through it now; `TreeCodePointMap<V>` (delegating to Guava's `TreeRangeMap`) is kept only as the differential-test oracle `ArrayCodePointMap` is checked against (see `CodePointMapDifferentialTest`), not as a production alternative.
- `[min, max)` range convention throughout, immutable `Range`, `put`/`get`/`remove`/`containsKeys`, `union`/`difference`/`intersection`, `compute`/`computeIfAbsent`, `complement`, and `intersectionRejectingConflicts` — the last one specifically for the union/loop-ambiguity use case: it's like `intersection`, but throws `ConflictingMappingException` the moment two maps disagree on the value for an overlapping code point, which is exactly "these two branches both claim this character" in LL(1) terms.
- `getElseValue()`/`setElseValue(V)` (the latter on `MutableCodePointMap`) expose the else-value directly, and `getExplicit(codePoint)` (like `get`, but returns non-null only for a real explicit entry, ignoring the else-value fill) lets a caller do its own layered fallback before deferring to the else-value -- see `MultiDispatchingMatcherConstruct.getNext()` below, which stores its "else" successor as `dispatchMap`'s own else-value instead of a separate field.
- `complement(value)` (and every implementation's `getElseValue()`) is always finite, unlike Guava `RangeSet#complement()`: since the code point domain itself is bounded (`[0, MAX_CODE_POINT]`), "every code point this map doesn't have" is representable as an ordinary map with an implicit *else-value* — the value returned for any code point without an explicit entry — rather than an actually-unbounded structure. Each implementation stores this as a normal map (`ArrayCodePointMap`'s array / `TreeCodePointMap`'s `RangeMap`) plus that else-value, with one added wrinkle: an explicit entry can also be a "punched hole" (internally, a `null`-valued entry — never exposed to ordinary callers, who get a clear exception if they try to `put` a `null` value themselves) that excludes a range from the else-value fill without itself carrying a real value. `complement(value)` builds exactly this: else-value = `value`, one punched hole per entry of the source map's own `entrySet()` (which, being finite itself by the same argument, always yields a finite hole set — including when the source is itself a complement, so double-complement round-trips correctly). `entrySet()`, `get`/`getOrDefault`, and `containsKeys` all account for the else-value and punched holes directly; `union`/`putAll`/`difference`/`intersection`/`intersectionRejectingConflicts` need no else-value-specific logic of their own beyond that, since they're all built on `entrySet()` (or, for `ArrayCodePointMap`'s hot-path array-window scan, fall back to the else-value-aware materialization only when the receiver actually has one) — an else-value map's "everywhere else" is just more (finite) entries as far as those algorithms are concerned.
- `PatternConstruct.ComplexCharacter.ranges` (and everything downstream of it -- `containsFolded`, `SingleCharMatcherConstruct.validRanges`, `firstCharSet`/`lastCharSet`/`WordBoundaryConstruct.priorCharSet`/`wordSet`) is now a `CodePointMap<Boolean>`, not a Guava `RangeSet<Integer>`. `[^...]`/DOTALL negation goes through `CodePointMap#complement` directly; `&&` intersection is a real intersection (`b.intersection(min, max)` per `a`-entry, else-value-aware on either side) rather than the old `a.removeAll(b.complement())` formula, which would otherwise force materializing a complement just to subtract it. `MatcherConstruct#containsFolded` guards the `-1` end-of-input sentinel explicitly before consulting the map -- unlike `getNext()`'s `getExplicit()`, membership here has to see an else-value's fill (a negated class legitimately matches everything it doesn't exclude), so it can't rely on `getExplicit()` to keep `-1` out the way `getNext()` does; `-1` is simply never a real code point, checked first, unconditionally.
- `NamedCharClass`/`UnicodePredicates` (and the `RegexCharacterClass` enum nested in the former) are `CodePointMap<Boolean>` throughout now too -- no Guava `RangeSet`/`RangeMap` remains anywhere in `llkpattern/src/main`. Every constant's `ascii`/`unicode` field is a `CodePointMap<Boolean>`; hand-written literal sets use a small `build(Consumer<MutableCodePointMap<Boolean>>)` helper (an `ArrayCodePointMap` filled via ordinary `put`, which -- unlike the generated file's `appendSorted` -- tolerates entries added out of order); `unionOf`/`difference` are thin wrappers over `CodePointMap#union`/`#difference`. A constant that's logically a complement (`Assigned`, `\D`, `\H`, `\S`, `\V`, `\W`, `DOT`) is *eagerly materialized* into real entries (`materializedComplement`, a full `[0, MAX_CODE_POINT]` sweep) rather than built via `CodePointMap#complement`'s else-value fill: every consumer of these constants (unions, intersections, `entrySet()`-iterating code like `PatternParser`'s ambiguity check) expects ordinary "this set's members are its entries" semantics, and an else-value map's `entrySet()` is the *holes*, not the members -- the same inversion trap `PatternParser`'s own `materializeComplement` (used for `\P{...}`, merging into an already-populated `ComplexCharacter.ranges` via `putAll`, which only copies explicit entries) exists to avoid. `PatternParser`/`WordBoundaryConstruct` consume `NamedCharClass`/`RegexCharacterClass` constants directly now (no adapter step) -- `get(prefix, flags)`/`get(flags)` already return a `CodePointMap<Boolean>`.
- `CharacterClass.java` (the old, confirmed-dead `ImmutableRangeSet`-wrapper design that predated `ComplexCharacter`'s own ranges) has been deleted.
- `ArrayCodePointMap` is specialized to the Unicode code point domain: two parallel arrays, `int[] keys` (each packing `(min << 11) | count`, where `count` is the number of *additional* code points after `min` sharing the same value — 21 bits for `min` plus 11 for `count` fits an `int` exactly, no `long` needed) and a parallel `V[] values`, kept sorted by `min` for binary-search lookup. This avoids `TreeRangeMap`'s per-entry node/object overhead in favor of two flat arrays (starting at capacity 1 and growing by 1.5x, since most instances here are small), which is both smaller and more cache-friendly during matching. The binary search compares each key's *extracted* `min` (always a non-negative `int` in `[0, MAX_CODE_POINT]`), never the raw packed key itself, specifically to sidestep any sign-bit concern from packing `min` into high bits (a code point at/above `0x100000`, plane 16, does land on the sign bit when packed).
- Every mutator (`put`, `remove`, the bulk-append `appendSorted`) is localized to just the region of the array it actually touches, found via the same binary-search lookup reads use — a single touched entry is a plain field edit or lone insert/delete, and multiple touched entries trim the first/last in place and shift out whatever's strictly between, all without scanning the rest of the map. Building an n-entry map via n `put`/`appendSorted` calls is therefore O(n) amortized, not O(n^2) — an earlier version that rescanned the whole array on every mutation regressed a JMH benchmark by 3.4x before this was caught (see notes.md's 2026-09-08 entry).
- `entrySet()` always yields entries in ascending `min` order — a `CodePointMap`-interface-level contract (every implementation satisfies it for free, being a map of disjoint ranges over an ordered domain), not just an `ArrayCodePointMap` detail. `MutableCodePointMap.putAll`'s optimized override relies on it directly: rather than one `put()` call per source entry, it's a single sorted merge sweep over this map's own entries and the source's (`other` winning on overlap), degenerating automatically to a plain bulk append when the target starts empty. Every compile-time site that copies (or value-transforms) an already-known-sorted source into a fresh, empty destination map — every `PatternConstruct.buildEntryMap`/`buildMatcher` and `MatcherConstruct.populate`/loop-dispatch site that walks a child's or a merge result's `entrySet()` — uses `appendSorted` rather than `put`/`putAll` for exactly this reason: `put()`'s binary-search-and-splice is wasted work when the destination is empty and the entries already arrive in order (a plain filter, i.e. skipping some source entries, doesn't break this — the ones kept are still ascending). Only genuinely irregular, out-of-order construction (e.g. `NamedCharClass`'s hand-written literals, see below) still needs `put`.
- Adjacent entries with equal values are coalesced together on mutation (unlike `TreeCodePointMap`, whose Guava backing never auto-coalesces), except where doing so would exceed a single entry's 2048-code-point capacity (the 11-bit count field's range) — a longer logical range unavoidably splits across multiple consecutive entries, which is observable through `entrySet()` even though it maps to one logical value throughout.

### Unicode support

- `NamedCharClass` maps regex-style named classes (`\p{Alpha}`, `\p{IsGreek}`, `\p{general_category=Lu}`, etc.) to underlying `CodePointMap<Boolean>` predicates/ranges.
- `UnicodePredicates` is a ~14k line generated data file of Unicode category/script/block predicates (one `CodePointMap<Boolean>` field per predicate), produced by the `unicodeanalyzer` module's `UnicodeAnalyzer` from the running JDK's own `Character` tables. It carries a "DO NOT EDIT" javadoc and a `javax.annotation.processing.Generated` annotation recording the generation date; regenerate it with `./gradlew :unicodeanalyzer:generateUnicodePredicates` (run manually, as needed -- e.g. after a JDK upgrade changes Unicode data -- not part of the normal build). Script and block predicates are already generated into this file (one field per `Character.UnicodeScript`/`UnicodeBlock` value) but not yet wired into `NamedCharClass`'s `Source.Script`/`Source.Block` -- see remaining_work.md.

### Backreferences

- Decided: backreferences (`\1`, `\k<name>`) are supported, with disjointness checked at **compile time** using a precise, statically-computed entry set — not the current `entryElse = this` catch-all in `BackReference`. Not yet implemented; see remaining_work.md.
- A backreference's possible first characters are exactly the *referenced group's* possible first characters, computed by a new `firstCharSet()` AST helper mirroring the existing `lastCharSet()` used for `\b`/`\B`'s prior-character classification (same recursion shape: literal → first code point, character class → its ranges, sequence → first element, unquantified union → union of branches). Feeding this into the normal `RangeMap` disjointness check makes ordinary backreference usage (e.g. `(\w+)\s+\1`) compile with no special-casing, while genuinely ambiguous uses (e.g. `(a+)\1`, where the loop's continue-branch and the backreference's entry set both include `a`) are correctly rejected as a compile error, exactly like any other ambiguous alternation.
- Possibly-empty referenced groups (e.g. `(a*)\1`, where `\1` can be zero-width) make `firstCharSet()` return unknown, falling back to the catch-all entry set — same as `BackReference`'s original, pre-`firstCharSet()` stub. Fed into the normal disjointness check, this correctly rejects two such backreferences (or a backreference and any other catch-all construct) sharing the same alternation/loop-tail dispatch, since two catch-alls are always ambiguous; a single catch-all backreference alongside sibling branches with specific, disjoint entry sets isn't itself ambiguous (the specific branches simply take priority) and compiles fine, matching zero-width handling's existing "rare and probably not what you want, but not unsound" treatment elsewhere in this engine.
- Forward references (`\1` before its group is defined, e.g. `\1(a)`) are rejected at compile time.

### Public API shape

- `Ll1Pattern` and `Matcher` are designed to mirror `java.util.regex.Pattern`/`Matcher`'s public method surface, so callers can largely swap one for the other. See remaining_work.md for the current list of implemented vs. stubbed methods.
- **One compiled graph serves `matches()`, `lookingAt()`, and `find()`** — they don't need separate compilations. The difference between them is entirely about the `EndConstruct`/`EndMatcherConstruct` terminal: `matches()` requires the *whole region* to be consumed to succeed, while `lookingAt()`/`find()` only need a matched *prefix* (the rest of the string is allowed to be leftover). Rather than baking that choice into the compiled graph, it's a single `boolean requireFullMatch` field on `Matcher`, set immediately before each match attempt (`matches()` sets it true; `lookingAt()`/`find()` set it false) and read only by `EndMatcherConstruct.match()` (`return !matcher.requireFullMatch || matcher.pos == matcher.regionEnd;`). This mirrors how `java.util.regex`'s own NFA nodes take an "anchoring" flag rather than compiling two different automata.
- `EndConstruct` (the compile-time sentinel `Ll1Pattern.compile()` passes as the outermost `next`) registers `entryElse = this` in its own `entryMap` — reachable regardless of what character (or lack of one) comes next — rather than only the code point `-1` (Matcher's "no more input" sentinel — see `Matcher#peek()`). The latter would be sufficient for `matches()` (where reaching the terminal only ever happens at true end of input) but wrong for `lookingAt()`/`find()`: an *optional* loop's "exit" path (e.g. `a*` matched via `lookingAt()` against `"b"`) needs to be reachable at a position with real, valid leftover characters, not just at true end of string. `requireFullMatch` enforces the stricter check only when it's actually wanted.
- `Matcher#quantifiableCounts`/`captureGroups` are sized automatically from the compiled `Ll1Pattern` (`PatternParser` exposes the final quantifiable-construct count, capture-group count, and a name→`captureConstructIndex` map after `parse()` via `getQuantifiableCount()`/`getCaptureGroupCount()`/`getNamedGroups()`).
- `find()`'s unanchored search is a straightforward linear scan (`attemptMatch` at each candidate start position, `lookingAt()`-style, until one succeeds or the region is exhausted) — every candidate start position is just an ordinary `lookingAt()`-style attempt from a different `pos`.

## Alternatives Considered

### Successor dispatch via bound `MethodHandle` (`findSpecial`) instead of a plain virtual call

Considered for `SingleDispatchingMatcherConstruct.next.match(...)`: bind a `MethodHandle` to the successor's exact `match` override at construction time (via `findSpecial`, an `invokespecial`-style direct call — `findVirtual` + `bindTo` was also tried and rejected on the same grounds, since it's still an ordinary virtual dispatch under the hood) and invoke that instead of `next.match(matcher, peeked)`.

- **Pros**: in principle, skips a virtual-dispatch lookup per match step; `findSpecial`'s `invokespecial` semantics are exactly "call this one exact method," which is all a fixed `next` reference ever needs.
- **Cons**: a `MethodHandle` invocation on a non-static receiver isn't reliably inlined by any JVM, and is frequently *slower* than a plain virtual call even on newer Android runtimes — the entire performance premise doesn't hold. Getting a working, Android-API-26-compatible form at all required real complexity: `findSpecial` requires its `specialCaller` argument to be the calling `Lookup`'s own `lookupClass()` (or a subclass) — it emulates `super.foo()` from a specific class, not "call this concrete method on some unrelated object" — which fails for the common case of a `SingleDispatchingMatcherConstruct` whose successor is a sibling-hierarchy `MultiDispatchingMatcherConstruct`. The only fully-general fix, `MethodHandles.Lookup.privateLookupIn`, is Java 9+/Android API 33+ — below this project's Android floor of API 26 (worth over half of live Android devices vs. under half on API 33) — so avoiding it meant every concrete leaf class supplying its own one-line `findSpecial` call (exploiting `MethodHandles.lookup()`'s caller-sensitivity), real per-class boilerplate for no realized benefit.
- **Decision**: rejected. `SingleDispatchingMatcherConstruct.matchNext` uses a plain `next.match(matcher, peeked)`.

### `BeginCaptureMatcherConstruct` with a built-in branching role, for capturing-and-quantified loops

Considered for compiling a capturing, quantified construct (e.g. `(a)*`): give `BeginCaptureMatcherConstruct` a second mode where it itself holds a `dispatchMap` and does the per-branch routing among the loop's body parts, rather than being a pure single-successor node.

- **Pros**: one fewer node type actually allocated per capturing-loop iteration (no separate internal `DispatchMatcherConstruct`).
- **Cons**: breaks the clean Single/Multi dispatch split — a node meant to be single-successor gains a dispatch map, undermining the invariant that only `MultiDispatchingMatcherConstruct` subclasses ever branch on the next code point, and complicating `BeginCaptureMatcherConstruct` for every non-capturing-loop caller too.
- **Decision**: rejected. The capturing-and-quantified case instead composes existing opcodes: `LoopMatcherConstruct` → `BeginCaptureMatcherConstruct` (plain single successor) → an internal (non-self-registering) `DispatchMatcherConstruct` → ... → `EndCaptureMatcherConstruct` → back to the loop's entry node.

### Backreferences: catch-all entry set, dropping support, or a match-time check, instead of a precise compile-time entry set

A backreference's possible first characters depend on what was actually captured at match time, so a naive compile-time treatment has to either give up precision or give up on compile time entirely. Considered instead of the precise `firstCharSet()` approach described above:

- **(A) Drop backreferences entirely.** Simplest, and sidesteps the whole problem, but backreferences are commonly used (e.g. matching a repeated delimiter or tag) and most uses (anything not conditional/loop-tail) aren't actually ambiguous — dropping them unconditionally penalizes the common case to avoid the rare one.
- **(B) Keep a catch-all entry set (`entryElse = this`, today's actual behavior) and document backreferences as always lowest-priority relative to sibling branches.** Requires no new AST analysis. But it's not really a *design* — it's documenting an accident of `BackReference`'s current stub implementation — and it produces silently-wrong-relative-to-`java.util.regex` results for any pattern where a sibling branch should legitimately win: e.g. `(a)(?:\1|b)` against `"ab"` would always try `\1` first, when the two branches are in fact statically disjoint (`{a}` vs `{b}`) and should dispatch exactly.
- **(C) Defer the disjointness check to match time.** Would allow accepting patterns whose ambiguity can't be resolved statically at all, but makes matching non-total in a way nothing else in this engine is — every other construct's validity is fully known at compile time, and match failures are only ever "input didn't match," never "pattern itself turned out to be unsupported here." Introducing a runtime-detected-ambiguity failure mode breaks that guarantee for a single construct type.
- **Decision**: rejected all three in favor of the precise `firstCharSet()`-based entry set (see "Backreferences" above), which is strictly more permissive than (A), doesn't require documenting (B)'s surprising priority rule since real disjointness is checked instead, and keeps ambiguity detection fully at compile time unlike (C).
