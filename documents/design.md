# Design

## Pipeline

`String pattern` → **`PatternParser`** (recursive descent) → **`PatternConstruct` AST** → **compile step** → **`MatcherConstruct` graph** → **`Matcher`** walks the graph against input, one code point at a time, with no backtracking.

### Package layout

Only the public API lives in `com.tbohne.llkpattern`: `Ll1Pattern`, `Matcher`, `PatternSyntaxException`. Everything else is under `com.tbohne.llkpattern.impl` and is not API (its members are `public` only so the layers can call each other): `impl.unicode` (the `CodePointSet` classes, `NamedCharClass`, `UnicodePredicates`, `CaseFolding`, `GraphemeCluster`; imports nothing from the other packages) <- `impl.constructs` <- `impl.parser` <- `Ll1Pattern`/`Matcher`. `CaseFolding.isUnicodeCase` reads `java.util.regex.Pattern`'s flag constants (which `Ll1Pattern`'s alias) so `impl.unicode` needs no upward dependency.

### Parsing (`PatternParser` / `PatternConstruct`)

- The parser lives in `com.tbohne.llkpattern.impl.parser` as a three-class chain, one object per compile: `PatternLexer` (cursor: `pattern`, `flags`, `index`, `peek`, `COMMENTS` skipping, single-character escapes incl. `\N{name}`, error helpers) <- `CharClassParser` (bracket expressions, `\d`/`\p{...}` escapes, `.`; `CASE_INSENSITIVE` folding of literal members) <- `PatternParser` (the only public one: unions, sequences, groups, lookbehind, boundaries, backreferences, quantifiers). Methods that cross a class boundary are package-private and `final`; no interfaces or composed sub-parsers, so the hot `peek`/`advance` calls stay direct. Stateless helpers live in `PatternText`, `InlineFlags` and `CharacterNames`.
- Grammar is documented as regex-flavored BNF in comments at the top of `PatternParser.java`. It supports much of `java.util.regex.Pattern`'s syntax: groups (capturing, named, non-capturing), alternation, quantifiers (`?`, `*`, `+`, `{n,m}`, and their reluctant/possessive forms — possessive is accepted and treated as a no-op, since this engine's no-backtracking greedy loop already behaves as possessive; reluctant is honored, see "Quantifier/loop compilation" below), character classes (including nested `&&` intersection and `^` negation), escapes, boundaries (`\b`, `\B`, `\A`, `\G`, `\Z`, `\z`), and Unicode property/script/block/category classes (`\p{...}`).
- **The single-pass architecture, and what it rules out.** Matching never looks at the input string as a whole: it revolves entirely around a *position* between two code points, advanced by `Matcher#peek()` (the code point about to be consumed) and inspected one code point backward by `Matcher#peekPrevious()` (used by `\b`/`\B`, see "Boundary matching" below) — never more than one code point in either direction, never speculatively. This is what guarantees linear-time matching, and it's also the reason for several of this engine's intentional divergences from `java.util.regex` (see README's "Intentional differences" list for the full, corpus-checked catalogue):
  - **Every union branch and every loop's body-vs-exit choice must claim a distinct "next" code point** (`.` aside, which is defined as "whatever a sibling branch doesn't claim" specifically so it can coexist with one) — this is the compile-time disjointness check described below, and it's the direct consequence of a `Matcher` that can only ever look at *one* upcoming code point to decide which branch it's in, never several code points ahead.
  - **Positive lookahead (`(?=...)`) is rejected** as a direct side effect of that same constraint: a lookahead's body can match input of unknown, even variable, length before the engine would know whether it succeeded, which is exactly the "look arbitrarily far ahead before committing to a branch" the distinct-next-code-point rule exists to rule out.
  - **General lookbehind (`(?<=...)`/`(?<!...)`) is rejected**, except for a lookbehind whose body matches exactly one code point (`(?<=x)`/`(?<!x)`, a single character or character class or an alternation of such, optionally wrapped in one capturing group) — supported, via a direct generalization of the one-code-point-backward check `\b`/`\B` already perform via `peekPrevious()` (see "Boundary matching"'s own "Lookbehind" subsection below), requiring no new architectural capability. A lookbehind of more than one code point would need to look arbitrarily far backward, which `peekPrevious()`'s single-code-point contract doesn't support and isn't planned to be extended to, for the same "would require exploring several possible interpretations rather than reading one committed position" reason lookahead is rejected.
  - **A multi-code-point loop body that matches part of itself and then fails is not retried with fewer iterations** (e.g. `(ab)+` finds nothing in `"abac"`) — there is no way to un-consume input already read once the position has advanced past it, for the same reason a general lookahead/lookbehind can't be supported.
  - Rejecting lookahead and general (more-than-one-code-point) lookbehind is a permanent characteristic of this design, not a "not yet implemented" gap: supporting them in general would mean exploring a branch's possible outcome before committing to it, which is materially the same problem backtracking solves, and reintroducing it here would give up the single-pass guarantee this whole engine exists for.
- Output is a `PatternConstruct` AST: `QuantifiedUnionPatternConstruct` (alternation + optional quantifier + optional capture), `SequencePatternConstruct`, `LiteralPatternConstruct`, `ComplexCharacterPatternConstruct` (a character class as a `CodePointSet`), `ComplexQuantifiedCharacterPatternConstruct`, `BoundaryPatternConstruct` (`\A`, `\Z`, `\z`), `LineBoundaryPatternConstruct` (`^`, `$`), `WordBoundaryPatternConstruct` (`\b`, `\B`) — the latter two split out separately, see "Boundary matching" below — `BackReferencePatternConstruct`, `EndPatternConstruct`. `\G` produces no AST node at all — see "Boundary matching".

### Compilation (AST → matcher graph)

- Each `PatternConstruct` compiles itself plus its "what comes next" continuation into one or more `MatcherConstruct` nodes. This is the LL(1)-flavored core of the design: instead of a generic NFA, each construct's `buildEntryMap` computes the set of code points that count as *this construct's own* entry point — represented as a plain `CodePointSet` ("entryMap") plus a catch-all `entryElse`. It's a set, not a "code point -> owning construct" map, because every `entryMap` is built by exactly one construct for itself (never aliased from another), so "who owns this range" is always already known from context — every consumer either already has that construct in hand, or (when merging multiple candidates' entry points — see `mergeEntryPoints` below) unions each candidate's own entry set directly, by pulling, with no per-candidate identity tagging needed at all.
- The critical invariant the compiler must enforce: for any `QuantifiedUnionPatternConstruct` (i.e. any `|` alternation, and any quantified construct's "keep looping vs. exit the loop" choice), the entry ranges of its branches must be pairwise disjoint. If two branches could both match the same next code point, that's a compile-time `PatternSyntaxException` (ambiguous branch), not a runtime backtrack. `PatternConstruct.mergeEntryPoints` (used by both plain alternation and a quantified construct's own entry point) computes each candidate's own entry ranges; `PatternConstruct.checkDisjoint` (called both from `buildFlattenedChain`, for a plain union's own dispatch, and directly from `QuantifiablePatternConstruct.buildLoopMatcher`, for the loop-body-vs-`next` case) rejects the first pair of candidates whose entry ranges overlap with a `PatternSyntaxException` naming the candidate index and the conflicting characters — a plain pairwise `CodePointSet#intersects` scan, no map/allocation needed to find the conflict itself. For a GREEDY loop's own body-vs-`next` check specifically, `PatternConstruct.skipZeroWidthEntrySet`'s `checkAssertions` mode additionally treats a `\b`/`\B`/`MULTILINE ^`/`MULTILINE $` sitting between the loop and a pure-end tail as its own source of ambiguity, not just a pass-through — see "Boundary matching" below for why plain see-through of the assertion's own entry point (which is what ordinary union dispatch uses) is unsound there specifically, and for `admittedInteriorExitPeekSet`'s role in computing what to check it against. Possessive and reluctant loops are exempt from this specific check (possessive already agrees with `java.util.regex`'s own non-backtracking possessive; a reluctant loop's early exit is instead proven safe at MATCH time — see point 4 of "Quantifier/loop compilation" below).
- **Quantifier/loop compilation**: a quantified construct (`QuantifiedUnionPatternConstruct` or `ComplexQuantifiedCharacterPatternConstruct` with `min != 1 || max != 1`) compiles to a small graph, built by `QuantifiablePatternConstruct.buildLoopMatcher`:
  1. **The body's own dispatch chain** — one node per body part, each part's own compiled `MatcherConstruct` given an `entrySet`/`failedEntry` pair (see "Opcode set" below) rather than a separate wrapping node: on a membership miss, a part defers to the next part in priority order, and the last part defers to the loop's own exit node (below). This chain's head does DOUBLE DUTY as both the loop's externally-visible entry point (`owner.matcher`) and the loop-back target reached after a completed iteration — there is no separate entry-only chain the way an N-way dispatch table (or the old fork-chain design — see "Alternatives Considered") would need one: a fresh entry (zero iterations so far) and a re-check after some iterations both just mean "try the body head again," and the body's own `failedEntry` chain already correctly falls through to the exit node in either case — including the `min == 0` "skip the loop entirely" case, which needs no special-casing at all here (the exit node's own `min` check, not any entry-time logic, is what actually allows it — see point 3).
  2. **`LoopMatcherConstruct`** (used for greedy loops, AND for a reluctant loop where `exitAssertionChain` is null — see point 4 for the reluctant-safe counterpart, used instead, never both), self-registered onto a throwaway `LoopBackPatternConstruct` (not `owner`) *before* the body compiles against that marker, breaking the construction-time cycle every loop body creates (the body's own compiled matcher loops back to this node). Reached only as the body chain's own successor once an iteration finishes — never as the loop's entry point (that's the body chain's head, above) — so `match()` unconditionally counts one more completed iteration, then dispatches back to the body chain's head (another attempt) if under `max`, or straight to the exit node (forcing a stop) otherwise. It does no code-point membership test of its own at all; that decision now lives entirely in the body chain's own `entrySet` checks.
  3. **`LoopExitMatcherConstruct`** — this loop's "stop iterating" node, reached either because the body chain naturally didn't match (any position, first attempt or re-check alike) or because whichever of point 2/4 owns this loop forced a stop at `max`. Enforces `min` (failing the whole match if too few iterations happened) and, on success, resets the shared iteration counter before dispatching to `next`'s own matcher. Never itself gated by an `entrySet` — every code-point decision that used to live in a combined loop/exit dispatch lives entirely in the body chain now. For a reluctant-safe loop (point 4), this `min` is pre-shifted by the same "+1" point 4 uses, to stay consistent with that loop's own shifted counter convention — but the node also separately records whether the loop's TRUE `min` is `0` (`minIsZero`), since `exitAssertionChain` (below) needs to ask about the real quantifier semantics regardless of which counting convention this exit's owning loop happens to use.
  4. **`ReluctantLoopMatcherConstruct`** (REPLACES `LoopMatcherConstruct` — never both — only for a reluctant construct, e.g. `a+?`, AND only when `MatcherConstruct.exitAssertionChain(next.matcher)` returns non-null — see below) merges point 2's role with the reluctant "prefer to stop" decision into one node, used in BOTH roles the body chain's head plays for a greedy loop: the loop's own externally-visible entry point, and the "continue" target reached after each completed iteration. Merging these roles (rather than a separate node wrapping the body chain's head — see "Alternatives Considered") is what lets a single node handle both "should I even attempt the very first iteration" (needed for `min == 0` loops like `a*?`/`a??`, which must be able to skip the body entirely before ever trying it) and "should I attempt another one" with one hop instead of two. Since this node is now reached BOTH before any iteration and after each completed one, its own slot in `quantifiableCounts` no longer counts completed iterations directly — every visit increments it unconditionally, so the stored value is always `completedIterations + 1`; `min`/`max` are compared as `min + 1`/`max + 1` (capped, not wrapped, for an unbounded `max`) to correct for that shift, which is also why `LoopExitMatcherConstruct`'s own `min` (point 3) has to agree on the same shifted convention when reached directly via the body's own `failedEntry` (bypassing this node entirely). At match time, once `min` is satisfied, it prefers to stop rather than attempt another iteration — exactly the "reluctant" half of greedy/reluctant that a no-backtracking design can still express without ever needing to un-consume anything: unlike a backtracking engine's reluctant loop (try the shorter match, undo and retry longer if something downstream rejects it), this only ever takes the exit path once taking it is already known to succeed, so none of `LoopExitMatcherConstruct`'s side effects (resetting the counter, ending an enclosing capture) are ever undone. Whether it's safe to try the exit path at all is mostly a *compile-time* property of `next.matcher`'s own structure (computed once, by `exitAssertionChain`, when deciding whether to build this node at all instead of a plain `LoopMatcherConstruct`), plus — when that path runs through one or more zero-width assertions — a cheap match-time re-check of those specific assertions; whether the path actually *succeeds* right now also depends on `Matcher#requireFullMatch`, read at match time since one compiled pattern serves `matches()`, `find()`, and `lookingAt()` alike:
     - `exitAssertionChain(node)` (generalizing an earlier `exitIsPureEnd` boolean) conservatively asks: does `node` reach `EndMatcherConstruct`, possibly via a chain of `\b`/`\B`/`^`/`$` assertions, along a path that, for any code point that could still be pending in *this* loop's own body (which — by `checkDisjoint`'s own guarantee, the same disjointness check every loop body already goes through — `node`'s own `entrySet`, and every `entrySet` reachable by cascading through its `failedEntry` chain, is guaranteed to miss), never fails to eventually reach `End`? It recurses through `EndCaptureMatcherConstruct`/`PassThroughMatcherConstruct`'s own `next`, through a gated node's `failedEntry` (safe precisely because of that disjointness guarantee — see above), through another loop's own `LoopExitMatcherConstruct` only when its `minIsZero` (a guaranteed no-op skip — see point 3 above for why this reads `minIsZero` rather than comparing `min` directly), through another loop's own `ReluctantLoopMatcherConstruct` via its `exitNode` unconditionally (sound because that node's own dispatch, whichever branch it takes at match time, always either succeeds directly or itself cascades to the very same `exitNode`, by the same inductive argument), and — the new part — through a `WordBoundaryMatcherConstruct`/`LineBoundaryMatcherConstruct` node, appending it to the returned list and continuing into its own `next`. It returns the (possibly empty) list for `EndMatcherConstruct` itself, and `null` (conservatively) for anything else it doesn't recognize — a lookaround, `\A`/`\z`/`\Z` (not analyzed for this yet — see remaining_work.md), or another loop that isn't a provable no-op — leaving that shape greedy (this engine's existing default) rather than trying to reason further.
     - At match time, `matchBody` takes the exit once the shifted `quantifiableCounts[idx] >= min + 1` AND (`!requireFullMatch`, i.e. `find()`/`lookingAt()`, where `EndMatcherConstruct` succeeds unconditionally) OR (`requireFullMatch` AND `pos == regionEnd` already) AND every guard in the assertion chain (if any) independently `holdsHere` — a side-effect-free, `peek`/`peekPrevious`-based re-derivation of each assertion's own `matchBody` logic (see `MatcherConstruct.ZeroWidthAssertionGuard`), evaluated BEFORE committing to `exitNode`, never speculatively (design.md's "Speculative reluctant-loop exit with rollback" alternative, below, explains why check-then-commit is safe here where a genuinely speculative try/roll-back wouldn't be). The `requireFullMatch` clause is what also fixes `Matcher#hitEnd` under `matches()`: without it, this node would still hand off to the body one more (necessarily doomed, since nothing's left to consume) time, which peeks past the end and spuriously sets `hitEnd`, exactly like a greedy loop's own final failed continuation attempt does — but a reluctant loop that's already exactly at `regionEnd` has no reason to make that attempt at all.
     - This only changes anything for a reluctant loop whose own body/next disjointness already leaves room for a real choice — which, per the constraint at the top of this section, is exactly the loops where `next`'s own resolution isn't already forced. A reluctant loop immediately followed by something that forces a specific next code point (`a+?b`) never reaches this node's "prefer to stop" branch with any effect, since the body's own entry gate (not this node) already forces the correct iteration count regardless of greedy/reluctant.

  Under `CASE_INSENSITIVE`, a body part's `entrySet` has any same-flags folding baked in at compile time (`MatcherConstruct#foldedEntrySet`, i.e. folded at the leaves: a literal's or backreference's entry set via `CaseFolding#expand`, a bracket class's at parse time, a named class's never, as in the JDK), keeping the match-time check a single plain, unfolded `contains` — see "Opcode set" below. `checkDisjoint` compares these already-folded sets, so a fold overlap between chain candidates (e.g. `(?i:[a-z]+)X`, `(?i:a|A)`) is a compile-time ambiguity like any other overlap, never resolved by chain priority; the only catch-all candidate is a `.`-style wildcard.
- **Capturing groups**: a capturing, unquantified `QuantifiedUnionPatternConstruct` (`captureConstructIndex != -1`) wraps its compiled alternation-dispatch node in a `BeginCaptureMatcherConstruct` (which becomes `owner.matcher`, recording the start position), and compiles its branches against a `CaptureEndPatternConstruct` — a zero-width synthetic `PatternConstruct` standing in for the real `next` — whose own matcher is an `EndCaptureMatcherConstruct` (records the substring, then forwards unconditionally to the real `next`). Capture storage (`Matcher#captureGroups`) is a flat array indexed by a fixed `captureConstructIndex` known to both `BeginCapture` and `EndCapture` (not a stack — this engine has no recursion, so the same capture construct can never be open twice at once, and re-entering it naturally overwrites the previous `Group` — exactly regex's "last iteration wins" semantics — for free; this is exactly what the capturing-and-quantified case below relies on).
- **Capturing AND quantified at once** (e.g. `(a)*`): `buildLoopMatcher` takes a `captureConstructIndex` (`-1` when not capturing). The capture must re-fire every iteration, identically whether this is the very first attempt or a later re-check — but the `BeginCaptureMatcherConstruct` recording it must run strictly AFTER a body part's own `entrySet` gate passes, not before: a single shared `BeginCaptureMatcherConstruct` wrapping the whole body chain's head would record a capture start even on a `min == 0` loop's very first, ultimately-zero-iteration attempt, since it would run unconditionally before the body's own gate got a say. So each body part instead gets its own throwaway `LoopBodyPartGatePatternConstruct` carrying that part's `entrySet`/`failedEntry`, with a `BeginCaptureMatcherConstruct` wrapped INSIDE it (compiled ungated, since gating already happened by the time it runs) — the gate is checked, then the capture fires, then the part's own real content runs. Ambiguity detection is unaffected — it runs identically whether or not the loop is capturing, since capturing only changes what happens once a branch is chosen, not which branch gets chosen.
- `MatcherConstruct` subclasses (one class per file in the `impl.constructs` package, next to `MatcherConstruct.java`) are the compiled, executable nodes — see "Opcode set" below for the full set. Every node carries an optional `entrySet`/`failedEntry` pair, checked before its own `matchBody(Matcher, int peeked)` runs: on a miss, dispatch defers to `failedEntry` instead (or fails outright if there isn't one); on a pass (or no `entrySet` at all — the common case), `matchBody` runs and consumes zero or more code points before advancing to its successor(s).
- Matching is therefore just: start at the compiled root node, and recursively call `match()`. No backtracking stack is needed because ambiguity was already ruled out at compile time.

#### The `compile()` algorithm and cycle handling

`MatcherConstruct` instances are deeply immutable once built — every field on every `MatcherConstruct` is genuinely `final` (see "Opcode set" below for why that's still possible even with a genuine construction-time cycle, in particular for `LoopMatcherConstruct`). But the matcher graph *does* have cycles (a loop's body eventually dispatches back to the loop's own entry `MatcherConstruct`), so something has to break the cycle during construction without the constructed node ever seeing a half-built dependency:

- Every `PatternConstruct` has a `@MonotonicNonNull MatcherConstruct matcher` field. `PatternConstruct.compile()`'s contract: if `matcher` is already non-null, return it immediately — don't rebuild. Otherwise, build `entryMap` and then construct the one `MatcherConstruct` this node compiles to.
- The key trick is in the `MatcherConstruct` subclass constructors, not in `compile()`: a `MatcherConstruct` constructor must, as its *very first* action, assign `this` to its owning `PatternConstruct`'s `matcher` field — *before* it does anything else, including looking up or compiling any of its own dependencies (e.g. what a loop dispatches back to, or what a union's branches dispatch to). Only after that assignment does the constructor walk the `PatternConstruct` graph (via each dependency's own `compile()`) to resolve the `MatcherConstruct`s it needs for its `dispatchMap`/`exitMap`, and accumulate those into its own dispatch map.
- This ordering is what makes cycles safe without any visited-set/recursion-guard bookkeeping: if compiling node A transitively needs to compile node B which loops back and needs A again, that second `compile()` call on A sees `matcher` already set (to the in-progress `A` instance) and returns it immediately, rather than recursing infinitely. The returned reference is to a real, fully-constructed-by-the-time-anyone-uses-it object — it's *only* used as a dispatch-map value (a reference to jump to), never dereferenced by the constructor that's still running, so returning a self-reference mid-construction is safe even though the object's own fields (its dispatch map) aren't filled in yet at the moment it's handed out.
- Compiling tail-to-front (i.e. `compile()` is always called with "what comes next" already known/passed in, starting from `EndPatternConstruct` and working backwards through the pattern) makes cycles rare in practice, even though the mechanism above handles them regardless.
- The constructor navigates via a reference to its owning `PatternConstruct`, not via extra constructor arguments per dependency: `PatternConstruct` has a `next` field (recorded in `compile()`); for an *acyclic* dependency, everything a `MatcherConstruct` constructor needs is already reachable off `owner` by direct field read (`owner.next.matcher`, or `owner.entryMap`'s `PatternConstruct` values' own `.matcher` fields) — no `.compile()` call needed. Loop compilation is the one case that genuinely needs the self-registration-then-*recurse* pattern (not just self-registration-then-read): `QuantifiablePatternConstruct.buildLoopMatcher` builds a `LoopBackPatternConstruct` and self-registers a `LoopMatcherConstruct` onto it *first*, then calls `part.compile(marker)` for each body part — safe, since a nested attempt by the body to read `marker.matcher` again finds the (still-being-built) `LoopMatcherConstruct` instance already there instead of recursing. The marker's own entry point (queried by a nullable construct nested in the body that needs to look past itself at "what comes next" — see below) delegates straight through to `owner`'s, since semantically "what follows a loop body" is the loop itself.

##### Entry-point computation vs. matcher compilation

A `PatternConstruct`'s `entryMap`/`entryElse` (its own advertised "what character(s) can follow me") and its `matcher` (the compiled `MatcherConstruct` graph) are two separate, independently-lazy computations, each memoized and cycle-guarded on its own:

- `getEntryPointMap()`/`getEntryElse()` are the only way anything reads another construct's entry set (never the raw `entryMap`/`entryElse` fields directly). The first call lazily invokes `buildEntryMap(next)`, guarded by a three-state flag (not started / constructing / constructed) on the construct itself: a re-entrant call made *while that same construct's own `buildEntryMap` is still running* throws (see below) instead of silently reading a half-built map or recursing forever. A call arriving after that construct has already finished (a completely ordinary case, not a re-entrant one) just returns the cached result.
- Critically, this guard is scoped to *entry-point construction specifically* -- not to matcher compilation, and not to "is this construct anywhere on the current call stack for any reason." A construct's `matcher` can be (and, for a loop's entry/re-entry node, always is) self-registered and sitting mid-construction while something else asks for that same construct's entry point for the first time; that's not re-entrance, it's simply the first, on-demand request, and it's resolved immediately by delegating structurally to whatever sub-part actually determines it.
- Because of that, `buildEntryMap` for `SequencePatternConstruct` and for a quantified construct (`QuantifiablePatternConstruct.buildLoopEntryMap`) must never trigger anything's full `compile()`/`buildMatcher()` -- only entry-point getters, plus a cheap, direct assignment of each relevant sub-part's `next` field (bypassing `compile()` entirely) so a nullable sub-part can still fold in what follows it. `SequencePatternConstruct`'s own entry set is always exactly its *first* element's (entering the sequence means entering its first element); the tail-to-front `compile()` calls that actually wire up the matcher graph happen separately, in `buildMatcher()`. A quantified construct's own entry set is `FIRST(body)` (the union of its body parts' entry points, each body part's `next` pointed at `loopBodyTarget()` -- a `LoopBackPatternConstruct`, wrapped in a `CaptureEndPatternConstruct` when the loop itself captures -- rather than the construct itself; see the identity-sharing rule below for why) unioned with `next`'s own entry set when `min == 0` (skipping the construct entirely is valid) -- computed once, in `buildEntryMap`, well before `buildMatcher()` builds the real dispatch graph (which still needs the full body-plus-`next` candidate merge, since "continue vs. exit" routing is a different, larger question than "what's my own advertised entry set").
- This split is what makes a loop nested inside another loop's body resolve correctly: the nested loop's own dispatch construction needs the *outer* loop's entry set (since exiting the nested loop routes to the outer loop), and asking for it via `getEntryPointMap()` triggers the outer loop's cheap, structural `FIRST(body)` computation on the spot if nobody's asked yet -- which typically bottoms out immediately (e.g. in `(a(b)?)+`, the literal `a` pins the outer loop's entry set without ever needing to touch the inner `(b)?` loop at all). The one case that's a genuine, unbreakable cycle is a loop whose entire body can match zero characters (e.g. `(a?)+`): computing the loop's own entry set then requires its own not-yet-available entry set, and the guard converts that into a `PatternSyntaxException` naming the loop's start index, rather than a stack overflow or a silently wrong dispatch -- consistent with this engine's "unsatisfiable/indeterminate at compile time is an error, not a silent failure" philosophy elsewhere (see "Boundary matching" above). Note this is also just an infinite-loop hazard in its own right (a loop that can advance zero characters per iteration), so rejecting it at compile time isn't purely an artifact of the implementation technique.
- **Identity-sharing rule**: whenever a downstream construct bakes a `next` reference into a *fixed field* rather than re-reading it later -- the one example today is `CaptureEndPatternConstruct.realNext`, set once from `buildEntryMap`'s `next` argument and never revisited (`compile()` memoizes on `matcher != null`, so a later `buildEntryMap` re-run never happens even if a fresh `next` value is passed to a subsequent `compile()` call) -- then whatever object is used as `next` during entry-point computation MUST be the exact same object later reused as `next` during matcher compilation, not merely one that resolves to an equal *value*. `buildLoopMatcher` used to violate this by pointing a capturing loop's body parts at `this` (the loop construct) during `buildEntryMap`, then at a freshly-`new`-built `LoopBackPatternConstruct`/`CaptureEndPatternConstruct` pair during `buildMatcher` -- a nested capturing body part's own `CaptureEndPatternConstruct` (built once, during entry-point computation, from whichever object was `next` *then*) ended up permanently pointed at `this`, whose `.matcher` isn't set until the whole loop finishes compiling, throwing a `NullPointerException` the first time that marker's `buildMatcher()` ran (`((x))*`, `(?:(x))*`; see notes.md's 2026-09-21 entry). The fix -- `QuantifiablePatternConstruct.loopBodyTarget()` -- is the general pattern: memoize the marker(s) as a field, computed once and reused identically by both `buildLoopEntryMap` and `buildLoopMatcher`, rather than constructing a fresh one in each. Any future change to what a loop (or similar identity-baking construct) points its parts' `next` at should re-check this specifically, not just "does the entry set still compute the right *characters*."

##### `entryMap` aliasing (avoiding a copy per AST level)

`entryMap` is `CodePointSet`, not `MutableCodePointSet` -- most `buildEntryMap()` overrides never build a new map at all, they just **alias** another construct's already-built one:

- A construct whose own entry point is defined to be exactly some other construct's -- `SequencePatternConstruct` (its first element's), `CaptureEndPatternConstruct` (`realNext`'s), a bare-flags-only `QuantifiedUnionPatternConstruct` (`next`'s), `BackReferencePatternConstruct` (the referenced group's `firstCharSet()`), `ComplexCharacterPatternConstruct`/`ComplexQuantifiedCharacterPatternConstruct` (their own/their delegate's `validRanges()`) -- just assigns `entryMap = source.getEntryPointMap()` (or the equivalent already-in-hand map), a plain reference copy.
- This is safe specifically *because* `entryMap`'s value is always Boolean `true`, carrying zero information (see the field's own doc): two different constructs' entry-point maps holding the exact same object is indistinguishable, from every consumer's perspective, from holding two separately-built maps with identical content. Nothing mutates `entryMap` after `buildEntryMap()` returns (every other reader goes through `getEntryPointMap()`/`getEntryElse()`), so a shared reference can't be corrupted by one holder's later writes.
- The one place a genuinely `PatternConstruct`-valued map must NOT leak out as `entryMap`: `mergeEntryPoints`'s own internal merge (built purely to run the ambiguity check with a useful "candidate #N" error message) is real, multi-valued, and would corrupt downstream identity checks like a loop's continue-vs-exit classification (`e.getValue() == next`) if exposed directly -- doing so once caused a real bug (see notes.md's 2026-09-06 `CaptureEndPatternConstruct` entry). `mergeEntryPoints` itself now projects that transient merge down to a genuinely new Boolean-valued map exactly once (`MergedEntries.ranges`), before it's ever handed back to any caller -- so every caller (`QuantifiedUnionPatternConstruct.buildEntryMap`, `QuantifiablePatternConstruct.buildLoopEntryMap`) can just alias `result.ranges` straight into `entryMap`, with no per-caller re-projection and no risk of ever aliasing the raw, PatternConstruct-valued merge by mistake.
- `LiteralPatternConstruct` is the only true leaf (nothing to alias) -- if its `entryMap` is ever actually pulled (see `getEntryPointMap()`), building it is unavoidably a freshly-built single-entry map. Whether that pull ever happens for a given `LiteralPatternConstruct` depends on `needsEntryPointBeforeMatcher()` below.

##### `mergeEntryPoints`: merging by pulling, not tagging

Merging several candidates' entry points (a union's branches, a loop's body parts plus its own `next`) unions each candidate's own `getEntryPointMap()` straight into a fresh `ArrayCodePointSet` via `insertAll` -- one plain call per candidate, no per-candidate identity tagging. This forces every candidate's `entryMap` to materialize (each pull goes through the ordinary cached, cycle-guarded `getEntryPointMap()`, so a quantified construct's own body pointing `next` back at itself for a nullable loop, e.g. `(a?)+`, is still caught by that pull path's three-state guard and converted into a `PatternSyntaxException` rather than infinite recursion). `mergeEntryPoints` doesn't check disjointness itself -- that's matcher-build time's job (`checkDisjoint`, run from `buildForkChainInternal` against real `MatcherConstruct`s, and directly from `validateDisjointness` for the loop-body-vs-`next` runtime-dispatch case), since it's a plain `CodePointSet#intersection` scan against real matchers, not something merging entry points needs to compute itself. `claimsEntryElse()` exists as a separate method from `getEntryElse() != null` purely to give `mergeEntryPoints` a clean loop body over `candidates.size() > 1`.

##### `needsEntryPointBeforeMatcher()`: not pulling what nothing needs

`compile()` itself calls `ensureEntryPointBuilt()` unconditionally before `buildMatcher()` for every construct -- required in general, since e.g. `QuantifiedUnionPatternConstruct.buildMatcher`'s unquantified-with-branches case reads `compileTarget`/`rawEntryElse`, fields only `buildEntryMap()` populates. But for a construct whose `buildMatcher()` reads nothing `buildEntryMap()` sets, that call is pure waste whenever nothing else ever pulls this construct's entry point either -- exactly the case of a leaf/alias reached only as a merge candidate. `needsEntryPointBeforeMatcher()` (default `true`) lets such a construct opt out, so `compile()` skips `ensureEntryPointBuilt()` entirely: `LiteralPatternConstruct`, `ComplexCharacterPatternConstruct` (true leaves, whose matchers are built entirely from their own constructor-supplied data), `CaptureEndPatternConstruct` (`buildMatcher()` reads only `realNext.matcher`), and `SequencePatternConstruct` (`buildMatcher()` does its own independent tail-to-front `next` wiring via each part's own `compile()` call, never touching `entryMap`/`entryElse`).

This matters in practice because every union/loop branch that's a bare literal or character class is actually parsed as a one-element `SequencePatternConstruct` wrapping it, not the leaf directly -- so `SequencePatternConstruct` needed the same opt-out as its leaf children for the win to reach real patterns; skipping it only on `LiteralPatternConstruct` itself was measured to change nothing; skipping it (also) on `SequencePatternConstruct` dropped `CorpusBenchmark.llkCompile`'s `gc.alloc.rate.norm` by 28% (4,958,552 → 3,566,024 B/op) and its time by 18% (1.872 → 1.534 ms/op). A construct left un-pulled after `compile()` isn't stuck: its `entryPointState` simply stays `ENTRY_POINT_NOT_STARTED`, and a later, genuine pull (an ancestor's `getEntryPointMap()`) computes it fresh at that point -- `compile()` already unconditionally sets `this.next` before checking this flag, so nothing that `buildEntryMap()` would need is missing when that eventually happens.

The quantified-loop case (`QuantifiedUnionPatternConstruct`/`ComplexQuantifiedCharacterPatternConstruct` with `min`/`max` making it a real loop) and the unquantified-with-branches union case both still need the pull, since both `buildMatcher()`s read fields only `buildEntryMap()` populates: the former's `buildLoopMatcher` reads `rawEntryElse` directly (to build `owner`'s own entry fork chain, once every body candidate is compiled), and the latter reads `compileTarget`/`rawEntryElse`.

##### `LoopFirstEntryMatcherConstruct`: skipping a re-check the caller already made

A greedy loop's first body node normally re-checks an entry set its caller may already have verified. `LoopFirstEntryMatcherConstruct` skips that re-check, but only when the two checks are provably identical: a single-alternative, non-capturing body with `min >= 1` (`QuantifiablePatternConstruct.buildLoopMatcher`). The gain is a small dispatch-cost reduction, with no statistically significant ms/pass change on either device.

It is deliberately not generalized:
- **Multi-alternative body (`(a|b)+`):** each branch's own check is still needed to pick the right branch.
- **`min == 0` loop (`a*`):** the loop's exposed entry set folds in `next`'s, so it is broader than any single branch's and passing the outer check doesn't imply passing the inner one.
- **Capturing single-alternative loop (`(a)+`):** skipping the check would let a capture start be recorded on unverified input for an ungated top-level loop, the same shape of bug the project already hit once (a capture start recorded on a `min == 0` loop's very first attempt).

##### Opcode set

The matcher graph is a small "opcode" virtual machine. Every `MatcherConstruct` carries an optional `final @Nullable CodePointSet entrySet`/`final @Nullable MatcherConstruct failedEntry` pair (both usually `null`), checked by a single, non-overridable `match(Matcher, int peeked)` template method BEFORE a node's own `matchBody(Matcher, int peeked)` runs: a plain (unfolded), `-1`-guarded `entrySet.contains(peeked)` check, deferring to `failedEntry.match(...)` on a miss (or failing outright if `failedEntry` is `null`). `entrySet`/`failedEntry` are populated via the OWNING `PatternConstruct`'s own `dispatchEntrySet`/`dispatchFailedEntry` fields (read by `MatcherConstruct`'s owner-based constructor), set by a chain builder just before that construct's first `compile()` call — this is what lets ANY existing node type become a chain candidate with no constructor changes of its own, and is the mechanism that replaced a separate `ForkingMatcherConstruct` node wrapping each candidate (see "Alternatives Considered"):

- **`SingleDispatchingMatcherConstruct`** (abstract, holds `final MatcherConstruct next`, called via a plain virtual `next.match(...)`): the base for every node whose successor is fixed at construction time and never depends on which character was seen. Subclasses: `SingleCharMatcherConstruct` (character-class membership test via its own `validRanges`, folded at match time — distinct from any `entrySet` gating that might additionally wrap it as a chain candidate), `LiteralMatcherConstruct`, `BeginCaptureMatcherConstruct`, `EndCaptureMatcherConstruct`, `WordBoundaryMatcherConstruct`, `BackReferenceMatcherConstruct`/`BoundaryMatcherConstruct`, and `PassThroughMatcherConstruct` (a zero-width forwarder — see below). `next` is safe to be `final` here because none of these nodes are ever the self-referential node in a cycle — that role belongs exclusively to a loop's own `LoopMatcherConstruct` (below).
- **Chain building** (`PatternConstruct.buildFlattenedChain`, for a plain union's own dispatch; `QuantifiablePatternConstruct.buildLoopMatcher`'s own body-part loop, for a loop's) compiles candidates tail-to-front, giving each one's OWN compiled node the next candidate's already-resolved matcher as its `dispatchFailedEntry` before compiling it — so a candidate's own node IS the fork, with no extra object allocated per candidate. A plain union's last candidate, when there's no catch-all branch, is left entirely ungated (no `entrySet` at all): its own compiled matcher already re-verifies membership as its own first action, so a redundant gate would only test something whose answer is already implied. A loop body part can never be left ungated this way, since it always has somewhere real to defer to (the loop's own exit node, below) — "doesn't match" is never simply "the whole match fails" the way it can be for a catch-all-less union's last branch.
- **`PassThroughMatcherConstruct`** (a `SingleDispatchingMatcherConstruct` with a no-op `matchBody`): needed anywhere a construct's own `buildMatcher()` would otherwise just alias `matcher = someOtherConstruct.matcher` (e.g. `SequencePatternConstruct`, a bare flags-only `QuantifiedUnionPatternConstruct`) AND that construct is itself gated as some OUTER chain's own candidate — `someOtherConstruct` may already be fully compiled (or gated for an unrelated, INNER reason), so the outer gating can't be retrofitted onto it after the fact and needs a node of its own instead. `MatcherConstruct.aliasOrPassThrough(owner, target)` picks the plain alias when `owner` has no gating of its own (the common case, no extra node) or wraps `target` in one of these when it does.
- **`LoopMatcherConstruct`** is reached only as a loop body's own continuation, once a body pass finishes (never as the loop's own entry point — see "Quantifier/loop compilation" above for why the body chain's own head serves that role too). It does no code-point membership test at all: `match()`'s `entrySet` is always `null` (it's reached only via `LoopBackPatternConstruct`'s own, ungated, dispatch fields), and its `matchBody` just counts one more completed iteration, then dispatches back to the body chain's head if under `max`, or to the loop's `LoopExitMatcherConstruct` otherwise. Kept as its own top-level class rather than participating in the ordinary chain mechanism, because its "continue" successor — the body chain's own head — genuinely isn't known until *after* it self-registers to break the construction-time cycle every loop body creates; rather than a mutable (or otherwise indirected) field on the node itself, it holds a `final PatternConstruct continuation` and reads `continuation.matcher` at match time — reusing `PatternConstruct.matcher`'s own already-mutable-once nature (the SAME mechanism the rest of this section's cycle-breaking discussion relies on) instead of inventing an equivalent one scoped to this class.
- **`LoopExitMatcherConstruct`** is a loop's "stop iterating" node — enforces `min`, resets the shared iteration counter on success, and dispatches to `next`'s own matcher. Never itself gated (`entrySet` always `null`); reached via `LoopMatcherConstruct`/`ReluctantLoopMatcherConstruct` (forced, at `max`) or via the body chain's own `failedEntry` fallthrough (a genuine non-match, at any iteration count). A separate `minIsZero` field records whether the loop's TRUE `min` is `0`, since `min` itself may already be pre-shifted by `ReluctantLoopMatcherConstruct`'s own "+1" convention (see "Quantifier/loop compilation" above).
- **`ReluctantLoopMatcherConstruct`** replaces `LoopMatcherConstruct` — never both — for a reluctant loop where `MatcherConstruct.exitAssertionChain` proves stopping early is safe (possibly modulo a match-time re-check of a `\b`/`\B`/`^`/`$` chain). Unlike `LoopMatcherConstruct`, it's reached both as the loop's own entry point (before any iteration) and as the body's post-iteration continuation, so its `quantifiableCounts` slot counts visits to itself rather than completed iterations, and its own `min`/`max` thresholds are the "+1"-shifted equivalents — see "Quantifier/loop compilation" above for the full mechanism.
- **`BeginCaptureMatcherConstruct`/`EndCaptureMatcherConstruct`** are pure single-successor opcodes, unrelated to looping, with the flat `captureGroups` array + fixed `captureConstructIndex` design described above (not a stack). The capturing-and-quantified case composes existing opcodes rather than giving `BeginCapture` a second, branching role — see "Alternatives Considered": each capturing loop body part gets its own `LoopBodyPartGatePatternConstruct` (carrying that part's `entrySet`/`failedEntry`) wrapping a `BeginCaptureMatcherConstruct` (single successor) → that part's own (ungated) compiled matcher → ... → `EndCaptureMatcherConstruct` → loops back to the `LoopBackPatternConstruct`.
- **`EndMatcherConstruct`** has no successor at all, so it extends neither base directly.

`SingleDispatchingMatcherConstruct.next.match(...)` is called as a plain virtual call — see "Alternatives Considered" for why a bound-`MethodHandle` form was tried and rejected.

#### Boundary matching (`BoundaryPatternConstruct`/`WordBoundaryPatternConstruct`/`LineBoundaryPatternConstruct`)

Unlike every other construct (essentially "a dispatch map keyed by the next code point"), a boundary depends on matcher *state* — position, surrounding characters — not just the upcoming code point. Two boundary types have grown a real implementation with their own logic distinct enough that each got pulled out of the original single `BoundaryPatternConstruct`/`BoundaryEnum`-keyed dispatch into its own `PatternConstruct`/`MatcherConstruct` pair: `\b`/`\B` (`WordBoundaryPatternConstruct`/`WordBoundaryMatcherConstruct`) and `^`/`$` (`LineBoundaryPatternConstruct`/`LineBoundaryMatcherConstruct`). `BoundaryPatternConstruct`/`BoundaryMatcherConstruct` now only cover `\A`, `\z`, and `\Z`.

Every zero-width assertion reports its own entry point as whatever can start what FOLLOWS it (`PatternConstruct.buildZeroWidthEntryMap`: `next`'s entry ranges, plus `next`'s catch-all only if `next` itself claims one, e.g. the end of the pattern). An assertion consumes nothing and can only NARROW when its branch succeeds, so `next`'s entry set is a sound (if not tight) gate -- and it means a union branch or loop part that OPENS with an assertion (`\b[ab]c`) is ambiguity-checked against its siblings by its real first characters, exactly like any other branch: `\b[ab]c|a` and `a*\b-|a` are rejected, like `a*-|a`. (These used to report a bare catch-all, `entryElse = this`, with no explicit ranges, and were dispatched as an ungated tail fallback that was never compared with its siblings -- unsound as soon as anything consuming follows the assertion: the sibling silently won.) That still isn't enough for a loop's own "continue vs. exit" ambiguity check specifically: a loop has already irreversibly consumed a code point once it decides to continue, so if a zero-width assertion sits between the loop and a later real character (e.g. `a*^a`), the coarse catch-all entry set hides the real question -- "does exiting the loop, through this assertion, eventually require the SAME code point the loop's own body would also accept?" `QuantifiablePatternConstruct.buildLoopMatcher`'s ambiguity check therefore uses `PatternConstruct.skipZeroWidthEntrySet` instead of the assertion's raw entry point when computing its own `next`-side comparison: a recursive walker (same shape as `firstCharSet`/`lastCharSet` below) that sees straight through a chain of zero-width assertions -- and through a `SequencePatternConstruct`'s first element or an unquantified `QuantifiedUnionPatternConstruct`'s own branches, so a boundary buried inside a nested group or alternation is still seen through -- to whatever construct actually determines which code points can follow. This is deliberately scoped to the loop-ambiguity call site only; ordinary union dispatch keeps the coarse catch-all treatment, which is still correct there.

That same walk still isn't the whole story for `\b`/`\B`/`MULTILINE ^`/`MULTILINE $` specifically: these four are POSITION-DEPENDENT (their own truth value depends on which character the loop body just consumed, not just on the upcoming one), so even the "what does the tail eventually require" question `skipZeroWidthEntrySet` answers by seeing straight through them can miss a real ambiguity when the tail beyond them is a catch-all pure end (e.g. `a+\B`: `\B`'s own entry point is a catch-all, and `End`'s is too, so plain see-through finds no overlap with the body's `{a}` -- yet `\B` genuinely CAN hold right after consuming an `'a'`, precisely when the next character is also `'a'`, since two word characters never differ in word-ness). `skipZeroWidthEntrySet`'s `checkAssertions` mode (used only for a plain GREEDY loop's own check -- never reluctant, whose early exit is instead proven safe/unsafe at MATCH time by `MatcherConstruct#exitAssertionChain`, and never possessive, which already agrees with `java.util.regex`'s own non-backtracking possessive) additionally unions in each assertion's own `admittedInteriorExitPeekSet(bodyLastCharSet, flags)` -- the set of peek code points at which that specific assertion, evaluated right after a body iteration whose last-consumed character is somewhere in `bodyLastCharSet` (the union of `PatternConstruct.lastCharSet()` over the loop's own body candidates, or `null` if not statically known -- the same safe "give up the enhancement" fallback `lastCharSet` itself uses elsewhere), could hold:

- **`WordBoundaryPatternConstruct.admittedInteriorExitPeekSet`**: classifies `bodyLastCharSet`'s own word-ness (word / non-word / mixed, via the same `classify` helper the compile-time `\b`/`\B` optimization above already uses) and returns the peek code points \b/\B could then admit -- the word set or its complement for a pure prior class, or every code point (`PatternConstruct.universalCodePointSet()`) for a mixed one (some prior character in it always matches whatever word-ness the peek has).
- **`LineBoundaryPatternConstruct.admittedInteriorExitPeekSet`** (consulted only under `MULTILINE`): `$` admits exactly the line-terminator-starting code points, unconditionally (its own truth doesn't depend on the prior character at all); `^` admits every code point (again via `universalCodePointSet()`) whenever `bodyLastCharSet` could itself be a line terminator, and none otherwise.

Both return `null` ("not statically known", same conservative fallback as everywhere else in this file) when `bodyLastCharSet` itself is `null`, so an unresolvable loop body just leaves the old, coarser see-through behavior in place rather than risking an over-eager rejection. `\A`/`\z`/`\Z` (`BoundaryPatternConstruct`) aren't given this treatment -- out of scope for now, see remaining_work.md.

`\G` is a different case entirely: per the project owner, it doesn't actually match any specific position in the input at all -- it's really just a flag meaning "anchor `find()` to exactly where the previous match ended, don't scan forward for a later one," and `Matcher#matchEnd` already tracks that position (for `group(0)`/`end()`). So `\G` gets no `PatternConstruct`/`MatcherConstruct` representation whatsoever: `PatternParser` recognizes it directly (not through the generic boundary-parsing path) and sets a `boolean anchorsToPreviousMatchEnd` flag, carried onto `Ll1Pattern`, consulted only by `Matcher#find(int)` -- when set, `find(int start)` tries `attemptMatch(start, false)` exactly once instead of scanning `[start, regionEnd]`. `matches()`/`lookingAt()` are unaffected, since they never scan for a later start position in the first place, so `\G` has nothing to change there. `\G` is only accepted as the very first thing in the whole pattern (a raw index-0 check on the pattern string, before any other parsing) -- anywhere else it's rejected at compile time with a `PatternSyntaxException`, rather than silently doing nothing there the way `java.util.regex` does.

`\b`/`\B` (word boundary / non-word-boundary) are implemented via `Matcher#peekPrevious()` (mirrors `peek()`, looking one code point backward instead of forward, bounded at `lookFloor` rather than `0` -- see `useTransparentBounds()` below) and a dedicated `WordBoundaryMatcherConstruct`. It's a plain `SingleDispatchingMatcherConstruct` — it doesn't consume input, so it still has exactly one successor, just like every other single-dispatch node; branching on matcher state didn't require a new node *shape*, only a new field (`peekPrevious()`) to read.

On top of that, `WordBoundaryPatternConstruct.buildMatcher()` applies a compile-time optimization: `\b`/`\B` very often sit next to a literal/character-class with a statically known "is this a word character" answer, so only one side needs checking at match time in that case. It classifies both the character just consumed and the one about to be consumed as always-word/always-non-word/unknown:
- **Peek side** (the character about to be consumed): read directly off the already-built `entryMap`/`entryElse` of `next` — no new analysis needed. If `next.entryElse != null`, or its `entryMap` ranges are a mix of word and non-word code points, the side is unknown.
- **Prior side** (the character just consumed): a `PatternConstruct.lastCharSet()` recursion, walking `LiteralPatternConstruct`/`ComplexCharacterPatternConstruct`/`ComplexQuantifiedCharacterPatternConstruct`/unquantified `QuantifiedUnionPatternConstruct`/`SequencePatternConstruct`. Returns `null` (a safe "not statically known" fallback) for anything that could match zero-width, or for any construct type it doesn't recognize. `SequencePatternConstruct.buildEntryMap` sets this (via `lastCharSet()` on the preceding sibling) before compiling a `WordBoundaryPatternConstruct` that isn't the first element of its `SequencePatternConstruct`; it's left `null` (safe, just unoptimized) otherwise. `firstCharSet()`/`lastCharSet()`'s own contract: the returned set must already be folded by whatever `CASE_INSENSITIVE`/`UNICODE_CASE` applied to that specific piece of content, same as `entryMap` is -- `ComplexCharacterPatternConstruct`'s ranges are folded at parse time already; `LiteralPatternConstruct` folds its own singleton the same way its `entryMap` does (`MatcherConstruct#foldedEntrySet`). Getting this wrong for a leaf type under-reports what it could actually have matched: it was wrong for `LiteralPatternConstruct` until 2026-09-29 (see notes.md), which both let a backreference's entry set silently miss a code point its referenced group could have captured (a match-time dispatch-gate bug, not just a missed optimization -- see the Backreferences section below) and let this `\b`/`\B` elision wrongly conclude "can never match" for a pattern that actually can, whenever the extra folded-in code point (e.g. U+212A Kelvin sign, U+017F long s under `(?iu)`) has different word-ness than the literally-written character.

If both sides are statically known, the boundary either always holds (compiles to a zero-width no-op, `matcher = next.matcher`) or never can (a compile-time `PatternSyntaxException` — e.g. `a\bb` is rejected, since two word characters can never have a word boundary between them; this is consistent with this project's general "unsatisfiable at compile time is an error, not a silent always-fail" philosophy, unlike `java.util.regex`, which would compile `a\bb` and just never match it). Otherwise, `WordBoundaryMatcherConstruct` only checks whichever side isn't statically known, via a small pair of enums (`PriorWordBoundaryMatchType`/`PeekWordBoundaryMatchType`) whose combinations are constructed by `WordBoundaryPatternConstruct.buildMatcher()` so the nonsensical ones are unconstructible, and only calls the (slightly more expensive, backward-looking) `peekPrevious()` when the preceding side is the one left unresolved.

`BoundaryPatternConstruct`'s `BoundaryEnum` values (`\A`, `\z`, `\Z` -- `\G` no longer among them, see above) are all implemented:

- **`InputBegin`/`InputEnd`** (`\A`/`\z`): always the true start/end of input (`pos == regionStart`/`pos == regionEnd`) -- `MULTILINE` has no effect on either.
- **`InputEndExceptTerminator`** (`\Z`): the end of input, or immediately before the input's own *final* line terminator, if it has one -- checked by scanning forward from `pos` for a line terminator that reaches exactly to `regionEnd` (not merely one somewhere in the remaining input), via the package-private `MatcherConstruct.matchesEndExceptTerminator` helper (shared with `LineBoundaryMatcherConstruct`, below). This is a zero-width assertion that does not consume the terminator, so `matches()` (which requires the whole region, terminator included) still fails whenever one is present; only `find()`/`lookingAt()` (a prefix match) see the exemption -- verified directly against `java.util.regex` while implementing this, since it's easy to misremember `matches()` as tolerating it too.

`LineBoundaryPatternConstruct`/`LineBoundaryMatcherConstruct` (`^`/`$`, a `boolean isLineBegin` distinguishing them instead of a shared enum): without `MULTILINE`, exactly `InputBegin`/`InputEndExceptTerminator` (`^` reuses the plain `pos == regionStart` check; `$` reuses `matchesEndExceptTerminator`). Under `MULTILINE`, `^` also matches immediately after any line terminator (a backward scan, `MatcherConstruct.lineTerminatorLengthBefore` -- the mirror image of the forward `lineTerminatorLengthAt` scan `\Z`/multiline-`$` use, treating a `"\r\n"` pair as ending at one position, not creating a second match point between the `\r` and the `\n`), and `$` also matches immediately before any line terminator. Line-terminator recognition (`\n`, `\r`, `"\r\n"` as one unit, `\u0085`, `\u2028`, `\u2029` by default; only `\n` under `UNIX_LINES`) is implemented once, symmetrically, as two `MatcherConstruct`-level static helpers shared by both `BoundaryMatcherConstruct` and `LineBoundaryMatcherConstruct` rather than duplicated.

`Matcher.useAnchoringBounds(false)` makes `^ $ \A \z \Z` see the true edges of the input instead of the region's: `Matcher` keeps `anchorStart`/`anchorEnd` (`regionStart`/`regionEnd` when anchoring, else `0`/`input.length()`), recomputed by `syncAnchors()` from `region`/`reset`/`useAnchoringBounds`, and only the boundary constructs read them (the character-consuming code still stops at `regionEnd`, so `lineTerminatorLengthAt` reads `input` directly when `pos == regionEnd < anchorEnd`). The setting survives `reset()`/`usePattern()`, like `java.util.regex`. A MULTILINE `^` never matches at `anchorEnd` and counts as hitting the end, as in the JDK. `AnchoringBoundsTest` diffs match results and both hit-end flags against `java.util.regex` over every region of many inputs.

`Matcher.useTransparentBounds(true)` lets `\b`/`\B` see outside the region: `Matcher` keeps `lookFloor`/`lookCeil` (region edges, or `0`/`input.length()` when transparent), `peekPrevious()` stops at `lookFloor`, and `peekForBoundary()` reads past `regionEnd`. When `pos == regionEnd` with a real character beyond, `WordBoundaryMatcherConstruct` tests the real boundary itself, because its compile-time classification of the following character assumes that character is the one about to be consumed. A `\b`/`\B` whose both neighbours are statically known is elided at compile time, but not to nothing: it compiles to an `ElidedWordBoundaryMatcherConstruct`, which only does anything at `regionEnd` under transparent bounds (where the statically-known following character can't actually be consumed, so the real next character decides whether `java.util.regex` reaches the following node and flags `hitEnd`), and is a plain pass-through otherwise. `TransparentBoundsTest` therefore diffs `hitEnd` for every pattern.

#### Lookbehind (`LookbehindPatternConstruct`/`LookbehindMatcherConstruct`)

`(?<=X)`/`(?<!X)` is supported only when `X` always matches exactly one code point -- a direct generalization of `\b`/`\B`'s own single-code-point `peekPrevious()` check, so it can still be evaluated in O(1) per position. Lookahead (`(?=...)`/`(?!...)`) and lookbehind whose body isn't provably exactly one code point wide are rejected at compile time; see this section's own "Alternatives Considered" entry for why they're permanently out of scope rather than merely unimplemented.

`PatternParser#parseLookbehind` parses the body with the exact same recursive-descent machinery an ordinary non-capturing group uses (`parseUnion`), so a real capturing group nested inside it (e.g. `(?<=(a))`) is numbered and registered completely normally, before the parsed body is statically resolved by `PatternConstruct.LookbehindPatternConstruct#resolveSingleCodePointBody` -- a recursion shaped like `lastCharSet`/`firstCharSet` but stricter (total width must be exactly one code point, not just "last/first character known") that also threads through which capturing group, if any, wraps the whole body. A body isn't just "one code point" for a plain literal/character class: `(?<=a|b)` (an alternation of one-code-point branches) and `(?<=(a|b))` (the same, wrapped in one capturing group) both resolve too, as long as no more than one capturing group ever wraps the single code point behind the assertion.

Unlike `\b`/`\B`, `LookbehindPatternConstruct` never resolves to a compile-time no-op or a static "can never match" rejection: there's no "peek" side to classify away, since the previous character is never known at compile time regardless of what's on either side of the assertion in the pattern. `buildMatcher()` always builds a real `LookbehindMatcherConstruct`, which checks `matcher.peekPrevious()` against the body's resolved `CodePointSet` and dispatches to `next` on success.

When the body was wrapped in a capturing group, `LookbehindMatcherConstruct` "self-captures" the one code point behind `matcher.pos` directly -- writing `captureGroups[]` itself -- rather than going through the general `BeginCaptureMatcherConstruct`/`EndCaptureMatcherConstruct` machinery. This is safe specifically because the body is provably exactly one code point wide: unlike a general capturing construct (which has to guard against a begin-without-end write if something between `BeginCapture` and `EndCapture` fails), there's no possibility of a partial write here -- the check and the capture happen atomically in one `matchBody()` call.

Like `\b`/`\B`/`^`/`$`, a lookbehind's truth is position-dependent, so the see-through entry point `buildEntryMap` gives it (`buildZeroWidthEntryMap`, the same one every zero-width assertion uses) isn't enough for a loop's own continue-vs-exit ambiguity check -- see the `WordBoundaryPatternConstruct`/`LineBoundaryPatternConstruct` discussion above. `LookbehindPatternConstruct.admittedInteriorExitPeekSet` is `skipZeroWidthEntrySet`'s hook for this, simpler than the `\b`/`\B` version specifically because a lookbehind's truth depends only on the prior character, never on peek at all: once the loop body's own `lastCharSet` shows the assertion *could* hold right after an iteration, exiting through it is ambiguous with continuing for literally every peek code point (`universalCodePointSet()`), not just a classified subset -- e.g. `a+(?<=a)b` is rejected as genuinely ambiguous (this engine's flattened dispatch can't tell "continue the loop" from "exit via the lookbehind, then match `b`" apart at the next `a`), the same way `a+\B` is. A *reluctant* loop has no such compile-time check at all (per `skipZeroWidthEntrySet`'s own `checkAssertions` doc, that check only ever runs for a plain greedy loop) -- `a+?(?<=a)b` compiles fine, and `LookbehindMatcherConstruct` implementing `ZeroWidthAssertionGuard` (alongside `WordBoundaryMatcherConstruct`/`LineBoundaryMatcherConstruct`) lets `MatcherConstruct#exitAssertionChain` evaluate it, side-effect-free, before a `ReluctantLoopMatcherConstruct` commits to an early exit.

Unlike `\b`/`\B` (which also peeks forward via `peekForBoundary()`, and so can depend on whether more input exists), `LookbehindMatcherConstruct` never sets `hitEnd`/`requireEnd`: it only ever looks backward, so nothing about its result can change with a longer suffix -- confirmed by `LookbehindTest`'s own differential run against `java.util.regex` across regions and transparent/opaque bounds, the same technique `TransparentBoundsTest` uses for `\b`/`\B`.

#### Extended grapheme clusters (`GraphemeClusterPatternConstruct`/`GraphemeClusterMatcherConstruct`)

`\X` matches one whole extended grapheme cluster (UAX #29) starting at the current position. Unlike every
zero-width assertion above, it's an ordinary CONSUMING construct -- more like a multi-code-point `LiteralPatternConstruct`
than a boundary -- so it needs none of the zero-width wiring (`entryElse = this`, `admittedInteriorExitPeekSet`,
`ZeroWidthAssertionGuard`); it participates in ordinary entry-point/dispatch machinery exactly like a character
class.

**Why `\X` needs only a forward scan.** Determining where the NEXT cluster boundary is, starting from a position
already known to be a boundary, only ever needs to scan FORWARD -- `GraphemeCluster.nextBoundary` (a direct port
of JDK 27's `jdk.internal.util.regex.Grapheme#nextBoundary`) reads one code point at a time from the current
position, exactly the access pattern this engine's `peek()`-driven matching already uses elsewhere for a
multi-code-point literal. `\X` needs none of the backward-lookback machinery `\b{g}` (below) needs: it only ever
scans forward from a position it's already sitting at, never backward and never past `\X`'s own successor
construct.

**Entry point: universal, not `.`-style catch-all.** `.` claims "whatever a sibling branch doesn't" (via
`residualElse`, see "`.`: all other options"), so it can coexist with a sibling that claims some of the domain explicitly. `\X` can't do this: its
own width isn't statically known (a cluster could be one code point or many), so there's no way to characterize
"whatever `\X` wouldn't otherwise claim" the way `.`'s complement-based mechanism does. `GraphemeClusterPatternConstruct`
therefore reports `entryMap = universalCodePointSet()` unconditionally -- every code point, claimed explicitly --
which means `\X` can never safely sit next to another union branch or loop-exit candidate: `a|\X` and `\X*a` are
both rejected as ambiguous at compile time, like any explicit class covering everything (see README's "Intentional differences" list).
This is the conservative, always-correct choice given the width isn't known; a future refinement narrowing
`\X`'s claimed entry set (e.g. to "definitely starts a cluster of exactly N code points" for some literal
sibling) is possible in principle but not attempted here.

**Unicode data.** The GCB (grapheme cluster break) property classification a cluster boundary decision depends on
(CR/LF/Control/Extend/ZWJ/Regional_Indicator/Prepend/SpacingMark/L/V/T/LV/LVT, plus Indic_Conjunct_Break's
Linker/Consonant/Extend for GB9c) is generated by `UnicodeAnalyzer.graphemeClusterBreak()`, a direct port of JDK
27's `jdk.internal.util.regex.Grapheme#getType`, into thirteen `GCB_*` `CodePointSet` fields in the generated
`UnicodePredicates.java` -- pinned to JDK 27's Unicode tables like every other named class here (see README's
"Unicode data is currently pinned to JDK 27's tables" entry and the "Regenerating `UnicodePredicates.java`"
section of CLAUDE.md for the regeneration recipe). `Extended_Pictographic` isn't a fourteenth generated set: it's
already the existing `isExtendedPictographic` predicate (`Character.isExtendedPictographic`, generated
separately), and `GraphemeCluster.getType` checks it first, exactly mirroring `Grapheme.getType`'s own priority.
`GraphemeCluster.java`'s `isLinker`/`isConsonant`/`isExtend` (Indic_Conjunct_Break) are copied verbatim from JDK
27's `jdk.internal.util.regex.IndicConjunctBreak` rather than generated -- they're already given as literal
hardcoded code point ranges in the JDK source (not derived from a runtime `Character` query), so there's nothing
for a generator to compute.

**Faithful, not re-derived, JDK behavior.** `GraphemeClusterMatcherConstruct.matchBody` mirrors JDK 27's
`Pattern.XGrapheme#match` exactly, including its one easy-to-miss detail: `hitEnd` is set only when there's no
input left to START a cluster with (`peeked == -1`), never merely because the consumed cluster happens to reach
`regionEnd` (which could, in principle, still be mid-cluster if the input were longer) -- ported as-is rather than
"fixed," per this project's general policy of matching `java.util.regex`'s actual behavior over what UAX #29 alone
would imply. `\X` never scans past `matcher.regionEnd`, even under `useTransparentBounds(true)` (transparent
bounds only ever extend what `\b`/`\B`/lookbehind can see backward/forward for a zero-width check, not how far a
CONSUMING construct may read).

#### Grapheme boundary (`GraphemeBoundaryPatternConstruct`/`GraphemeBoundaryMatcherConstruct`)

`\b{g}` is a zero-width assertion: it holds at a position iff there's an extended grapheme cluster boundary there.
Unlike `\X`, determining whether the CURRENT position is a boundary can't always be answered by looking at just
the immediately adjacent code points, the way `\b`/`\B`'s single `peekPrevious()` call answers "is the prior
character a word character": three of the fourteen UAX #29 rules are genuinely context-dependent beyond the
adjacent pair --

- **GB12/13 (regional indicators / flag emoji).** The SAME adjacent `(RI, RI)` pair is a boundary between two
  flags but not within one -- e.g. `🇺🇸🇬🇧` (four regional-indicator code points): no boundary between RI₁ and
  RI₂ (they form one flag), but a boundary between RI₂ and RI₃ (that's where the next flag starts). The rule is
  parity-based ("boundary before an RI iff an even number of RIs immediately precede it"), so telling these two
  positions apart needs counting every RI back to the start of the run, not just looking at the immediate
  neighbor.
- **GB11 (ZWJ emoji sequences).** `Extended_Pictographic Extend* ZWJ × Extended_Pictographic` -- whether a ZWJ
  suppresses the break into a following pictograph depends on whether an `Extended_Pictographic` genuinely started
  the `Extend*` run before that ZWJ, which needs walking back through that run.
- **GB9c (Indic conjunct sequences).** `Consonant [Extend|Linker]* Linker [Extend|Linker]* × Consonant` -- e.g.
  `क्ष` (Devanagari KA + VIRAMA + SSA) is one cluster. The position right before the trailing Consonant needs
  walking back through the `Extend|Linker` run to confirm both a leading Consonant AND at least one Linker are
  there; the plain pairwise table alone would say "break" (Extend → Other defaults to a break).

Every other rule (GB3-GB9b: CRLF, Control, Hangul L/V/T/LV/LVT, Prepend, plain Extend/ZWJ/SpacingMark) depends only
on the immediately adjacent pair, exactly like `\b`/`\B`.

**Design: bounded backward walks per rule, not JDK's rescan-from-match-start.** JDK 27's own `Pattern.GraphemeBound`
sidesteps the three context-dependent rules above by rescanning forward from `matcher.last` (the start of the
current match attempt) on every single check -- correct, but O(distance-from-match-start) per check, and reliant
on the invariant that `matcher.last` is itself always a genuine boundary. This engine instead does a genuinely
LOCAL, self-contained check (`GraphemeCluster.isBoundary`): the ordinary pairwise `RULES` table for the common
case, plus three small BOUNDED backward walks -- one per context-dependent rule above, each walking back only
through the specific kind of run that rule cares about (the RI run for GB12/13, the `Extend*` run for GB11, the
`[Extend|Linker]*` run for GB9c) rather than to some external anchor. Each walk is bounded by `Matcher#lookFloor`
(the same bound `peekPrevious()`/lookbehind already use, honoring `useTransparentBounds`), so it's exactly as
"local" as `\b`/`\B` already are, just occasionally reading back further than one code point when (and only when)
the input actually contains one of these three specific run shapes. This sidesteps needing any "last known
boundary" anchor concept in `Matcher` at all -- a design decision this project made deliberately, per the project
owner (2026-09-23), rather than porting JDK's `matcher.last`-based approach.

**No compile-time elision.** Unlike `\b`/`\B` (which can resolve to a no-op or a compile error when both
neighbors' word-ness is statically known), `GraphemeBoundaryPatternConstruct.buildMatcher()` always builds a real
`GraphemeBoundaryMatcherConstruct` -- same as `LookbehindPatternConstruct`, and for the same reason: there's no
"peek"-side classification cheap enough to be worth attempting here (a neighbor's GCB type alone doesn't resolve
the three context-dependent rules above anyway).

**Three fixed positions, mirroring JDK exactly.** `GraphemeBoundaryMatcherConstruct` handles the true region start
and true region end (honoring `useTransparentBounds`, via `lookFloor`/`lookCeil`) without ever calling
`GraphemeCluster.isBoundary`, mirroring `Pattern.GraphemeBound` precisely: at `lookFloor`, always a boundary; past
`lookCeil`, always a boundary too, but also sets `hitEnd`/`requireEnd` (unlike a 1-code-point lookbehind, which
never sets either, `\b{g}` also peeks forward, so a longer suffix could change its answer, same as `\b`/`\B`);
strictly between the two, the real check runs. A position splitting a surrogate pair is never a boundary, checked
before any GCB classification (see `GraphemeCluster.isBoundary`'s own doc for why this guard is load-bearing, not
just an optimization: a lone surrogate would otherwise classify as `GCB_CONTROL`, and the plain pairwise table
treats two adjacent Control-classified values as an unconditional break).

**Loop ambiguity: deliberately conservative, not precise.** `GraphemeBoundaryPatternConstruct.admittedInteriorExitPeekSet`
(consulted the same way `WordBoundaryPatternConstruct`'s/`LookbehindPatternConstruct`'s own versions are, from
`skipZeroWidthEntrySet`'s `checkAssertions` mode -- see "Boundary matching" above) doesn't attempt to reason about
which peek code points could actually trigger GB9c/GB11/GB12-13: whenever the loop body's own last-consumed
character is statically known at all (`bodyLastCharSet != null`), it treats `\b{g}` as potentially holding for
EVERY peek code point, i.e. always ambiguous with continuing the loop. This over-rejects some loops that would
actually be fine at match time (e.g. `a+\b{g}b`, rejected the same way `a+\B` is) in exchange for never
under-rejecting a genuinely ambiguous one -- the same tradeoff this project already accepts for `\X` itself (see
README's "Intentional differences"). A *reluctant* loop has no such compile-time check at all (per
`skipZeroWidthEntrySet`'s own `checkAssertions` doc), so `a+?\b{g}b` compiles fine, resolved at match time via
`GraphemeBoundaryMatcherConstruct implements ZeroWidthAssertionGuard` (consulted by
`MatcherConstruct#exitAssertionChain`), same mechanism as `\b`/`\B`/lookbehind.

**`\B{g}` is not special syntax**, matching `java.util.regex` exactly: only `\b` recognizes a `{` suffix in the
JDK grammar (`Pattern.java`'s escape-parsing switch), so `\B{g}` parses as `\B` (non-word-boundary) followed by
the literal text `{g}`. This engine's `rejectBoundaryType()` still rejects any OTHER `\b{...}`/`\B{...}` form
outright (rather than silently reading it as literal text after a plain boundary) -- unchanged by `\b{g}`'s own
implementation.

### `hitEnd` / `requireEnd`

`Matcher.hitEnd`/`requireEnd` are plain booleans, cleared at the start of each `matches()`/`lookingAt()`/`find(int)` and sticky across every start position one `find()` tries (same as `java.util.regex`). They are only ever written from cold paths, so the match hot path is unchanged: a gated dispatch miss whose input is the end-of-input sentinel (`MatcherConstruct.match`), a `SingleChar` miss on the sentinel, a literal that runs off the region end while the remaining input still agrees with its prefix (a mismatch before the end is not a hit-end), a backreference whose group is longer than the remaining input, `$`/end-of-input boundaries that matched at the end, `\b`/`\B` reached at the end, and a failed `find()`. Java's `requireEnd` is set by `$` and the end-except-terminator boundary (both flags) but the plain end-of-input boundary sets only `hitEnd`. A failed `find()` is always a hit-end except when the whole pattern is a single alternative starting with the begin-of-input anchor or a non-`MULTILINE` line-begin anchor (`Ll1Pattern.startsWithBeginAnchor`): `java.util.regex` tries only the search start for those, so nothing scans to the end. There is no backtracking here, so flags set in a branch Java would have abandoned and re-tried are not reproduced; `HitEndRequireEndTest` diffs both flags against `java.util.regex` across patterns, inputs and flag sets to guard this.

### Code point range representation

- `CodePointSet` (interface, no type parameter) is the single representation for a range of Unicode code points
  throughout this codebase -- pure membership ("is this code point in the set", nothing more), not a
  code-point-to-value map: this engine's entry-point/dispatch machinery and every `NamedCharClass`/generated
  `UnicodePredicates` constant only ever needed a boolean answer, so there's no generic value-carrying map
  underneath it, and no Guava `RangeMap`/`RangeSet` remains anywhere in `llkpattern/src/main` (an earlier design
  had one, `CodePointMap<V>`, generic over an arbitrary value type fixed to `Boolean` almost everywhere it was
  used -- see notes.md's 2026-09-12/2026-09-14 entries for that migration and its later full removal). Dropping
  the value entirely, rather than keeping a generic map with `V` fixed to `Boolean`, removes a whole parallel
  values array and the null-valued "punched hole" trick a generic map's `complement` would otherwise need: since
  a set's only two states at any code point are "in" and "out", a negated set is just this same set with the two
  states swapped (`invert()`), not a rebuild.
- `[min, max)` range convention throughout, immutable `Range`, `contains`/`containsAll`/`add`/`remove`,
  `union`/`difference`/`intersection`/`complement`, `invert`. Ambiguity detection's own "these two branches both
  claim this character" conflict check is a plain pairwise `CodePointSet#intersects` scan (`PatternConstruct.checkDisjoint`,
  see "Compilation" above), not a property of `CodePointSet` itself.
- `forEachRange(RangeConsumer)` visits every range as a plain `(int min, int max)` callback -- no `Range`/`Entry`/
  `Iterator` allocated per range for `ArrayCodePointSet`'s common case. `rangeSet()` is a `CodePointSet`-interface
  default built *from* `forEachRange` (eagerly, into a `LinkedHashSet`) rather than the other way around --
  `ArrayCodePointSet` overrides `forEachRange`/`first` directly instead of `rangeSet()`. Preferred over `rangeSet()`
  on any hot path that just wants to visit ranges and has no actual use for a `Range` object -- `PatternParser`'s
  `intersect` (`&&`) helper and most of `PatternConstruct`/`MatcherConstruct`'s own compile-time range-merging
  loops all use it.
- `first(RangePredicate)` is `forEachRange`'s short-circuiting counterpart: same zero-allocation range visitation,
  but stops at (and returns `true` from) the first range the predicate accepts, instead of always visiting every
  range. Worth it specifically for a query that can stop early -- `WordBoundaryPatternConstruct`'s `isSubsetOf`/
  `isDisjointFrom` (bail out on the first violation) are the only two current callers; `forEachRange` would have
  kept scanning the rest of a large character class after the answer was already known.
- `ComplexCharacterPatternConstruct.ranges` (and everything downstream of it -- `SingleCharMatcherConstruct.validRanges`, `firstCharSet`/`lastCharSet`/`WordBoundaryPatternConstruct.priorCharSet`/`wordSet`) is a `CodePointSet`, not a Guava `RangeSet<Integer>`, and is `final`/effectively immutable: every constructor sets it exactly once, from a set `PatternParser` finished building beforehand (`CharClassParser#parseComplexCharacterRanges` builds into its own local accumulator throughout a bracket expression's parse, only handing the finished set to a `ComplexCharacterPatternConstruct` at the end), so a caller with a source set it's sure won't be mutated again (a `NamedCharClass`/`RegexCharacterClass` constant, `parseComplexEscape`'s return value) can assign it in directly with no defensive copy. Within a single bracket-expression run, `CharClassParser#parseComplexCharacterRanges` unions in large contributions (an escape's or nested class's `CodePointSet`) by reference via `UnionCodePointSet` while the run is still being parsed, rather than copying each one into the run's `CodePointSetBuilder` immediately -- but always collapses back to a concrete `ArrayCodePointSet` (`mergeRun`) before the run's result can reach `ComplexCharacterPatternConstruct.ranges` or any compiled matcher, since `UnionCodePointSet`'s membership/range operations are real virtual dispatch (or a full materialize), not `ArrayCodePointSet`'s single binary search, and this field sits on the match-time hot path. `[^...]`/DOTALL negation goes through `CodePointSet#complement` directly (an `invert` flag flip plus a cheap array copy -- see `CodePointSet`'s own doc); `&&` intersection is a real intersection (`b.intersection(min, max)` per `a`-entry, inversion-aware on either side) rather than the old `a.removeAll(b.complement())` formula, which would otherwise force materializing a complement just to subtract it. `SingleCharMatcherConstruct` guards the `-1` end-of-input sentinel explicitly before consulting the set -- a negated class legitimately matches everything it doesn't exclude, so `-1` is simply never a real code point, checked first, unconditionally, rather than relying on the set's own membership query to keep it out.
- `NamedCharClass`/`UnicodePredicates` (and the `RegexCharacterClass` enum nested in the former) are `CodePointSet` throughout now too -- no Guava `RangeSet`/`RangeMap` remains anywhere in `llkpattern/src/main`. Every constant's `ascii`/`unicode` field is a `CodePointSet`; hand-written literal sets use a small `build(Consumer<MutableCodePointSet>)` helper (an `ArrayCodePointSet` filled via ordinary `add`, which -- unlike the generated file's `appendSorted` -- tolerates entries added out of order); `unionOf`/`difference` are thin wrappers over `CodePointSet#union`/`#difference`. A constant that's logically a complement (`Assigned`, `Graph`, `\D`, `\H`, `\S`, `\V`, `\W`, `DOT`) is built via `CodePointSet#complement` directly (`DOT` is simply `{'\n'}.complement()`) -- cheap even at class-init time, since `ArrayCodePointSet#complement`'s fast path is a plain array copy plus a flipped `invert` bit, never a domain walk. `PatternParser`/`WordBoundaryPatternConstruct` consume `NamedCharClass`/`RegexCharacterClass` constants directly now (no adapter step) -- `get(prefix, flags)`/`get(flags)` already return a `CodePointSet`, and a standalone escape atom (a bare `\D`/`\p{...}` in running pattern text, not inside `[...]`) aliases the constant straight into a fresh `ComplexCharacterPatternConstruct.ranges` with no copy at all, since that field is effectively immutable once constructed (see `PatternConstruct.ComplexCharacterPatternConstruct` below).
- `CharacterClass.java` (the old, confirmed-dead `ImmutableRangeSet`-wrapper design that predated `ComplexCharacterPatternConstruct`'s own ranges) has been deleted.
- `ArrayCodePointSet` is `CodePointSet`'s one implementation, specialized to the Unicode code point domain: a
  single flat `int[] keys` array (each entry packing `(min << 11) | count`, where `count` is the number of
  *additional* code points after `min` in the same run — 21 bits for `min` plus 11 for `count` fits an `int`
  exactly, no `long` and no parallel "value" array needed, since a set has nothing to store per entry but the run
  itself), kept sorted by `min` for lookup (a binary/linear-search hybrid, see `floorIndex` -- linear below
  `LINEAR_SEARCH_THRESHOLD` entries, since a real binary search costs more than it saves for the small sets this
  library builds most). This avoids a tree structure's per-entry node/object overhead in favor of one flat array
  (starting at capacity 1 and growing by 1.5x), which is both smaller and more cache-friendly during matching.
  `invert()` (backing `complement()`) is a flipped `boolean` bit plus a cheap array copy, not a rebuild -- see
  `ArrayCodePointSet`'s own class doc for the full membership-testing story. The binary search compares each
  key's *extracted* `min` (always a non-negative `int` in `[0, MAX_CODE_POINT]`), never the raw packed key
  itself, specifically to sidestep any sign-bit concern from packing `min` into high bits (a code point at/above
  `0x100000`, plane 16, does land on the sign bit when packed).
- Every mutator (`insert`, `remove`, the package-private bulk-append `appendSorted`) is localized to just the region of the array it
  actually touches, found via the same lookup reads use — a single touched entry is a plain field edit or lone
  insert/delete, and multiple touched entries trim the first/last in place and shift out whatever's strictly
  between, all without scanning the rest of the array. Building an n-entry set via n `insert`/`appendSorted` calls is
  therefore O(n) amortized, not O(n^2) — an earlier version that rescanned the whole array on every mutation
  regressed a JMH benchmark by 3.4x before this was caught (see notes.md's 2026-09-08 entry, from before this
  class's rename from `ArrayCodePointMap`).
- `rangeSet()`/`forEachRange` always yield ranges in ascending `min` order — a `CodePointSet`-interface-level
  contract (every implementation satisfies it for free, being a set of disjoint ranges over an ordered domain),
  not just an `ArrayCodePointSet` detail. `MutableCodePointSet.insertAll`'s optimized override relies on it directly:
  rather than one `insert()` call per source entry, it's a single sorted merge sweep over this set's own entries and
  the source's, degenerating automatically to a plain bulk append when the target starts empty. Every compile-time
  site that copies an already-known-sorted source into a fresh, empty destination set — every
  `PatternConstruct.buildEntryMap`/`buildMatcher` and `MatcherConstruct.populate`/loop-dispatch site that walks a
  child's or a merge result's ranges via `forEachRange` — uses `appendSorted` rather than `insert`/`insertAll` for
  exactly this reason: `insert()`'s binary-search-and-splice is wasted work when the destination is empty and the
  entries already arrive in order (a plain filter, i.e. skipping some source entries, doesn't break this — the
  ones kept are still ascending). Only genuinely irregular, out-of-order construction (e.g. `NamedCharClass`'s
  hand-written literals, see below) still needs `append`.
- Adjacent entries are always coalesced together on mutation (there's no "value" to disagree on, unlike an
  earlier generic-map design would have had — see this section's first bullet), except where doing so would
  exceed a single entry's 2048-code-point capacity (the 11-bit count field's range) — a longer logical range
  unavoidably splits across multiple consecutive entries, which is observable through `rangeSet()` even though it
  represents one contiguous run.

### Unicode support

- `NamedCharClass` maps regex-style named classes (`\p{Alpha}`, `\p{IsGreek}`, `\p{general_category=Lu}`, etc.) to underlying `CodePointSet` predicates/ranges.
- `UnicodePredicates` is a ~14k line generated data file of Unicode category/script/block predicates (one `CodePointSet` field per predicate), produced by the `unicodeanalyzer` module's `UnicodeAnalyzer` from the running JDK's own `Character` tables. It carries a "DO NOT EDIT" javadoc and a `javax.annotation.processing.Generated` annotation recording the generation date; regenerate it with `./gradlew :unicodeanalyzer:generateUnicodePredicates` (run manually, as needed -- e.g. after a JDK upgrade changes Unicode data -- not part of the normal build). To pick up a *newer* JDK's Unicode data than whichever JDK Gradle's own daemon happens to be running on, run `UnicodeAnalyzer` against that newer JDK directly instead of through the Gradle task: compile via `./gradlew :unicodeanalyzer:classes` (a JDK Gradle itself can run on, e.g. 17 or 21), then invoke the compiled class directly with the newer JDK's own `java` (its classpath needs the `unicodeanalyzer` module's compiled classes plus the Guava jar under `~/.gradle/caches/modules-2/files-2.1/com.google.guava/`), and copy its output over the checked-in file with CRLF line endings. This sidesteps a real compatibility issue: Gradle's own Groovy buildscript compiler has crashed intermittently when run directly on some newer JDKs (seen on 25). Script predicates are generated one field per `Character.UnicodeScript` value, named exactly `UnicodeScript#name()`; `NamedCharClass#scriptByName` resolves `\p{IsLatin}`/`\p{script=Latin}` (full names or ISO 15924 aliases, case-insensitively) through a generated `UnicodePredicates.scriptByEnumName` string switch (shrinker-safe, unlike reflection) rather than ~160 enum constants. Block predicates are generated the same way, as `BLOCK_`-prefixed fields (prefixed because several block names collide with script names, e.g. `GREEK`) plus a `blockByEnumName` switch keyed by `UnicodeBlock#toString()`, resolved by `NamedCharClass#blockByName` for `\p{InGreek}`/`\p{block=Greek}`. The name scanner in `CharClassParser` accepts digits and `-` so names like `Latin-1Supplement`/`Latin_1_Supplement` reach the lookup.

### Backreferences

- Backreferences (`\1`, `\k<name>`) are supported, with disjointness checked at **compile time** using a precise, statically-computed entry set.
- A backreference's possible first characters are exactly the *referenced group's* possible first characters, computed by a new `firstCharSet()` AST helper mirroring the existing `lastCharSet()` used for `\b`/`\B`'s prior-character classification (same recursion shape: literal → first code point, character class → its ranges, sequence → first element, unquantified union → union of branches). `firstCharSet()`/`lastCharSet()`'s contract is that the returned set is already folded by whatever `CASE_INSENSITIVE`/`UNICODE_CASE` applied to that specific piece of content -- a character class's ranges are already folded at parse time (see "Case folding in character classes" below), and a bare literal folds itself the same way its own `entryMap` does, so every leaf answers with what it could actually have matched, not just the raw text as written. A backreference's own entry set folds this *again* by its own flags on top: `(?i)(a)(?-i)(?:\1|A)` needs `\1`'s entry set to include `'A'` (what the group could have captured under `(?i)`, independent of `\1`'s own case-sensitivity) -- getting only one of the two folds wrong either under- or over-reports what `\1` can dispatch on, a real match-time bug since this entry set gates dispatch, not just a compile-time approximation. Feeding the (doubly-folded) result into the normal disjointness check makes ordinary backreference usage (e.g. `(\w+)\s+\1`) compile with no special-casing, while genuinely ambiguous uses (e.g. `(a+)\1`, where the loop's continue-branch and the backreference's entry set both include `a`) are correctly rejected as a compile error, exactly like any other ambiguous alternation -- as is `(?i)(a)(?-i)(?:\1|A)` itself, once `\1`'s entry set correctly includes `'A'`.
- Possibly-empty referenced groups (e.g. `(a*)\1`, where `\1` can be zero-width) make `firstCharSet()` return unknown, falling back to the catch-all entry set. Fed into the normal disjointness check, this correctly rejects two such backreferences (or a backreference and any other catch-all construct) sharing the same alternation/loop-tail dispatch, since two catch-alls are always ambiguous; a single catch-all backreference alongside sibling branches with specific, disjoint entry sets isn't itself ambiguous (the specific branches simply take priority) and compiles fine, matching zero-width handling's existing "rare and probably not what you want, but not unsound" treatment elsewhere in this engine.
- Forward references (`\1` before its group is defined, e.g. `\1(a)`) are rejected at compile time. So is a
  reference to a group number with no group of that number open yet at all (e.g. `\141`, parsed the same way
  `java.util.regex` parses it -- `\1` greedily extended by further digits only while doing so stays within the
  number of groups opened so far, so `\141` is `\1` followed by literal `"41"`, not octal 0141): `java.util.regex`
  compiles this as a backreference node that structurally can never match any input (`BackRef.match` bails out the
  instant the referenced group index is out of range), the same "unsatisfiable at compile time is an error, not a
  silent always-fail" treatment this project already gives `a\bb` (see "Boundary matching" above) and forward
  references themselves -- so llk rejects it outright too, rather than compiling a node that's dead on arrival.

### Quotation, atomic groups, and negative-only flag groups

- `\Q...\E` is removed by a pre-pass in the `PatternLexer` constructor (`removeQuoting`), as `java.util.regex` does: quoted ASCII non-alphanumerics get a backslash, everything else is copied verbatim, and an unterminated `\Q` quotes to the end. The rest of the parser never sees quotation, so it works inside brackets and groups, keeps whitespace/`#` literal under `COMMENTS`, and a following quantifier applies to the last quoted character. The cost is that error positions in a pattern containing quotation refer to the rewritten text.
- `(?>X)` parses as `(?:X)`: with no backtracking, every group already matches atomically.
- Inline flag groups apply as `(flags | enabled) & ~disabled`, so `(?-i)` and `(?-i:X)` are accepted.

### `LITERAL` and `CANON_EQ`

- `LITERAL`: `PatternParser.parse()` short-circuits to a bare `SequencePatternConstruct` holding one `LiteralPatternConstruct` of the whole pattern text (no `\Q...\E` pre-pass, no metacharacters, no inline flags). `CASE_INSENSITIVE`/`UNICODE_CASE` still apply through the literal's own flags. An empty pattern is rejected like any empty sequence. `LITERAL` takes precedence over `CANON_EQ`.
- `CANON_EQ` is a text pre-pass (`CanonicalEquivalence.rewrite`, run right after `removeQuoting`), never a matcher feature, so `Matcher` and the compiled graph are unchanged and offsets stay in input coordinates. The pattern is NFD-normalized; each starter followed by combining marks (non-spacing marks, Hangul vowel/trailing jamo) becomes `(?:...)` over every canonically equivalent spelling: every mark ordering that NFD maps back to the same string, plus every single-code-point composition of a prefix of any such ordering followed by the remaining marks, plus any code point written in the original pattern whose decomposition is exactly the cluster (singletons and composition exclusions such as U+212B and U+0958 never come out of composing). The group wraps the whole cluster so a following quantifier applies to all of it.
- The spellings are left-factored into a trie before being emitted. A flat alternation would have several branches starting with the same base character whenever a cluster has two or more reorderable marks, which is exactly the ambiguity this engine rejects. Spellings of one cluster are never prefixes of each other, so every trie level has disjoint first characters and the result is always LL(1)-valid on its own; ambiguity can still arise with neighbouring constructs (`e|é`, `(?:é|è)`) and is rejected as usual.
- Inside a bracket expression a cluster can't be a member, so the clusters of one class are merged into one trie and emitted as alternatives next to the class of its plain members. A cluster in a negated class, a nested class, or next to a range `-` is a compile error with an explanation. Under `CASE_INSENSITIVE`+`UNICODE_CASE`, an original spelling that folds to an already-present single-code-point spelling is dropped (U+212B and U+00C5 would otherwise be duplicate branches).
- The rewrite runs on raw text before escapes are decoded, so an escaped `\u00e9` is not a cluster. Classes, `.` and `\w` never consume trailing combining marks, and error positions refer to the rewritten text.

### Public API shape

- `Ll1Pattern` and `Matcher` are designed to mirror `java.util.regex.Pattern`/`Matcher`'s public method surface, so callers can largely swap one for the other. See remaining_work.md for the current list of implemented vs. stubbed methods.
- **One compiled graph serves `matches()`, `lookingAt()`, and `find()`** — they don't need separate compilations. The difference between them is entirely about the `EndPatternConstruct`/`EndMatcherConstruct` terminal: `matches()` requires the *whole region* to be consumed to succeed, while `lookingAt()`/`find()` only need a matched *prefix* (the rest of the string is allowed to be leftover). Rather than baking that choice into the compiled graph, it's a single `boolean requireFullMatch` field on `Matcher`, set immediately before each match attempt (`matches()` sets it true; `lookingAt()`/`find()` set it false) and read only by `EndMatcherConstruct.match()` (`return !matcher.requireFullMatch || matcher.pos == matcher.regionEnd;`). This mirrors how `java.util.regex`'s own NFA nodes take an "anchoring" flag rather than compiling two different automata.
- `EndPatternConstruct` (the compile-time sentinel `Ll1Pattern.compile()` passes as the outermost `next`) registers `entryElse = this` in its own `entryMap` — reachable regardless of what character (or lack of one) comes next — rather than only the code point `-1` (Matcher's "no more input" sentinel — see `Matcher#peek()`). The latter would be sufficient for `matches()` (where reaching the terminal only ever happens at true end of input) but wrong for `lookingAt()`/`find()`: an *optional* loop's "exit" path (e.g. `a*` matched via `lookingAt()` against `"b"`) needs to be reachable at a position with real, valid leftover characters, not just at true end of string. `requireFullMatch` enforces the stricter check only when it's actually wanted. That catch-all means "end-of-find": the match is complete here under `lookingAt()`/`find()` whatever follows, but under `matches()` only at end of input. It is order-sensitive in a union, unlike a lowest-priority catch-all: `java.util.regex` takes the first alternative that succeeds, so `a*|b` on `"b"` is `""` under `find()` and `"b"` under `matches()`, while `b|a*` is `"b"` in both. `QuantifiedUnionPatternConstruct.buildMatcher` therefore keeps such a branch (`PatternConstruct#elseIsEndOfFind`, mirroring how the catch-all propagates) at its own list position, compiled ungated behind an `EndOfFindGateMatcherConstruct` that admits its explicit first characters, or end-of-find in the current mode, and otherwise defers to the next sibling. Any other catch-all (an unresolvable backreference) is still the ungated tail fallback, and its explicit ranges are overlap-checked too. Two catch-all branches (`a*|b*`) are still rejected.
- `Matcher#quantifiableCounts`/`captureGroups` are sized automatically from the compiled `Ll1Pattern` (`PatternParser` exposes the final quantifiable-construct count, capture-group count, and a name→`captureConstructIndex` map after `parse()` via `getQuantifiableCount()`/`getCaptureGroupCount()`/`getNamedGroups()`).
- `find()`'s unanchored search is a straightforward linear scan (`attemptMatch` at each candidate start position, `lookingAt()`-style, until one succeeds or the region is exhausted) — every candidate start position is just an ordinary `lookingAt()`-style attempt from a different `pos`.

### Case folding in character classes

`CASE_INSENSITIVE` is applied to a class's members at parse time, never at match time, so `SingleCharMatcherConstruct` is a plain membership test. `CharClassParser#addLiteral`/`addLiteralRange` (per bracket member) and `CharClassParser#singleCharacter` (a lone literal that had to become a class) expand each literal member through `CaseFolding`, mirroring `java.util.regex`: a lone character matches its whole case-equivalence class (`lower(upper(x))` key, so `(?iu)[s]` matches `ſ`), a `lo-hi` range matches any `x` with `x`, `upper(x)` or that key inside it. Without `UNICODE_CASE` only ASCII letters fold; `UNICODE_CHARACTER_CLASS` implies `UNICODE_CASE`. Folding is per literal member because the JDK never folds a named class (`\w`, scripts, blocks) or a nested class: it *substitutes* sets instead (`NamedCharClass#caseInsensitive`: `Lu`/`Ll`/`Lt` become `LC`, the case properties and POSIX `Upper`/`Lower` become the union of all cased letters or `[A-Za-z]`). A negated class is therefore a plain complement of the already-folded members. `CaseFolding` finds a set's preimage under `upper`/`key` through two sorted tables built once, lazily, from `Character`, so its cost does not grow with the size of the class.

### `.`: all other options

The parser gives `.` a `ComplexCharacterPatternConstruct` with `residualElse` set. `ranges` is its accept set (everything, minus the line terminators unless `DOTALL`), used for the match-time membership check and as a ceiling on gates. But its entry point is an empty explicit set plus an else claim (`entryElse = this`, `elseIsResidual()`), so it can never overlap a sibling by construction. `elseIsResidual()` mirrors `elseIsEndOfFind()` through every construct that forwards an else claim (sequence head, capture marker, zero-width assertion, quantified wrapper, union). What each context does with the claim:

- **Union**: the residual candidate is compiled as the ungated tail after every sibling's gate has missed, like any else candidate; its own membership check keeps line terminators out. Two else claimants (`.|.`, `.` and an unresolvable backreference) stay ambiguous.
- **Loop**: `narrowResidualGates` gives a residual body part the gate `firstCharSet()` minus every other body part's gate and `next`'s entry set, so `.+b` iterates over `[^b]`. A residual body and an end-of-find exit coexist (`.*` at the end of a pattern; `mergeOneEntryPoint`'s `isLoopExit` case): the body takes what it can and the exit takes the rest. A residual `next` after a residual body (`.+.`) is rejected, since the exit would be left nothing. A residual body inside a possessive loop is rejected whenever a sibling or `next` claims part of its accept set (`.++b`): `java.util.regex` swallows the `b` there too, so `[^b]++b` would be a silent divergence.
- **`LoopFirstEntryMatcherConstruct`** is not used for a loop with a residual part. Its proof (the outer gate already checked the first character against the body gate) doesn't hold when the loop is reached as another choice's ungated tail: `a|.+b` on `"b"` would let `.` consume the `b`.

Since nothing backtracks, a loop over `.` stops at the first character the following part claims (`h.*o` finds `"hello"` in `"hello world"`). This is the one place the engine deliberately deviates from `java.util.regex` on an otherwise unambiguous pattern; `DotElseDifferentialTest` checks each `.` pattern against the same pattern with `.` rewritten to its explicit residual class.

## Alternatives Considered

### Successor dispatch via bound `MethodHandle` (`findSpecial`) instead of a plain virtual call

Considered for `SingleDispatchingMatcherConstruct.next.match(...)`: bind a `MethodHandle` to the successor's exact `match` override at construction time (via `findSpecial`, an `invokespecial`-style direct call — `findVirtual` + `bindTo` was also tried and rejected on the same grounds, since it's still an ordinary virtual dispatch under the hood) and invoke that instead of `next.match(matcher, peeked)`.

- **Pros**: in principle, skips a virtual-dispatch lookup per match step; `findSpecial`'s `invokespecial` semantics are exactly "call this one exact method," which is all a fixed `next` reference ever needs.
- **Cons**: a `MethodHandle` invocation on a non-static receiver isn't reliably inlined by any JVM, and is frequently *slower* than a plain virtual call even on newer Android runtimes — the entire performance premise doesn't hold. Getting a working, Android-API-26-compatible form at all required real complexity: `findSpecial` requires its `specialCaller` argument to be the calling `Lookup`'s own `lookupClass()` (or a subclass) — it emulates `super.foo()` from a specific class, not "call this concrete method on some unrelated object" — which fails for the common case of a `SingleDispatchingMatcherConstruct` whose successor is a sibling-hierarchy `ForkingMatcherConstruct`/`LoopMatcherConstruct`. The only fully-general fix, `MethodHandles.Lookup.privateLookupIn`, is Java 9+/Android API 33+ — below this project's Android floor of API 26 (worth over half of live Android devices vs. under half on API 33) — so avoiding it meant every concrete leaf class supplying its own one-line `findSpecial` call (exploiting `MethodHandles.lookup()`'s caller-sensitivity), real per-class boilerplate for no realized benefit.
- **Decision**: rejected. `SingleDispatchingMatcherConstruct.matchNext` uses a plain `next.match(matcher, peeked)`.

### `BeginCaptureMatcherConstruct` with a built-in branching role, for capturing-and-quantified loops

Considered for compiling a capturing, quantified construct (e.g. `(a)*`): give `BeginCaptureMatcherConstruct` a second mode where it itself holds a `dispatchMap` and does the per-branch routing among the loop's body parts, rather than being a pure single-successor node.

- **Pros**: one fewer node type actually allocated per capturing-loop iteration (no separate internal fork chain).
- **Cons**: breaks the clean single-vs-branching split — a node meant to be single-successor gains a dispatch role, undermining the invariant that only `ForkingMatcherConstruct`/`LoopMatcherConstruct` ever branch on the next code point, and complicating `BeginCaptureMatcherConstruct` for every non-capturing-loop caller too.
- **Decision**: rejected. The capturing-and-quantified case instead composes existing opcodes: `LoopMatcherConstruct` → `BeginCaptureMatcherConstruct` (plain single successor) → an internal (non-self-registering) `ForkingMatcherConstruct` chain → ... → `EndCaptureMatcherConstruct` → back to the loop's entry node.

### A separate `ForkingMatcherConstruct` node per candidate, instead of `entrySet`/`failedEntry` on every node

The matcher graph's dispatch used to be a chain of dedicated fork nodes (`ForkingMatcherConstruct`: `memberSet`/`next`/`otherwise`) wrapping each candidate's own compiled matcher, rather than folding the fork into every node via an `entrySet`/`failedEntry` pair (see "Opcode set" above).

- **Pros**: a clean separation of concerns — a candidate's own compiled node never needs to know it's part of a chain at all, so no `PatternConstruct.dispatchEntrySet`/`dispatchFailedEntry` threading, no `PassThroughMatcherConstruct`/`LoopBodyPartGatePatternConstruct` machinery for constructs that alias another's matcher or need gating checked before a side effect fires. A loop's own entry point could be built as a wholly separate fork chain from its loop-back continuation, without needing the two to be proven equivalent.
- **Cons**: one extra allocated node per candidate beyond the last (an N-branch union or N-part loop body allocates N-1 fork nodes purely for dispatch, on top of the candidates' own nodes), and — for a loop specifically — a *second*, separately-built fork chain for the loop's own entry point, duplicating the routing logic the loop-back continuation already expresses. `CASE_INSENSITIVE` correctness needed a whole second pass (an exact-only chain falling through to a fold-only chain) built by `buildForkChain` itself, rather than being resolved once at chain-construction time into each candidate's own `entrySet`.
- **Decision**: rejected in favor of the current design (2026-09-18, branch `flatten-matcher-dispatch`) — see this file's "Opcode set" section. Measured effect: a small real compile-time improvement on desktop JMH (~3%) and Pixel 3a (~4%), match time an effective wash on both devices — see README's benchmark section and notes.md for the numbers. The `entrySet`/`failedEntry`-on-every-node model does cost some of what this alternative avoided: `PassThroughMatcherConstruct`/`LoopBodyPartGatePatternConstruct` exist specifically to paper over the cases where a node can't simply carry its own gating (an alias to an already-compiled or differently-gated target, or a side effect that must not fire before the gate passes).

### Inline per-node comparison (no `entrySet`), instead of a precomputed entry gate

Each node would compare `peeked` against its own data inline and, on rejection before consuming, defer to `failedEntry`; on acceptance it commits and delegates to `next`, never branching on a delegated call's result (an opcode-chain model).

- **Pros**: no `entrySet`/`dispatchEntrySet` at all, so no `CodePointSet` aggregation for dispatch, no fold-expansion of `entrySet`, and no `PassThroughMatcherConstruct`/`LoopBodyPartGatePatternConstruct`. A speculative-vs-confirmed capture split (`startedGroups` promoted by `EndCapture`) cleanly handles captures on attempts that never complete.
- **Cons**: a leaf's own comparison only answers "do I match here?", not "can anything in this subtree start here?". A `SequencePatternConstruct` with a nullable prefix needs the outer fallback threaded onto later elements too (`((a?b)c)?` vs `""` failed), which needs either combinatorial matcher duplication, a per-attempt "would you accept" query (re-adding the membership check), or a commit signal breaking `final` fields.
- **Decision**: rejected (2026-09-18, implemented and reverted) -- see notes.md.

### Speculative reluctant-loop exit with rollback, instead of a compile-time-proven-safe gate

Give `ReluctantLoopMatcherConstruct` (see "Quantifier/loop compilation" above) a genuinely speculative exit: try `next` once `min` is satisfied, and if that fails, un-do whatever it did and fall back to another body iteration — closer to how a backtracking engine actually implements reluctant quantifiers.

- **Pros**: no `exitAssertionChain` analysis needed.
- **Cons**: `LoopExitMatcherConstruct`'s own exit has side effects — it resets the loop's shared iteration counter, and (for a capturing loop) the body chain's own `BeginCaptureMatcherConstruct` has already recorded a capture start by the time exit is even considered — and any further constructs `next` reaches (nested loops' own counters, further captures) would need the same treatment. Undoing all of that on a failed speculative exit means either snapshotting mutable `Matcher` state before every attempt (allocation and complexity on every reluctant-loop iteration, not just the cases that actually need it) or making those fields non-`final`/re-derivable, undermining this whole design's "every `MatcherConstruct` field is deeply immutable, no backtracking stack" guarantee (see "The `compile()` algorithm and cycle handling" above). It would also reintroduce, for reluctant loops specifically, exactly the "try a branch speculatively, roll back on failure" shape this whole no-backtracking design exists to avoid.
- **Decision**: rejected in favor of `exitAssertionChain` (2026-09-22, extended 2026-09-23) — a purely compile-time, conservative safety proof (of which "pure end, no assertions at all" is the base case) requires no runtime rollback machinery at all. The residual case this alternative would ALSO have covered (a reluctant loop followed only by `\B`/`\b`/a `MULTILINE` `^`/`$` satisfiable before the true end, e.g. `a+?\B`) turned out not to need rollback either: `exitAssertionChain` was extended to collect that chain of assertions at compile time, and `ReluctantLoopMatcherConstruct` evaluates each one directly via `peek`/`peekPrevious` (side-effect-free, `ZeroWidthAssertionGuard#holdsHere`) BEFORE committing to the exit — check-then-commit, never speculative-then-rollback. See "Boundary matching" and "Quantifier/loop compilation" above.

### A separate `ReluctantLoopGate` node in front of the body chain's head, instead of merging into `ReluctantLoopMatcherConstruct`

Use two nodes for a reluctant-safe loop instead of one: keep `LoopMatcherConstruct` unchanged (post-iteration only, enforcing `max`, counting completed iterations directly, exactly as it does for a greedy loop), and add a separate node wrapping the body chain's head to add the "prefer to stop once `min` is satisfied" check, used as both the loop's entry point and `LoopMatcherConstruct`'s own "continue" target.

- **Pros**: no counter-shift subtlety -- `LoopMatcherConstruct` keeps counting completed iterations directly, so its logic (and the `min`/`max` values fed into it and into `LoopExitMatcherConstruct`) needs no changes at all to support reluctant loops; the two node types stay fully independent.
- **Cons**: every iteration boundary of a reluctant-safe loop pays for two node dispatches instead of one (`LoopMatcherConstruct`'s own `match()` call, then the wrapping node's), for no benefit greedy loops don't already get more cheaply with one node. The two nodes' fields also need to travel together in lockstep (same `quantifiableIndex`, same `exitNode`) despite being separate objects, since they jointly implement one conceptual decision.
- **Decision**: rejected in favor of merging both roles into `ReluctantLoopMatcherConstruct` -- the double-dispatch is purely an artifact of keeping `LoopMatcherConstruct`'s "count completed iterations" convention unchanged, not something inherent to the reluctant case. Shifting `min`/`max` by 1 (see "Quantifier/loop compilation" above) lets a single node's counter slot mean "visits to this node" instead, which is exactly what's needed to also serve as the loop's own entry point, at the cost of `LoopExitMatcherConstruct`'s own `min` needing the same shift when reached directly, and `exitAssertionChain` needing a separate `minIsZero` field rather than comparing `min` directly (a nested reluctant-safe loop's `LoopExitMatcherConstruct.min` may itself already be shifted) -- see notes.md.

### Backreferences: catch-all entry set, dropping support, or a match-time check, instead of a precise compile-time entry set

A backreference's possible first characters depend on what was actually captured at match time, so a naive compile-time treatment has to either give up precision or give up on compile time entirely. Considered instead of the precise `firstCharSet()` approach described above:

- **(A) Drop backreferences entirely.** Simplest, and sidesteps the whole problem, but backreferences are commonly used (e.g. matching a repeated delimiter or tag) and most uses (anything not conditional/loop-tail) aren't actually ambiguous — dropping them unconditionally penalizes the common case to avoid the rare one.
- **(B) Keep a catch-all entry set (`entryElse = this`, today's actual behavior) and document backreferences as always lowest-priority relative to sibling branches.** Requires no new AST analysis. But it's not really a *design* — it's documenting an accident of `BackReferencePatternConstruct`'s current stub implementation — and it produces silently-wrong-relative-to-`java.util.regex` results for any pattern where a sibling branch should legitimately win: e.g. `(a)(?:\1|b)` against `"ab"` would always try `\1` first, when the two branches are in fact statically disjoint (`{a}` vs `{b}`) and should dispatch exactly.
- **(C) Defer the disjointness check to match time.** Would allow accepting patterns whose ambiguity can't be resolved statically at all, but makes matching non-total in a way nothing else in this engine is — every other construct's validity is fully known at compile time, and match failures are only ever "input didn't match," never "pattern itself turned out to be unsupported here." Introducing a runtime-detected-ambiguity failure mode breaks that guarantee for a single construct type.
- **Decision**: rejected all three in favor of the precise `firstCharSet()`-based entry set (see "Backreferences" above), which is strictly more permissive than (A), doesn't require documenting (B)'s surprising priority rule since real disjointness is checked instead, and keeps ambiguity detection fully at compile time unlike (C).

### Client-runnable Unicode generator with an external data file, instead of the checked-in `UnicodePredicates`

Let a client run `UnicodeAnalyzer` themselves, emitting script/category/property ranges to a non-code data file (e.g. from a newer JDK's Unicode tables), which this library would load at startup and prefer over its built-in `UnicodePredicates` when present.

- **Pros**: clients could get newer Unicode data without waiting for a library release or JDK-matched regeneration; the built-in data could shrink to a minimal fallback.
- **Cons**: a fair amount of work (a file format, a parser/loader, a discovery mechanism, versioning/validation of the file against the library); slower startup and likely slower matching/compilation, since the current sets are plain compiled-in `ArrayCodePointSet`s built by generated code while a loaded file needs a runtime parse and can't be constant-folded or class-loaded lazily the same way; a new failure mode (missing/corrupt/mismatched data file) and a shrinker/packaging question on Android; and very little practical value, since Unicode data changes rarely and regenerating `UnicodePredicates.java` (see notes.md) is already a small, documented step.
- **Decision**: rejected (2026-09-19) -- not worth the work or the speed cost.

### `CANON_EQ` by normalizing the input instead of rewriting the pattern

Normalize both the pattern and the input to NFD and match the normalized forms.

- **Pros**: canonical ordering makes mark permutations identical, so there is no alternation and no ambiguity at all.
- **Cons**: every `start()`/`end()`/`group()` must be mapped back to original-input offsets; and `java.util.regex`'s own behaviour needs a rule that a match can't end in the middle of a combining sequence for a class (`[a-z]` doesn't match the `e` of `e` + U+0301) but can for `.`, which normalizing the input erases. Needs surgery across `Matcher`, regions, bounds and `hitEnd`.
- **Decision**: rejected; the pattern rewrite needs no `Matcher` changes at all.

### `CANON_EQ` with a flat alternation of spellings, as `java.util.regex` does

Emit every equivalent spelling of a cluster as its own branch.

- **Pros**: simplest possible rewrite.
- **Cons**: with two or more reorderable marks, several branches begin with the same base character, so the pattern is rejected as ambiguous.
- **Decision**: rejected in favour of the left-factored trie above, which accepts every cluster.

### Lookahead, and lookbehind wider than one code point

Support `(?=X)`/`(?!X)` in general, and/or a lookbehind body `X` that can match more than one code point (requiring either a bounded-width restriction with backward scanning, or genuine backtracking to try the assertion at each candidate width).

- **Pros**: matches `java.util.regex`'s full lookaround feature set; no "exactly one code point" restriction for users to work around.
- **Cons**: lookahead fundamentally needs to try matching the REST of the pattern speculatively before committing to the current dispatch decision, which this engine's single-pass, no-backtracking architecture has no mechanism for (and adding one would give up the linear-time guarantee this engine exists for -- see the top-level "single-pass architecture" framing this design is built around). Wider lookbehind has the same problem in the backward direction: which of several possible widths applies isn't known without trying more than one, which is exactly the kind of speculative backtracking this engine avoids everywhere else.
- **Decision**: rejected, permanently (not merely unimplemented) -- see remaining_work.md. 1-codepoint lookbehind (`LookbehindPatternConstruct`/`LookbehindMatcherConstruct`, this section above) is the one shape of lookaround that fits the existing `peekPrevious()` primitive `\b`/`\B` already use, with no speculation needed at all.

### A nullable union branch folded to the end (`a*|b` as `a+|b|`), instead of an end-of-find gate

Rewrite a union with a nullable branch so that branch's empty alternative comes last (`a*|b` ~ `a+|b|(empty)`), making every earlier branch non-nullable and the ambiguity disappear.

- **Pros**: no new matcher node; would make the tail-fallback treatment correct by construction.
- **Cons**: only equivalent under `matches()`. Under `find()`/`lookingAt()` the JDK's first alternative wins even when empty, so `a*|b` on `"b"` is `""` there and the rewrite gives `"b"`. Also observable through capture groups (`(a*)|b` sets group 1 to `""`; a synthesized empty branch would leave it unset), and allocates AST nodes on every compile that reaches it.
- **Decision**: rejected in favour of a mode-aware gate that keeps the branch's own priority position.

### Rejecting an end-of-find branch that isn't last, instead of gating it

`a*|b` as a compile error (the branch can already complete, so `b` is dead under `find()`).

- **Pros**: zero match-time cost; a clear error for a dead branch.
- **Cons**: rejects `a*|b`, which is correct and meaningful under `matches()`; the JDK accepts it, and the mode-aware gate reproduces the JDK's behavior in every mode.
- **Decision**: rejected in favour of the gate.

### `.` as an ordinary explicit any-character class, instead of a residual else claim

`.` registers its whole accept set as its entry point, so `a|.` and `.+b` are rejected as ambiguous.

- **Pros**: no special case in unions or loops; every pattern that compiles agrees with `java.util.regex`.
- **Cons**: rejects `.+b`, `a|.` and `.*x` -- some of the most common shapes in real patterns -- and contradicts the project's stated exception for `.`.
- **Decision**: rejected in favour of the residual claim.

### Resolving a residual loop body at match time, instead of computing its gate

Leave the body part ungated and let its own membership check fail over to the exit.

- **Pros**: no set difference at compile time.
- **Cons**: the body node would accept the exit's characters (`.+b` would consume the `b`); a failed check falls through to a parent, not to the exit, so it would need new fallthrough wiring in every loop shape.
- **Decision**: rejected in favour of `narrowResidualGates`.

### Treating a possessive `.` loop as residual too

- **Pros**: `.++b` compiles.
- **Cons**: it would match as `[^b]++b`, where `java.util.regex` can never match it (the possessive loop swallows the `b`); a silent divergence is worse than the ambiguity error.
- **Decision**: rejected; the pattern stays a compile error.
