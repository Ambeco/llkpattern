# Design

## Pipeline

`String pattern` → **`PatternParser`** (recursive descent) → **`PatternConstruct` AST** → **compile step** → **`MatcherConstruct` graph** → **`Matcher`** walks the graph against input, one code point at a time, with no backtracking.

### Parsing (`PatternParser` / `PatternConstruct`)

- Grammar is documented as regex-flavored BNF in comments at the top of `PatternParser.java`. It supports much of `java.util.regex.Pattern`'s syntax: groups (capturing, named, non-capturing), alternation, quantifiers (`?`, `*`, `+`, `{n,m}`, and their reluctant/possessive forms — accepted but treated as no-ops since this engine has no backtracking to be reluctant about), character classes (including nested `&&` intersection and `^` negation), escapes, boundaries (`\b`, `\B`, `\A`, `\G`, `\Z`, `\z`), and Unicode property/script/block/category classes (`\p{...}`).
- Lookahead and lookbehind are explicitly rejected at parse time (`throwUnexpectedChar("lookahead/lookbehind not supported...")`) because they can't be guaranteed to execute in linear time.
- Output is a `PatternConstruct` AST: `QuantifiedUnion` (alternation + optional quantifier + optional capture), `Sequence`, `LiteralString`, `ComplexCharacter` (a character class as a `RangeSet<Integer>`), `ComplexQuantifiedCharacter`, `BoundaryConstruct` (`^`, `$`, `\A`, `\G`, `\Z`, `\z`), `WordBoundaryConstruct` (`\b`, `\B` — split out separately, see "Boundary matching" below), `BackReference`, `EndConstruct`.

### Compilation (AST → matcher graph)

- Each `PatternConstruct` compiles itself plus its "what comes next" continuation into one or more `MatcherConstruct` nodes. This is the LL(1)-flavored core of the design: instead of a generic NFA, each construct's `buildEntryMap` computes, from the *next* possible input code point, which `MatcherConstruct` to dispatch to — represented as a `RangeMap<Integer, MatcherConstruct>` ("entryMap") plus a catch-all `entryElse`.
- The critical invariant the compiler must enforce: for any `QuantifiedUnion` (i.e. any `|` alternation, and any quantified construct's "keep looping vs. exit the loop" choice), the entry ranges of its branches must be pairwise disjoint. If two branches could both match the same next code point, that's a compile-time `PatternSyntaxException` (ambiguous branch), not a runtime backtrack. `PatternConstruct.compileAndMergeCandidates` (used by both plain alternation and loop dispatch) compiles each candidate, converts its entry ranges to a `TreeCodePointMap`, and rejects the first overlapping range with a `PatternSyntaxException` naming the candidate index and the conflicting characters.
- **Quantifier/loop compilation**: a quantified construct (`QuantifiedUnion` or `ComplexQuantifiedCharacter` with `min != 1 || max != 1`) compiles to a plain `DispatchMatcherConstruct` (built via its loop-flavored constructor — see "Opcode set" below; this is the externally-visible entry point, self-registering into `owner.matcher` to break the cycle described below) whose one dispatch map routes "continue" characters through a `LoopMatcherConstruct` (enforces `max`, then dispatches to whichever body part matched) and "exit" characters through an `EndLoopMatcherConstruct` (enforces `min`, then dispatches to `next`). The *same* map serves both the first attempt and every re-check after a successful iteration — no special-casing for `min == 0` vs `min >= 1` is needed in the dispatch map itself, because the runtime min/max counters (not two different static maps) are what make one map correct for every bound: even on the very first attempt, if the input's next character happens to look like "exit", the dispatch correctly routes there and `EndLoopMatcherConstruct` correctly rejects it if `min` hasn't been satisfied yet.
- **Capturing groups**: a capturing, unquantified `QuantifiedUnion` (`captureConstructIndex != -1`) wraps its compiled alternation-dispatch node in a `BeginCaptureMatcherConstruct` (which becomes `owner.matcher`, recording the start position), and compiles its branches against a `CaptureEndMarker` — a zero-width synthetic `PatternConstruct` standing in for the real `next` — whose own matcher is an `EndCaptureMatcherConstruct` (records the substring, then forwards unconditionally to the real `next`). Capture storage (`Matcher#captureGroups`) is a flat array indexed by a fixed `captureConstructIndex` known to both `BeginCapture` and `EndCapture` (not a stack — this engine has no recursion, so the same capture construct can never be open twice at once, and re-entering it naturally overwrites the previous `Group` — exactly regex's "last iteration wins" semantics — for free; this is exactly what the capturing-and-quantified case below relies on).
- **Capturing AND quantified at once** (e.g. `(a)*`): `DispatchMatcherConstruct`'s loop-flavored constructor takes a `captureConstructIndex` (`-1` when not capturing). When capturing: each loop body part compiles against a `CaptureEndMarker` standing in for the loop's own `owner` (instead of `owner` directly), so finishing one iteration records the captured substring before looping back rather than looping back directly; `LoopMatcherConstruct` dispatches unconditionally to a `BeginCaptureMatcherConstruct`, whose one successor is an internal (non-self-registering) `DispatchMatcherConstruct` that does the by-character dispatch among body parts (`BeginCapture`/`EndCapture` stay pure single-successor opcodes — see "Opcode set" below; this composes them rather than giving `BeginCapture` a second, branching role — see "Alternatives Considered"). Ambiguity detection is unaffected — it runs identically whether or not the loop is capturing, since capturing only changes what happens once a branch is chosen, not which branch gets chosen.
- `MatcherConstruct` subclasses (in `MatcherConstruct.java`) are the compiled, executable nodes — see "Opcode set" below for the full set and the Single/Multi-dispatching split. Each node's `match(Matcher, int peeked)` method consumes zero or more code points and advances to its successor(s), either an unconditional single successor or (for the handful of genuinely branching nodes) a range lookup on the next code point via `getNext(...)`.
- Matching is therefore just: start at the compiled root node, and recursively call `match()`. No backtracking stack is needed because ambiguity was already ruled out at compile time.

#### The `compile()` algorithm and cycle handling

`MatcherConstruct` instances are deeply immutable once built — no self-referencing mutable fields (see "Opcode set: Single/Multi dispatch split" below for why this matters, in particular for `MultiDispatchingMatcherConstruct`). But the matcher graph *does* have cycles (a loop's body eventually dispatches back to the loop's own entry `MatcherConstruct`), so something has to break the cycle during construction without the constructed node ever seeing a half-built dependency:

- Every `PatternConstruct` has a `@MonotonicNonNull MatcherConstruct matcher` field. `PatternConstruct.compile()`'s contract: if `matcher` is already non-null, return it immediately — don't rebuild. Otherwise, build `entryMap` and then construct the one `MatcherConstruct` this node compiles to.
- The key trick is in the `MatcherConstruct` subclass constructors, not in `compile()`: a `MatcherConstruct` constructor must, as its *very first* action, assign `this` to its owning `PatternConstruct`'s `matcher` field — *before* it does anything else, including looking up or compiling any of its own dependencies (e.g. what a loop dispatches back to, or what a union's branches dispatch to). Only after that assignment does the constructor walk the `PatternConstruct` graph (via each dependency's own `compile()`) to resolve the `MatcherConstruct`s it needs for its `dispatchMap`/`exitMap`, and accumulate those into its own dispatch map.
- This ordering is what makes cycles safe without any visited-set/recursion-guard bookkeeping: if compiling node A transitively needs to compile node B which loops back and needs A again, that second `compile()` call on A sees `matcher` already set (to the in-progress `A` instance) and returns it immediately, rather than recursing infinitely. The returned reference is to a real, fully-constructed-by-the-time-anyone-uses-it object — it's *only* used as a dispatch-map value (a reference to jump to), never dereferenced by the constructor that's still running, so returning a self-reference mid-construction is safe even though the object's own fields (its dispatch map) aren't filled in yet at the moment it's handed out.
- Compiling tail-to-front (i.e. `compile()` is always called with "what comes next" already known/passed in, starting from `EndConstruct` and working backwards through the pattern) makes cycles rare in practice, even though the mechanism above handles them regardless.
- The constructor navigates via a reference to its owning `PatternConstruct`, not via extra constructor arguments per dependency: `PatternConstruct` has a `next` field (recorded in `compile()`); for an *acyclic* dependency, everything a `MatcherConstruct` constructor needs is already reachable off `owner` by direct field read (`owner.next.matcher`, or `owner.entryMap`'s `PatternConstruct` values' own `.matcher` fields) — no `.compile()` call needed. Loop compilation is the one case that genuinely needs the self-registration-then-*recurse* pattern (not just self-registration-then-read): `DispatchMatcherConstruct`'s loop-flavored constructor self-registers into `owner.matcher` *first*, then calls `part.compile(owner)` for each body part — safe, since a nested attempt by the body to read `owner.matcher` again finds the (still-being-built) `DispatchMatcherConstruct` instance already there instead of recursing.

##### Opcode set: Single/Multi dispatch split

The matcher graph is a small "opcode" virtual machine:

- **`SingleDispatchingMatcherConstruct`** (abstract, holds `final MatcherConstruct next`, called via a plain virtual `next.match(...)`): the base for every node whose successor is fixed at construction time and never depends on which character was seen. Subclasses: `SingleCharMatcherConstruct` (character-class membership test via a `RangeSet`, not a `RangeMap` lookup), `LiteralMatcherConstruct`, `BeginCaptureMatcherConstruct`, `EndCaptureMatcherConstruct`, `EndLoopMatcherConstruct`, `WordBoundaryMatcherConstruct`, `BackReferenceMatcherConstruct`/`BoundaryMatcherConstruct` (the latter two still stub `match()`s for their unimplemented cases, but are structurally single-successor). `next` is safe to be `final` here because none of these nodes are ever the self-referential node in a cycle — only a loop's entry dispatch node is, and that's `MultiDispatchingMatcherConstruct`'s job (below).
- **`MultiDispatchingMatcherConstruct`** (abstract, holds a `RangeMap`-based `dispatchMap` + `elseDispatch`, deliberately not `final` — a self-referential dispatch entry, a loop dispatching back to its own entry node, is unavoidably written by a *different*, nested constructor call while this one is still running; see the class doc for the full argument for why the whole graph is still safely published): the base for the two node *shapes* that genuinely branch on the next code point: `DispatchMatcherConstruct` (a union's `|`; also, via a second, loop-flavored constructor, a quantified construct's entry/re-entry dispatch — it's literally the same class as a union's dispatch, not a separate opcode, since both are exactly "route by next character without consuming it") and `LoopMatcherConstruct` (bolts a counter/max check onto multi-dispatch, since after that check it must still route to whichever body part matched).
- **`EndLoopMatcherConstruct`** is single-successor: it checks `min`, resets the loop's counter slot to 0, then advances — the reset-on-exit is sufficient without a separate reset-on-entry step because this engine never backtracks: a failed loop attempt aborts the whole match rather than retrying with stale counter state, so the slot is already 0 whenever a loop is freshly (re-)entered.
- **`BeginCaptureMatcherConstruct`/`EndCaptureMatcherConstruct`** are pure single-successor opcodes, unrelated to looping, with the flat `captureGroups` array + fixed `captureConstructIndex` design described above (not a stack). The capturing-and-quantified case composes existing opcodes rather than giving `BeginCapture` a second, branching role — see "Alternatives Considered": `LoopMatcherConstruct` → `BeginCaptureMatcherConstruct` (single successor) → an internal `DispatchMatcherConstruct` doing the actual per-branch routing → ... → `EndCaptureMatcherConstruct` → loops back to the entry node.
- **`EndMatcherConstruct`** has no successor at all, so it extends neither base directly.

`SingleDispatchingMatcherConstruct.next.match(...)` is called as a plain virtual call — see "Alternatives Considered" for why a bound-`MethodHandle` form was tried and rejected.

#### Boundary matching (`BoundaryConstruct`/`WordBoundaryConstruct`)

Unlike every other construct (essentially "a dispatch map keyed by the next code point"), a boundary depends on matcher *state* — position, surrounding characters — not just the upcoming code point. `\b`/`\B` are the only boundary types with an actual implementation (plus a compile-time optimization the rest don't need), so they get their own `PatternConstruct`/`MatcherConstruct` pair (`WordBoundaryConstruct`/`WordBoundaryMatcherConstruct`) rather than sharing `BoundaryConstruct`/`BoundaryMatcherConstruct`'s `BoundaryEnum`-keyed dispatch.

`\b`/`\B` (word boundary / non-word-boundary) are implemented via `Matcher#peekPrevious()` (mirrors `peek()`, looking one code point backward instead of forward, bounded at `regionStart` rather than `0` since `useTransparentBounds()` is still a stub) and a dedicated `WordBoundaryMatcherConstruct`. It's a plain `SingleDispatchingMatcherConstruct` — it doesn't consume input, so it still has exactly one successor, just like every other single-dispatch node; branching on matcher state didn't require a new node *shape*, only a new field (`peekPrevious()`) to read.

On top of that, `WordBoundaryConstruct.buildMatcher()` applies a compile-time optimization: `\b`/`\B` very often sit next to a literal/character-class with a statically known "is this a word character" answer, so only one side needs checking at match time in that case. It classifies both the character just consumed and the one about to be consumed as always-word/always-non-word/unknown:
- **Peek side** (the character about to be consumed): read directly off the already-built `entryMap`/`entryElse` of `next` — no new analysis needed. If `next.entryElse != null`, or its `entryMap` ranges are a mix of word and non-word code points, the side is unknown.
- **Prior side** (the character just consumed): a `PatternConstruct.lastCharSet()` recursion, walking `LiteralString`/`ComplexCharacter`/`ComplexQuantifiedCharacter`/unquantified `QuantifiedUnion`/`Sequence`. Returns `null` (a safe "not statically known" fallback) for anything that could match zero-width, or for any construct type it doesn't recognize. `Sequence.buildEntryMap` sets this (via `lastCharSet()` on the preceding sibling) before compiling a `WordBoundaryConstruct` that isn't the first element of its `Sequence`; it's left `null` (safe, just unoptimized) otherwise.

If both sides are statically known, the boundary either always holds (compiles to a zero-width no-op, `matcher = next.matcher`) or never can (a compile-time `PatternSyntaxException` — e.g. `a\bb` is rejected, since two word characters can never have a word boundary between them; this is consistent with this project's general "unsatisfiable at compile time is an error, not a silent always-fail" philosophy, unlike `java.util.regex`, which would compile `a\bb` and just never match it). Otherwise, `WordBoundaryMatcherConstruct` only checks whichever side isn't statically known, via a small pair of enums (`PriorWordBoundaryMatchType`/`PeekWordBoundaryMatchType`) whose combinations are constructed by `WordBoundaryConstruct.buildMatcher()` so the nonsensical ones are unconstructible, and only calls the (slightly more expensive, backward-looking) `peekPrevious()` when the preceding side is the one left unresolved.

`BoundaryConstruct`'s other `BoundaryEnum` values are a mix of implemented and not:

- **`InputBegin`/`InputEnd`** (`\A`/`\z`): always the true start/end of input (`pos == regionStart`/`pos == regionEnd`) -- `MULTILINE` has no effect on either.
- **`InputEndExceptTerminator`** (`\Z`): the end of input, or immediately before the input's own *final* line terminator, if it has one -- checked by scanning forward from `pos` for a line terminator that reaches exactly to `regionEnd` (not merely one somewhere in the remaining input). This is a zero-width assertion that does not consume the terminator, so `matches()` (which requires the whole region, terminator included) still fails whenever one is present; only `find()`/`lookingAt()` (a prefix match) see the exemption -- verified directly against `java.util.regex` while implementing this, since it's easy to misremember `matches()` as tolerating it too.
- **`LineBegin`/`LineEnd`** (`^`/`$`): without `MULTILINE`, exactly `InputBegin`/`InputEndExceptTerminator`. Under `MULTILINE`, `^` also matches immediately after any line terminator (checked with `peekPrevious()`, treating a `"\r\n"` pair as ending at one position, not creating a second match point between the `\r` and the `\n`), and `$` also matches immediately before any line terminator (checked with `peek()`/the existing next-code-point machinery).
- Line-terminator recognition (`\n`, `\r`, `"\r\n"` as one unit, `\u0085`, `\u2028`, `\u2029` by default; only `\n` under `UNIX_LINES`) is implemented once, symmetrically, for both the forward (`InputEndExceptTerminator`/multiline `$`) and backward (multiline `^`) directions.
- **`PreviousMatchEnd`** (`\G`) and **`Linebreak`** are still unimplemented stubs -- see remaining_work.md's "Open Questions" for the design questions each raises (`\G` needs matcher *history*, not just position/surrounding characters; `Linebreak` has no parser producer at all and may just be dead code).

### Code point range representation

- `CodePointMap<V>` (interface) + `TreeCodePointMap<V>` (its implementation, delegating to Guava's `TreeRangeMap`) is the intended long-term replacement for ad-hoc uses of Guava `RangeSet`/`RangeMap<Integer, V>` throughout this codebase.
- `[min, max)` range convention throughout, immutable `Range`, `put`/`get`/`remove`/`containsKeys`, `union`/`difference`/`intersection`, `compute`/`computeIfAbsent`, `complement`, and `intersectionRejectingConflicts` — the last one specifically for the union/loop-ambiguity use case: it's like `intersection`, but throws `ConflictingMappingException` the moment two maps disagree on the value for an overlapping code point, which is exactly "these two branches both claim this character" in LL(1) terms.
- `CharacterClass` (a thin wrapper around `ImmutableRangeSet<Integer>`) and `PatternConstruct.ComplexCharacter`'s direct use of Guava `RangeSet<Integer>` exist independently of `CodePointMap` — see remaining_work.md's open question on whether/how these should migrate.
- `TreeCodePointMap` is deliberately not optimized for the Unicode code point domain — it's a thin adapter over a general-purpose range map, on the theory that a more specialized implementation (e.g. exploiting Unicode block/plane structure) is worth building later, once real usage patterns are known; the `CodePointMap` interface exists so that swap doesn't require touching any caller.

### Unicode support

- `NamedCharClass` maps regex-style named classes (`\p{Alpha}`, `\p{IsGreek}`, `\p{general_category=Lu}`, etc.) to underlying predicates/ranges.
- `UnicodePredicates` is a large (~12.9k line) generated-looking data file of Unicode category/script/block predicates. `unicodeanalyzer/` is presumably the code generator that produces it from Unicode Character Database source data.

### Public API shape

- `Ll1Pattern` and `Matcher` are designed to mirror `java.util.regex.Pattern`/`Matcher`'s public method surface, so callers can largely swap one for the other. See remaining_work.md for the current list of implemented vs. stubbed methods.
- **One compiled graph serves `matches()`, `lookingAt()`, and `find()`** — they don't need separate compilations. The difference between them is entirely about the `EndConstruct`/`EndMatcherConstruct` terminal: `matches()` requires the *whole region* to be consumed to succeed, while `lookingAt()`/`find()` only need a matched *prefix* (the rest of the string is allowed to be leftover). Rather than baking that choice into the compiled graph, it's a single `boolean requireFullMatch` field on `Matcher`, set immediately before each match attempt (`matches()` sets it true; `lookingAt()`/`find()` set it false) and read only by `EndMatcherConstruct.match()` (`return !matcher.requireFullMatch || matcher.pos == matcher.regionEnd;`). This mirrors how `java.util.regex`'s own NFA nodes take an "anchoring" flag rather than compiling two different automata.
- `EndConstruct` (the compile-time sentinel `Ll1Pattern.compile()` passes as the outermost `next`) registers `entryElse = this` in its own `entryMap` — reachable regardless of what character (or lack of one) comes next — rather than only the code point `-1` (Matcher's "no more input" sentinel — see `Matcher#peek()`). The latter would be sufficient for `matches()` (where reaching the terminal only ever happens at true end of input) but wrong for `lookingAt()`/`find()`: an *optional* loop's "exit" path (e.g. `a*` matched via `lookingAt()` against `"b"`) needs to be reachable at a position with real, valid leftover characters, not just at true end of string. `requireFullMatch` enforces the stricter check only when it's actually wanted.
- `Matcher#quantifiableCounts`/`captureGroups` are sized automatically from the compiled `Ll1Pattern` (`PatternParser` exposes the final quantifiable-construct count, capture-group count, and a name→`captureConstructIndex` map after `parse()` via `getQuantifiableCount()`/`getCaptureGroupCount()`/`getNamedGroups()`).
- `find()`'s unanchored search is a straightforward linear scan (`attemptMatch` at each candidate start position, `lookingAt()`-style, until one succeeds or the region is exhausted) — every candidate start position is just an ordinary `lookingAt()`-style attempt from a different `pos`.

## Alternatives Considered

### Successor dispatch via bound `MethodHandle` (`findSpecial`) instead of a plain virtual call

Considered for `SingleDispatchingMatcherConstruct.next.match(...)`: bind a `MethodHandle` to the successor's exact `match` override at construction time (via `findSpecial`, an `invokespecial`-style direct call — `findVirtual` + `bindTo` was also tried and rejected on the same grounds, since it's still an ordinary virtual dispatch under the hood) and invoke that instead of `next.match(matcher, peeked)`.

- **Pros**: in principle, skips a virtual-dispatch lookup per match step; `findSpecial`'s `invokespecial` semantics are exactly "call this one exact method," which is all a fixed `next` reference ever needs.
- **Cons**: a `MethodHandle` invocation on a non-static receiver isn't reliably inlined by any JVM, and is frequently *slower* than a plain virtual call even on newer Android runtimes — the entire performance premise doesn't hold. Getting a working, Android-API-26-compatible form at all required real complexity: `findSpecial` requires its `specialCaller` argument to be the calling `Lookup`'s own `lookupClass()` (or a subclass) — it emulates `super.foo()` from a specific class, not "call this concrete method on some unrelated object" — which fails for the common case of a `SingleDispatchingMatcherConstruct` whose successor is a sibling-hierarchy `MultiDispatchingMatcherConstruct`. The only fully-general fix, `MethodHandles.Lookup.privateLookupIn`, is Java 9+/Android API 33+ — below this project's Android floor of API 26 (worth over half of live Android devices vs. under half on API 33) — so avoiding it meant every concrete leaf class supplying its own one-line `findSpecial` call (exploiting `MethodHandles.lookup()`'s caller-sensitivity), real per-class boilerplate for no realized benefit.
- **Decision**: rejected. `SingleDispatchingMatcherConstruct.matchNext` uses a plain `next.match(matcher, peeked)`.

### `BeginCaptureMatcherConstruct` with a built-in branching role, for capturing-and-quantified loops

Considered for compiling a capturing, quantified construct (e.g. `(a)*`): give `BeginCaptureMatcherConstruct` a second mode where it itself holds a `dispatchMap` and does the per-branch routing among the loop's body parts, rather than being a pure single-successor node.

- **Pros**: one fewer node type actually allocated per capturing-loop iteration (no separate internal `DispatchMatcherConstruct`).
- **Cons**: breaks the clean Single/Multi dispatch split — a node meant to be single-successor gains a dispatch map, undermining the invariant that only `MultiDispatchingMatcherConstruct` subclasses ever branch on the next code point, and complicating `BeginCaptureMatcherConstruct` for every non-capturing-loop caller too.
- **Decision**: rejected. The capturing-and-quantified case instead composes existing opcodes: `LoopMatcherConstruct` → `BeginCaptureMatcherConstruct` (plain single successor) → an internal (non-self-registering) `DispatchMatcherConstruct` → ... → `EndCaptureMatcherConstruct` → back to the loop's entry node.
